## 1. Что мы строим

AUTOforYOU — автомобильная платформа для Украины. Три направления, **все остаются и доводятся до конца**:

1. **Пригон авто из США.** Каталог лотов, калькулятор цены «под ключ» (аукцион + доставка + растаможка),
   заявка после расчёта, отслеживание контейнера, B2B-доска для верифицированных перекупщиков.
2. **Объявления о продаже авто по Украине (C2C).** Подача, модерация, фото, фильтры, избранное,
   сохранённые поиски, жалобы, сделки, переписка, платное продвижение.
3. **Telegram-бот и канал.** Уведомления пользователям, заявки брокеру, публикация объявлений в канал.

### Главный бизнес-сценарий (пригон)

Клиент считает цену в калькуляторе → видит примерную стоимость → оставляет заявку (имя, телефон,
удобный способ связи, параметры расчёта) → заявка **мгновенно** приходит брокеру (в Telegram и в админку)
→ дальше брокер общается с клиентом лично. Брокер работает через админку/кабинет со статусами заявок.

## 2. Ключевой принцип: «сайт готов, осталось вставить данные»

Сейчас цель — **полностью рабочий сайт**, а не реальные цены и ключи. Тарифы брокера, цены продвижения,
API-ключи, SMTP, LiqPay, домен владелец добавит **в самом конце**.

Поэтому каждая внешняя зависимость должна быть сделана так:

- **Всё настраивается без правки кода.** Ключи и адреса хранятся в `.env`. Цены, тарифы, ставки,
  тексты для брокера редактируются в Django Admin (модели настроек/тарифов), а не хардкодятся.
- **Внешние API — через адаптеры.** Для каждого провайдера (курс НБУ, VIN/NHTSA, carVertical,
  Opendatabot, источник лотов, LiqPay, SMTP, Telegram) есть интерфейс, реальная реализация
  и demo/sandbox-реализация. Переключение — одна переменная в `.env`.
- **Честный статус «не настроено».** Если ключа нет, сайт не падает и не показывает фейковые данные
  как реальные. Пользователь видит понятное сообщение, а админ — статус интеграции.
- **Тестовые данные помечены как тестовые**, пока владелец не вставит реальные (например, `is_estimate`
  и баннер «демо» в калькуляторе). После заполнения данных пометки исчезают автоматически.
- **Единый список того, что заполняет владелец** — `docs/LAUNCH_CHECKLIST.md`: каждая переменная `.env`,
  каждая таблица в админке, где взять значение, как проверить, что работает.

Итог: владелец подключает домен, заполняет `.env` и админку по чек-листу, запускает `docker compose up`,
и всё работает.

## 3. Требования к безопасности и личным данным (обязательные)

- **Токены:** JWT не хранятся в `localStorage`. Используются httpOnly + Secure + SameSite cookie,
  включена CSRF-защита, SSR Next.js продолжает работать.
- **Регистрация:** подтверждение email, согласие на обработку данных (уже есть), капча или
  эквивалентная защита от ботов (бесплатное решение).
- **Пароли:** стандартное хеширование Django, валидаторы сложности, сброс пароля по email
  (ссылка одноразовая, с ограниченным сроком), смена пароля в кабинете, отзыв всех сессий при смене.
- **Защита от перебора:** ограничение попыток входа по IP и аккаунту, временная блокировка.
- **Доступ к данным:** телефон, email и заявки видит только владелец, брокер/админ по роли.
  На каждый эндпоинт с личными данными есть тест на 401/403 для чужого пользователя.
  Нет утечек через списки, сериализаторы, сообщения об ошибках, sitemap, SSR-HTML.
- **Права пользователя (закон Украины о защите персональных данных):** удаление аккаунта,
  выгрузка своих данных, политика конфиденциальности и cookie (страницы уже есть — проверить связку).
- **Загрузки файлов:** проверка типа и размера, удаление EXIF-геоданных с фото, безопасные имена.
- **Инфраструктура:** секреты только в `.env`, HTTPS, HSTS, безопасные заголовки (CSP и др.),
  порт БД не наружу, бэкапы Postgres, логирование без личных данных.
- **Роли:** buyer / dealer / broker / admin. Если отдельной роли broker нет — предусмотреть.

| 7 | Готовность к запуску | Деплой-сценарий под любой VPS, домен + HTTPS, бэкапы, мониторинг ошибок, LAUNCH_CHECKLIST.md, финальный прогон всех тестов |

**Реальные цены и ключи — после этапа 7, их заполняет владелец. Это не задачи для Claude.**

## 5. Определение «готово» для любой задачи

1. `python manage.py test` — все тесты зелёные.
2. `cd frontend && npm run build` и `npx tsc --noEmit` — без ошибок.
3. Написаны Playwright-тесты на новую/изменённую функцию: успешный сценарий и сценарий ошибки или
   попытки обхода. Для функций без UI (бот, фоновые задачи) — Django-тесты с моками внешних API.
4. Нет новых хардкод-значений цен, ключей, контактов — только `.env` или админка.
5. Обновлены `ROADMAP.md` (галочка), `PROGRESS.md` (что сделано и что осталось)
   и `docs/LAUNCH_CHECKLIST.md` (если появилось что-то, что заполняет владелец).

## 6. Правила работы

- Одна сессия — одна задача. Модули вне задачи не трогать.
- Перед изменениями — короткий план, после одобрения — код.
- Никаких молчаливых заглушек и выдуманных данных. Если нужно решение владельца — вопрос в отчёт.
- Схему БД менять только через миграции, с объяснением причины.
- Файлы не удалять без согласования. Неиспользуемое скрывать feature-флагами.
- Язык документации и отчётов — русский.
