# Сценарий демонстрации

Прописанный порядок показа. Смысл документа в том, чтобы не импровизировать: на демо всегда что-то идёт не так, и заранее известный порядок плюс заготовленные ответы экономят больше времени, чем любая подготовка слайдов.

Рассчитано на **15 минут** показа плюс вопросы.

## Порядок показа

### 1. Что это за проект — 1 минута

Открыть http://localhost

> Маркетплейс автомобилей. Два направления: импорт с аукционов США под ключ и каталог локальных объявлений по Украине. Стек — Django с DRF на бэкенде, Next.js на фронте, всё в Docker.

Показать: главная → «Два напрямки» → «Як це працює» → блок расчёта с живым курсом НБУ.

Не углубляться. Это только контекст.

### 2. С чего начал — аудит, 2 минуты

Открыть `AUDIT.md` в редакторе.

> Проект принимал на поддержку. Перед тем как что-то трогать, провёл аудит: инвентаризация, проверка работоспособности руками, безопасность, расхождения кода и документации.

Назвать три находки — коротко, без чтения вслух:

- **Ставки растаможки оказались верными**, хотя сайт на каждой странице писал «тестовые тарифи, плейсхолдери». Сверил с законом: бензин 50/100 €/л, дизель 75/150, мито 10%, ПДВ 20% — всё совпадает. Дисклеймер был пессимистичнее реальности.
- **Аналитики нет ни одной**, при этом баннер согласия на cookie имитировал выбор: обе кнопки писали разные значения в `localStorage`, но их никто не читал.
- **Каталоги не индексировались**: данные грузились на клиенте, робот видел пустую сетку — а `sitemap.xml` при этом обещал ему эти страницы.

### 3. Как ведётся работа — 2 минуты

Открыть вкладку с Issues.

> Каждая задача — Issue с меткой и критериями готовности. Ветка режется от `main` и привязывается к Issue через `gh issue develop`, поэтому связь видна на доске.

Открыть любой закрытый PR, например #25.

> Каждый PR — одна тема. Внутри атомарные коммиты: один коммит — одно логическое изменение, откатывается отдельным `revert`. В описании — что было, что стало, чем подтверждается.

Показать в PR #25 блок с curl до и после.

> `main` защищён: прямой push запрещён, три проверки обязательны. Проверить легко:

```powershell
git switch main
git commit --allow-empty -m "demo"
git push origin main
```

Ожидаемо: `protected branch hook declined`. Это успех.

```powershell
git reset --hard origin/main
```

### 4. Playwright — 5 минут, основная часть

```powershell
cd D:\pyCharm\AUTOforYOU\frontend
npx playwright test
```

> 33 теста, около 18 секунд.

Пока идёт — сказать главное:

> Когда принимал проект, тестов было девять. Три из них **не могли упасть в принципе**.

Открыть `docs/TEST_CASES.md`, раздел «Как отличить настоящий тест от фальшиво-зелёного». Показать первый пример:

```ts
const banner = page.locator('[role="alert"]');   // объявлен
await expect(page.locator('main')).toBeVisible(); // а проверяется main
```

> Тест назывался «demo banner is visible», объявлял локатор баннера и никогда его не проверял. Причём баннера на той странице нет вообще.

Дальше — отчёт:

```powershell
npm run test:e2e:report
```

Показать HTML-отчёт: список тестов, шаги, время.

Затем **UI-режим** — главный рабочий инструмент:

```powershell
npm run test:e2e:ui
```

Показать: дерево тестов, запуск одного теста, вкладку Locator, подсветку элемента на странице.

Закрыть. Дальше **codegen**:

```powershell
npm run test:e2e:codegen
```

Покликать по сайту, показать, как генерируется код.

> Это черновик, а не готовый тест. В проекте есть след такого черновика: первая строка была `goto('chrome-error://chromewebdata/')` — codegen записал страницу ошибки Chrome, потому что стартовал с недоступного адреса. Его пришлось переписывать.

Закрыть.

Если останется время — **trace**:

```powershell
npx playwright show-trace test-results\<папка>\trace.zip
```

> Trace Viewer показывает, что происходило внутри браузера: таймлайн, снимок DOM на каждом шаге, сеть, консоль. Причём посмертно — перезапускать не нужно.

Trace пишется только для упавших тестов. Если все зелёные, заранее подготовить один упавший прогон — см. «Если что-то пошло не так».

### 5. Проверка мутацией — 2 минуты, самое сильное место

> Зелёный прогон ничего не доказывает. Старые тесты тоже были зелёными. Доказывает только то, что тест краснеет, когда поведение ломается.

Показать в PR #28 блок «Проверка мутацией»:

```
x  1 каталог України віддає вміст без JavaScript      <- покраснел
x  2 каталог імпорту віддає вміст без JavaScript      <- покраснел
ok 3 головна віддає блоки без JavaScript
ok 4 sitemap містить каталог України
```

> Откатил каталоги к клиентской версии, пересобрал контейнер, прогнал. Покраснели ровно те два теста, что зависят от серверного рендера. Остальные не затронуты. После проверки версию восстановил.

### 6. Пайплайн — 2 минуты

Открыть вкладку Actions.

> Когда принимал проект, тесты в CI не запускались ни разу. Шага с ними не было вообще, а `manage.py check` был завершён `|| true` — джоб не мог упасть в принципе. Пайплайн был зелёным по построению, а не по результату.

Открыть любой недавний прогон, показать три джоба:

| Джоб | Что делает |
|---|---|
| Backend checks | ruff, системные проверки, миграции, 394 теста |
| Frontend checks | eslint, tsc, сборка |
| E2E tests | поднимает **весь стек в docker compose** и гоняет Playwright против него |

> E2E-джоб поднимает стек с `DEBUG=false`, то есть в прод-конфигурации, а не в отладочной. HTML-отчёт сохраняется артефактом на 7 дней.

Показать артефакт `playwright-report` внизу страницы прогона.

## Если что-то пошло не так

| Симптом | Причина | Что делать |
|---|---|---|
| Сайт отдаёт 502 | Стек не успел подняться | `docker compose ps`, ждать `(healthy)` |
| `failed to connect to the docker API` | Docker Desktop не запущен | Запустить, подождать значок кита |
| `did not expect test.describe() to be called here` | Запуск из корня репозитория | `cd frontend` |
| `Executable doesn't exist at ...chromium_headless_shell` | Версия браузеров не совпадает с Playwright | `npx playwright install chromium` |
| `ERR_CONNECTION_REFUSED at http://localhost:3000` | Задана старая `E2E_BASE_URL` | `Remove-Item Env:\E2E_BASE_URL` |
| Тесты зелёные, а нужен trace | Trace пишется только для упавших | Заранее подготовить упавший прогон |

**Как подготовить упавший прогон для показа trace.** До демо временно сломать один ассерт в копии спека, прогнать, получить `trace.zip`, вернуть как было. Артефакт останется в `test-results/`.

**Если сеть отвалилась.** Всё, кроме вкладок GitHub, работает локально. Заранее сохранить скриншоты страницы Actions и одного PR.

## Чего на демо не показывать

- Не открывать `.env` — там реальный токен Telegram-бота.
- Не запускать `docker compose down -v` — снесёт тома вместе с базой.
- Не мержить PR вживую, если CI ещё идёт: три обязательные проверки занимают около четырёх минут, пауза убьёт темп.
- Не обещать, что калькулятор готов к реальным сделкам: ставки растаможки верные, но логистика и аукционные сборы — базовые, их подтверждает брокер.

## Вопросы, которые зададут

**«Почему тестов всего 33, это же мало?»**
E2E дорогие и медленные, их держат тонким слоем поверх основной пирамиды. Под ними 394 backend-теста с покрытием 80%. E2E проверяют сквозные сценарии и то, что видит пользователь, а не каждую ветку логики.

**«Почему не покрыт личный кабинет?»**
Нужна авторизация и подготовленные данные. Правильное решение — логин через API в `globalSetup` и переиспользование `storageState`. Это следующий шаг, он записан в `docs/TEST_CASES.md`.

**«Зачем docker compose в CI, если есть моки?»**
Мок проверяет договорённость, а не систему. E2E-джоб поднимает настоящий Postgres, Redis, Django и Next — и ловит то, что моки пропускают: миграции, seed тарифов, конфигурацию nginx. Один раз это уже сработало: с `DEBUG=false` Django редиректил весь HTTP на HTTPS, и без реального стека это не всплыло бы.

**«Почему тесты не в одном языке?»**
Названия тестов на украинском, потому что они описывают интерфейс, а он украиноязычный — так их проще сверять с тем, что видно на экране. Комментарии в коде на русском, как и в остальном проекте.
