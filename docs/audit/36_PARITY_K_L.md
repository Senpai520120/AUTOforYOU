## Расхождения и находки этого пакета

1. **UTM из Q4 нигде не запланирован.** ANSWERS Q4: к заявке «прикрепляются снимок расчёта и источник (UTM, реферер, страница)». В задачах 2.1 и 2.3 `source` — только `calculator`/`listing` (2.1:37); Grep `utm|referrer` по docs/tasks и по коду пуст (в проекте «utm» только в ANSWERS, эталоне и README). Фронт ничего не сохраняет при первом заходе. Пункт K3.3. Данные нельзя восстановить задним числом, поэтому Запуск.
2. **У заявки нет email.** Поля 2.1:38: имя, телефон, способ связи, ник. Гостю (Q4: регистрация не нужна) нечего слать письмом и нельзя «отправить расчёт себе»; статус заявки гость увидеть не может (кабинет `/me/leads` только у вошедших). Влияет на K2.3, K6.1, L3.9.
3. **Постоянная ссылка на расчёт против очистки.** 2.6:56 удаляет анонимные `Calculation` старше `ANON_CALCULATION_TTL_DAYS`, исключая только привязанные к заявке или `Listing`. Расчёт с публичной ссылкой (K2.2) тоже нужно исключить, иначе ссылка «умрёт». Ссылка по `id` недопустима: он последовательный (pricing/models.py:209), любой может перебрать чужие расчёты; нужен неугадываемый токен.
4. **Письма уходят синхронно и без таймаута.** `send_mail(..., fail_silently=True)` прямо в запросе (users/services.py:74, local_listings/services.py:62); `EMAIL_TIMEOUT` в настройках нет (core/settings.py:333-344). Медленный SMTP подвесит запрос модерации или одобрения дилера, а сбой не виден. 3.4 переводит все `send_mail` на сервис и показывает статус (3.4:54, 3.4:79), но очередь Celery для писем не вводит. Пункт L2.1.
5. **Статусы заявки покрывают только начало пути.** 2.1:23 — `new → in_progress → contacted → won/lost/spam`. Этапов эталона «договор → авто куплено → в пути → растаможка → выдано» нет, связи заявка → контейнер тоже нет (2.10 даёт лишь действие «Додати клієнта до контейнера», 2.10:32, без внешнего ключа). Для запуска достаточно (брокер ведёт сделку по телефону, контейнер — отдельная сущность), но CRM остаётся без сквозной картины. Пункты K4.2, K6.4.
6. **Надёжность доставки заявки: нет резервного канала.** 2.2:22-23 при отсутствии токена/chat_id ставит `skipped_not_configured`, при сбое Telegram — три повтора по 30 с и `failed` (2.2:47); дальше только ручное «Надіслати повторно». Заявка в БД не теряется, но брокер может о ней не узнать. Резервного email нет совсем. K5.2, K5.3.
7. **Тексты писем не в админке.** Бриф §2 требует тексты для брокера в админке (BRIEF.md:34): это закрыто для заявки (2.2), бота (5.4) и сообщений/сделок (4.7). Письма пользователям — файлы-шаблоны (1.6:39, 1.7:24) или код (local_listings/services.py:47-60, users/services.py:66-74). Для запуска допустимо (владелец не обязан править письма), для роста нужна общая модель (Н-31). Решение основной сессии: оставить как есть до Н-31.
8. **Подпись «Детализация стоимости «под ключ»» и все подписи таблицы — по-русски** (CalcBreakdown.tsx:19-37); перевод — 6.4, процентные подписи — 2.6 (09-C2). Здесь не дублируется.
