# Задача 8.9: Учёт упавших Celery-задач (`FailedTask`), базовый класс повторов, оповещение в мониторинг

> Источник: Н-44a (`docs/audit/39_PARITY_Q_R.md`, Q3.1, Q3.2; ANSWERS, шаг 9: Запуск; `docs/audit/32_NEW_TASKS_INDEX.md`). Волна: [ВОЛНА-1] (до открытия регистрации, вместе с бэкапами и мониторингом). Оценка: 1 сессия. Security-reviewer не обязателен: ПДн не пишутся, аргументы проходят `scrub` из 7.2. Админка со списком и действием «повторить» — этап 9 (9.35), здесь только запись и просмотр.

## Контекст
- Повторы есть только у четырёх задач: `integrations/tasks.py:10-16` (`import_lot_task`) и `:47-53` (`send_notification`), `pricing/tasks.py:12-18` (`fetch_nbu_rates_task`, `autoretry_for=(URLError,)`), `telegram_bot/tasks.py:13-19` (`post_listing_to_channel`). Остальные (`saved_searches/tasks.py:8` `check_saved_searches`, `local_listings/tasks.py:7` `warn_expiring_listings`, `:44` `expire_listings`) повторов не имеют; идемпотентные ежедневные задачи допускают пропуск (следующий запуск подберёт), письма и Telegram — нет.
- После последнего повтора задача просто исчезает: ни `task_failure`-обработчика, ни таблицы упавших задач, ни `acks_late` (Grep по `*.py` пуст). Заявки брокеру закрывает 2.12 (досыл), но остальные задачи (письма 3.4, Telegram, поиски) остаются «немыми».
- `core/celery.py:7-9` создаёт приложение и подхватывает задачи. Настройки: `core/settings.py:355-368` (брокер, `CELERY_TASK_ALWAYS_EAGER` в тестах, `CELERY_TASK_EAGER_PROPAGATES=True`, `DatabaseScheduler`), расписание `:373-394`.
- Ловушка тестов: в eager-режиме с `CELERY_TASK_EAGER_PROPAGATES=True` исключение пробрасывается напрямую, и сигнал `task_failure` не отправляется. Тест должен либо временно выключить `app.conf.task_eager_propagates` (с `addCleanup`), либо вызывать обработчик сигнала напрямую; проверить по факту.
- Из задач, от которых зависит эта: 7.2 даёт `core/logging_filters.py: scrub(text)` (убирает email, телефоны, токены и ключи; `docs/tasks/7.2-prod-settings-logging.md`), 7.6 даёт `core/monitoring.py: capture_message(msg, level, extra)` (no-op при пустом `SENTRY_DSN`; `docs/tasks/7.6-error-monitoring.md`). Эта задача их использует, свои версии не создаёт.
- Приложения `core` в смысле Django нет (`CLAUDE.md`, таблица приложений), поэтому нужно маленькое приложение `task_ledger`.

## Цель
- [ ] Сигнал Celery `task_failure` (когда задача окончательно упала, включая исчерпанные повторы) создаёт запись `FailedTask`: `task_name`, `task_id`, `failed_at`, `retries`, `exception_class`, `error` (текст после `scrub`, обрезан), `args`/`kwargs` в безопасном виде, `queue` (если известна). Запись создаётся вне транзакции задачи и **никогда не бросает исключение** (ошибка записи только логируется).
- [ ] Безопасное представление аргументов: целые, булевы, `None` — как есть; строки — после `scrub`, не длиннее `FAILED_TASK_ARG_MAX_LEN`; словари, списки и прочие объекты — только тип и длина (`<dict:3>`). Тексты писем и сообщений, телефоны и email в таблицу не попадают.
- [ ] Каждая окончательная неудача отправляется в мониторинг: `capture_message('Celery task failed: <имя>', level='error', extra={task_name, task_id, retries, exception_class})` (без аргументов и текста ошибки). При пустом `SENTRY_DSN` ничего не происходит и сайт не падает.
- [ ] Базовый класс `core/tasks.py: ResilientTask` для сетевых задач: `autoretry_for=(OSError, ConnectionError)`, `retry_backoff=True`, `retry_jitter=True`, `max_retries` и `acks_late` из настроек (`CELERY_TASK_MAX_RETRIES`, `CELERY_TASK_ACKS_LATE`, значения по умолчанию из `.env`). Задачи подключают его явно (`base=ResilientTask`); глобальная подмена `task_cls` не используется, чтобы не менять поведение чужих задач.
- [ ] Класс применён к задаче без повторов, где потеря неприемлема: `saved_searches.tasks.check_saved_searches` (если после 4.4 у неё нет своих повторов). Четыре задачи, у которых повторы уже есть, не переписываются (их параметры покрыты тестами), но их окончательные неудачи тоже попадают в `FailedTask` через сигнал. Письма и Telegram 3.4 и новые задачи 2.12 используют базовый класс при выполнении своих задач.
- [ ] Чистка: ежедневная задача удаляет записи старше `FAILED_TASK_RETENTION_DAYS` (`.env`), запись в `CELERY_BEAT_SCHEDULE`.
- [ ] Админка `FailedTaskAdmin`: только чтение (add, change, delete запрещены), фильтры по имени задачи и дате, поиск по `task_name`; доступна admin/superuser. Действие «повторить» и журнал аудита — 9.35.

## Шаги
1. Приложение `task_ledger`, модель `FailedTask` и миграция (причина: окончательная неудача задачи сейчас не оставляет следа и не приходит в мониторинг). Индекс по `(task_name, failed_at)`.
2. `sanitize.py`: `safe_repr(value)` по правилам цели; `scrub` из 7.2. Модульные тесты на email, телефон, токен, длинную строку, вложенные структуры.
3. `signals.py`: обработчик `task_failure` (аргументы `sender`, `task_id`, `exception`, `args`, `kwargs`); внутри `try/except Exception` с логом `logger.exception` без аргументов задачи; затем `capture_message`. Подключение в `AppConfig.ready()`.
4. `core/tasks.py`: класс на базе `celery.Task` с атрибутами повторов из `settings`. Проверить, что `bind=True` и `base=ResilientTask` работают вместе.
5. Применить к `check_saved_searches`, добавить чистку и расписание.
6. Админка, `CLAUDE.md`, переменные в `.env`.

## Тесты
Django (`task_ledger/tests.py`; `capture_message` замокан, сети нет; сигнал тестируется с учётом ловушки eager-режима из «Контекста»):
- Задача бросает `ValueError('boom')` → одна запись `FailedTask` (имя, id, класс исключения, `retries`), `capture_message` вызван один раз с `extra` без аргументов.
- Задача с `ResilientTask` бросает `ConnectionError` → повторяется до лимита (`max_retries` из `override_settings`), затем одна запись, а не по записи на каждый повтор.
- В аргументах `('+380501234567', 'user@example.com', {'a': 1}, 42, None)` → в записи нет телефона и email, словарь заменён `<dict:1>`, число сохранено; строка длиннее лимита обрезана.
- Ошибка записи в БД внутри обработчика (мок `FailedTask.objects.create` бросает) → исключение не уходит наружу, мониторинг всё равно получает событие; в логе нет аргументов задачи.
- `SENTRY_DSN=''` (мок `capture_message` как no-op) → запись создаётся, ошибок нет.
- Чистка удаляет записи старше `FAILED_TASK_RETENTION_DAYS`, свежие оставляет.
- Админка: add/change/delete → 403; `moderator` и `broker` раздел не видят.
- `check_saved_searches` после подключения базового класса по-прежнему проходит существующие тесты `saved_searches/tests.py`.
Playwright: нет UI для пользователя. Просмотр списка в админке проверяется Django-тестом на changelist (200, в HTML имя задачи и время, нет значений аргументов).
