## Цель
Принятые решения (обосновано, подтвердить владельцу пунктами в конце):

1. **Точный повтор по ключу** (`Idempotency-Key`, UUID от клиента, один на открытие формы): вторая и следующие отправки с тем же ключом и тем же нормализованным телефоном возвращают **первую заявку** (`200`, тот же публичный ответ `LeadCreatedSerializer`, заголовок `Idempotent-Replay: true`) **без новой записи, без нового номера `AFY-…`, без уведомлений, журнала партнёру и метрики**. Причина: это одна и та же отправка (двойной клик, ретрай после обрыва), брокеру второй сигнал не нужен.
2. **Тот же телефон в окне без ключа или с новым ключом** (человек закрыл форму и отправил заново, другой лот/комментарий): создаётся **новая** заявка (содержание могло отличаться, терять его нельзя) с `duplicate_of` → первая заявка окна и пометкой «повтор». Брокер **получает уведомление, но с пометкой «🔁 Повтор заявки AFY-…»** (а не как о новой): для этого достаточно одной строки перед основным текстом, шаблон из админки не меняется. Повтор с ПДн уходит брокеру и партнёру, то есть это передача ПДн: запись в журнал партнёру (2.15, согласие `partner_transfer`) создаётся как для обычной заявки, с пометкой «🔁 Повтор заявки AFY-…» в тексте журнала (без смены схемы). Метрика `lead_created` для повтора не растёт (воронка считает одного клиента). Точный повтор по ключу журнал не пишет. Счётчик «без ответа» (10.6) повторы не считает.
3. **Чужой ключ**: ключ уже есть, а нормализованный телефон другой → `409` с общим текстом без ПДн и без `public_id` («Ця заявка вже надіслана з іншими даними. Оновіть сторінку та спробуйте ще раз.»). Запись не создаётся. Ключ без знания телефона первой заявки ничего не раскрывает; ответ при совпадении — только `public_id`, `status`, `created_at`.
4. **Окно** для пункта 2 — настройка `LEAD_DUPLICATE_WINDOW_MINUTES` в `.env` через `_positive_int_env` (`core/settings.py`), стартовое значение в `.env.example` — 60 (не из закона; подтвердить владельцу). `0` отключает проверку по телефону (ключ работает всегда). Хардкода в коде нет.
5. Порядок в `LeadCreateView.post`: throttle → honeypot → 503 `partner_name` → **поиск по ключу** (только если заголовок валидный UUID; телефон нормализуется для сверки, при ошибке формата поиск пропускается и сработает обычная валидация 400) → капча → поля → создание. Поиск стоит **до капчи**: токен капчи одноразовый, у ретрая он уже использован, иначе повтор получил бы 400 `captcha_failed`.
6. Гонка двух одновременных POST с одним ключом: уникальный индекс по `idempotency_key` + перехват `IntegrityError` → повторное чтение и возврат первой заявки (как в 1). Номер `AFY-…` при откате транзакции расходуется только у проигравшего запроса (счётчик внутри `atomic()` откатывается вместе с ним).
7. ПДн: окно сравнивает `Lead.phone` с нормализованным номером, номер, ключ и тело запроса в логах и метриках не пишутся; в лог идут только `lead_id`/`public_id` и причина (`lead.dedup reason=key|phone_window`). Повтор не раскрывает данные чужой заявки: в окне по телефону первая заявка находится сервером для ссылки `duplicate_of`, но публичный ответ новой заявки остаётся прежним (свой `public_id`, без поля про первую).
8. Клиент: `LeadForm` генерирует UUID (`crypto.randomUUID()`, запасной вариант при недоступности) при монтировании и хранит в `useRef`; ключ **не меняется** при ошибках 4xx/5xx/обрыве (повторная отправка = тот же ключ) и **меняется** только после успеха и «Надіслати ще» (`onNew`). Заголовок `Idempotency-Key` уходит в каждом `leadsApi.create`. Повторный клик в тот же тик защищён и `useRef`-флагом (в дополнение к `submitting`).
9. Кабинет брокера и админка: у повтора бейдж «Повтор» + ссылка на первую заявку (`duplicate_of` → `public_id`, только `public_id`).

## Шаги
1. Миграция `0012`: только `AddField` (никаких `RunPython`, существующие строки не меняются): `Lead.idempotency_key = UUIDField(null=True, blank=True, unique=True, editable=False)` и `Lead.duplicate_of = ForeignKey('self', null=True, blank=True, on_delete=SET_NULL, related_name='duplicates', editable=False)`. Индекс для окна: `Index(fields=['phone', '-created_at'], name='lead_phone_created_idx')` (запрос окна без него сканирует таблицу; телефон уже хранится в этой колонке, новых ПДн не появляется). Причина изменения схемы: идемпотентность должна переживать рестарт и несколько воркеров, кэш не гарантирует.
2. `services.py`: `find_replay(key, phone)` → `Lead | None` либо `KeyConflict`; `find_phone_duplicate(phone, now)` → первая заявка окна (`duplicate_of IS NULL`, `created_at >= now - window`, статус любой; если найденная сама повтор, берётся её `duplicate_of`). `create_lead(..., idempotency_key=None)` ставит поля, а для повтора вызывает `_after_commit(is_duplicate=True)`: уведомление брокеру и запись журнала партнёру с пометкой, без метрики.
3. `views.py`: разобрать заголовок `request.headers.get('Idempotency-Key')` через `uuid.UUID`; невалидный → игнорировать (не 400, чтобы не ломать клиентов без ключа); реализовать пункты 1, 3, 5, 6 цели; OpenAPI: `parameters`, ответы 200 и 409.
4. `notify.py`: функция-обёртка над `render_new_lead_text`, добавляющая строку «🔁 Повтор заявки {первая AFY-…}» (учитывать лимит `tg_len`, `MessageTooLong`); письмо брокеру — та же пометка в теме/теле без ПДн (политика «email завжди PII-free» из 9.56 сохраняется); in-app: `Повторна заявка {public_id}`.
5. Settings, `.env.example`, `.env.docker.example`, CORS-заголовок.
6. Фронтенд: ключ в `useRef`, заголовок, сброс ключа в `onNew`; `useRef`-флаг от двойного вызова в один тик.
7. Брокерские сериализаторы и бейдж в кабинете; админка.
8. Тесты (ниже), `openapi.yaml`, документация.

- Повтор повтора ссылается на корневую заявку (цепочка не растёт).
- Вне окна (`mock.patch('django.utils.timezone.now')`, граница `N` минут −1 с / ровно N): обычная заявка, `duplicate_of is None`, обычное уведомление. `LEAD_DUPLICATE_WINDOW_MINUTES=0` — окно выключено. Телефоны в разной записи (`0501234567`, `+380 50 123 45 67`) считаются одним.
- Разные телефоны в окне — не повтор; заявка того же человека без телефона-совпадения не затрагивается.

Playwright (`frontend/e2e/lead-duplicates.spec.ts`; пользователи `…@e2e.test`, записи с `[E2E]`, ошибки по тексту):
