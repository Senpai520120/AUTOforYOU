# Задача 1.13: Журнал аудита и блокировки пользователей с причиной и автором

Метка волны: [ВОЛНА-2] (ВОЛНА-1 от журнала не зависит; 1.2 даёт точку расширения). Если владелец потребует журнал с первого дня регистрации — поднять до [ВОЛНА-1], оценка не меняется.
Риск: высокий. После выполнения обязательна проверка security-reviewer (права на журнал, ПДн, блокировки).

## Контекст
Требование владельца Q10 (`docs/ANSWERS.md`): все действия модераторов и админов пишутся в журнал аудита. Сейчас журнала нет (пункты эталона C6.4, C7.1, C7.2, P3.4, Q3.6; `docs/audit/32_PARITY_C_D.md`, Н-8).

Что сейчас в коде:
- Бан пользователя — булевы `is_banned` и `is_active=False` (`users/models.py:39`). Причина, автор и время не хранятся.
- Бан реализован дважды, копипастой: админ-действие `ban_users` (`users/admin.py:8-23`) и `ban_reported_user` (`reports/admin.py:23-41`). Оба: ставят флаги, переводят `active`/`pending` объявления в `hidden` (`users/admin.py:16-19`, `reports/admin.py:34-37`), `queryset.update`/`save(update_fields=...)` без записи «кто и почему». Разбан `unban_users` (`users/admin.py:26-28`) — `queryset.update(...)`, без следа.
- Экшены жалоб `hide_listing` (`reports/admin.py:8-17`) и `dismiss_report` (`reports/admin.py:46-48`, `queryset.update`) не оставляют записи. Стандартный `LogEntry` Django пишется только для правок через формы ModelAdmin и не хранит «до/после».
- Модерация объявлений: `approve_listing` и `reject_listing` (`local_listings/services.py:19-38`) пишут только `moderated_by` и `moderated_at` на самом объявлении; повторная модерация затирает прошлую запись.
- Роли и действия «Призначити брокером/модератором» появятся в 1.2 (`users/admin.py`); там по задаче только вызов точки расширения, если 1.13 ещё нет.
- Обезличивание аккаунта (Q3, 1.8) не должно терять причину блокировки: нужна защита от повторной регистрации (C6.4).
- `core` не входит в `INSTALLED_APPS` (`core/settings.py:48-80`), поэтому журнал живёт в новом приложении.

Зависимые задачи: 4.3 (`block_listing`/`unblock_listing`, G1.3) и 4.5 (действия модератора по жалобам) только вызывают сервис журнала из этой задачи, собственной модели журнала не заводят. Блокировка пользователей (`block_user`) принадлежит этой задаче.

## Шаги
1. Тесты-сначала (см. «Тесты»).
2. Приложение `audit`: модель, миграция, `log_action`, защита от изменения. Причина новой схемы: журнал должен быть неизменяемым и независимым от `LogEntry` Django (тот не хранит «до/после» и не пишется из `queryset.update`).
3. Миграция `users`: `UserBlock` + частичный `UniqueConstraint` + data-миграция для текущих забаненных. Причина: хранить причину, автора и время блокировки (C6.4); `is_banned` остаётся быстрым флагом для проверки при входе.
4. Сервисы `block_user`/`unblock_user` в одной транзакции; объявления скрывает приватный хелпер `_hide_listings_of(user)` (единая точка для замены на `blocked` в 4.3).
5. Админка: экшены `ban_users`/`unban_users`/`ban_reported_user` вызывают сервисы; промежуточная страница ввода причины (стандартный приём Django: `action` → `TemplateResponse` с формой). Журнал в админке: `AuditLogAdmin` только чтение, фильтры по `action`, `actor`, дате, поиск по `target_repr`; доступ — `has_module_permission` только для `admin`/суперпользователя.
6. `approve_listing`/`reject_listing`: вызвать `log_action` (`before` — статус до, `after` — статус после, `reason` — причина отклонения). Подпись функций сохраняется, вызовы из 4.5 не ломаются.
7. Задача очистки по сроку и строка в `CELERY_BEAT_SCHEDULE`; при значении `0` задача ничего не удаляет.
8. `.env.example`, `PROGRESS.md`, пункт в LAUNCH_CHECKLIST. Прогон тестов `audit`, `users`, `reports`, `local_listings`, затем полный прогон один раз; build, tsc, Playwright из `frontend/`.

## Тесты
Django:
- `audit/tests.py`: `log_action` создаёт запись с `before`/`after`; запись в той же транзакции (при исключении после `log_action` внутри `atomic` строки нет); `save()` существующей записи и `delete()` бросают исключение; `purge_audit_log` при `AUDIT_LOG_RETENTION_DAYS=0` ничего не удаляет, при положительном значении удаляет только старые записи (через `freezegun`/подмену `created_at`); в `target_repr` и `reason` нет email (проверка на примере блокировки).
- `users/tests.py`: `block_user` создаёт `UserBlock`, ставит флаги, отзывает токены (`tokens_valid_after`), скрывает `active`/`pending` объявления, пишет `user.block`; пустая причина → `ValidationError`; блокировка staff и самоблокировка запрещены; повторная блокировка активно заблокированного не создаёт вторую активную строку (ограничение БД); `unblock_user` закрывает блокировку и пишет `user.unblock`, объявления остаются `hidden`; вход заблокированного → 401/403 с текстом без причины; data-миграция создаёт `UserBlock` для уже забаненных.
- `reports/tests.py`: экшены `hide_listing`, `ban_reported_user`, `dismiss_report` создают записи журнала с автором-действующим; без прав на жалобы действие недоступно.
- `local_listings/tests.py`: `approve_listing` и `reject_listing` пишут запись `listing.approve`/`listing.reject` с причиной; повторная модерация не затирает прежние записи.
- Права (23-D31-подобные): админ видит `AuditLog` в админке (200); пользователь группы «Модератори» с `is_staff=True` → 403 на `/admin/audit/auditlog/`; у журнала нет add/change/delete даже для суперпользователя; у публичного API журнала нет маршрутов (тест-аудит из 1.2 зелёный).
Playwright (`frontend/e2e/moderation-audit.spec.ts`, учётки из 0.4):
- Успех: админ в Django-админке блокирует пользователя через действие с причиной; в журнале появилась запись с автором и причиной; заблокированный пользователь на `/login` видит «Акаунт заблоковано. Зверніться до підтримки», причины в тексте нет.
- Ошибка/обход: действие блокировки без причины показывает «Причину блокування вказати обов'язково» и никого не блокирует; модератор (не admin) на `/admin/audit/auditlog/` получает 403; заблокированный пользователь со старым access-токеном получает 401 на `/api/v1/users/me/`.
