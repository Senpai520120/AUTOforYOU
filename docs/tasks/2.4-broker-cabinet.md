## Цель
- [ ] `GET /api/v1/broker/leads/`: список заявок для broker и admin. Фильтры `status`, `source`, `assigned_to=me`, поиск по имени и телефону, сортировка по дате, пагинация. Аноним → 401, buyer/dealer → 403.
- [ ] `GET /api/v1/broker/leads/<id>/`: карточка заявки с контактами (телефон, email если указан), способом связи (звонок / Telegram / Viber), **источником (Н-26: UTM source/medium/campaign/content, реферер, страница входа, страница заявки)**, `first_response_at`, снимком расчёта (входы, разбивка, итог, дата курса), лотом (если есть) и журналом статусов. В списке — колонка «Джерело» (utm source или «пряме»).
- [ ] `POST /api/v1/broker/leads/<id>/status/` `{status, note}`: смена статуса через `leads.services.change_status`. Недопустимый переход → 400 с понятным текстом. В журнале видно, кто и когда сменил.
- [ ] `POST /api/v1/broker/leads/<id>/take/`: «Взяти в роботу» — назначить себя (`assigned_to`), статус `new → in_progress`. Если заявку уже взял другой брокер → 409.
- [ ] Клиентская страница: `/broker/leads` (список, фильтр по статусу, счётчик новых) и `/broker/leads/[id]` (карточка, кнопки допустимых переходов, заметка, ссылки `tel:` и `https://t.me/<handle>`).
- [ ] Ссылка «Заявки» в шапке и пункт в `/me` видны только broker и admin (по данным из API, а не по самовыбранной роли: права определяет 1.2).
- [ ] buyer, открывший `/broker/leads` напрямую, видит «Доступ обмежено» и не получает данных (сервер отвечает 403).
- [ ] В типе `User` на фронте есть роль `broker`, подпись роли в `/me` учитывает её.
- [ ] Клиент видит смену статуса своей заявки в `/me/leads` (2.3). Статус отображается по-украински.
- [ ] Кнопка «Відкрити заявку» из Telegram-сообщения (2.2) ведёт на `/broker/leads/<id>`.
- [ ] Админка остаётся рабочим инструментом для admin (2.1). Если 1.2 даёт брокерам доступ в админку через группу, `LeadAdmin` уважает права модели (`view_lead`, `change_lead`).

## Тесты
Django (`leads/tests.py`), закрывают 23-D38 и 23-D39:
- `GET /api/v1/broker/leads/`: аноним → 401, buyer → 403, dealer (верифицированный) → 403, broker → 200, admin → 200.
- То же для detail, status и take (аноним 401, buyer 403).
- Фильтр `?status=new` отдаёт только новые. Поиск по телефону `0671234567` находит `+380671234567`.
- `POST status`: `new → in_progress` → 200, журнал содержит `changed_by=broker`. `new → delivered` → 400. Неизвестный статус → 400. Полная цепочка этапов (шаг 6) `in_progress → contract → car_bought → in_transit → customs → delivered` проходит поэтапно.
- **(Q10)** Пользователь с ролью `moderator` (и `is_staff`) на `broker/leads/` → 403; admin → 200.
- **(Н-26)** Detail отдаёт `utm`, `referrer`, `entry_page_url`, `page_url`, `first_response_at`; клиентский `leads/mine/` их не отдаёт.
- `take`: свободная заявка → 200, `assigned_to=broker`, статус `in_progress`. Заявка другого брокера → 409. Повторный take своим брокером → 200 (идемпотентно).
- Detail отдаёт `allowed_transitions`, совпадающие со словарём сервиса.
- Клиент после смены статуса видит новый статус в `GET /api/v1/leads/mine/`, но не видит заметок брокера и `assigned_to`.
- Число запросов к БД в списке не растёт с числом заявок (`assertNumQueries` на 1 и на 10 заявках).

Playwright (`frontend/e2e/broker.spec.ts`, 23-P24; `storageState` broker и buyer из 0.4):
- Успех: broker открывает `/broker/leads`, видит заявку из фикстуры, открывает карточку, нажимает «Взяти в роботу» → статус «У роботі», затем «Договір» → статус обновлён, в журнале две записи; видны источник заявки (UTM) и способ связи.
- Успех: клиент (buyer, автор заявки) в `/me/leads` видит новый статус.
- Обход: buyer в шапке не видит «Заявки». Прямой `/broker/leads` → «Доступ обмежено», запрос к API вернул 403.
- Обход: гость `/broker/leads` → `/login`.
- Ошибка: подменить ответ `page.route` на 400 при смене статуса → понятное сообщение, статус на экране не изменился (без оптимистичного обновления или с откатом).
- Мобильный проект (если есть в 0.4): `/broker/leads` на 375px без горизонтального скролла.
