# Задача 4.6: Сделки: гонки и правила переходов

## Контекст
Сделка C2C: продавец в кабинете жмёт «Продано» и выбирает покупателя из тех, кто писал по объявлению (`frontend/app/me/local-listings/page.tsx:72-90`, `GET /api/v1/deals/listing-buyers/<id>/`), затем `POST /api/v1/deals/` → `propose_deal` (`deals/services.py:22-61`). Покупатель подтверждает в `/me/deals` → `confirm_deal` (`deals/services.py:64-90`, ставит объявлению `sold`) или любая сторона отменяет → `cancel_deal` (`deals/services.py:93-113`). Статусы: proposed, confirmed, cancelled (`deals/models.py:8-10`). Шаг 7 сценария 3 (`docs/audit/20_SCENARIOS.md`).

Что сейчас в коде:
- **06-Q2 (важно):** `confirm_deal` без блокировки строк и без проверки «по объявлению уже есть подтверждённая сделка» (`deals/services.py:64-80`). Продавец может предложить сделку двум покупателям, оба подтвердят — две `confirmed`-сделки и два отзыва по одной машине. Прочие `proposed`-сделки по объявлению после подтверждения не отменяются.
- **06-Q3 (важно):** `propose_deal` не проверяет статус объявления (`deals/services.py:31-45`): можно предложить сделку по `sold`, `hidden`, `expired`, `pending`, `rejected` (после 4.3 — и `deleted`).
- **06-Q4 (важно):** после отмены повторно предложить сделку тому же покупателю нельзя: проверка существования включает `cancelled` (`deals/services.py:44`), и её дублирует безусловный `UniqueConstraint(listing, buyer)` (`deals/models.py:41-44`).
- Желательные того же места: 06-Q12 (повторная отмена уже отменённой сделки разрешена и шлёт уведомление повторно, `deals/services.py:98-102`), 06-Q8 (нечисловой `listing_id` в `POST /deals/` → `ValueError` → 500: `listing_id` не в сериализаторе, `deals/views.py:31-32`, `deals/serializers.py:39-40`), статус сделки в админке меняется произвольно (`deals/admin.py:14-20`, поле `status` редактируемое, машины состояний нет), фронт `/me/deals` показывает общий текст вместо ошибки сервера (`frontend/app/me/deals/page.tsx:53,63,76`).
- Email в текстах уведомлений и сериализаторах (06-S5) закрывает задача 1.9; тесты 401/403 на confirm/cancel/review (13-S3, 23-D10) — задача 1.11; логирование и `on_commit` уведомлений (06-Q5, 06-Q7) — задача 4.7. Здесь хелпер `_notify` не переписывается, только вызывается.

## Цель
- [ ] **06-Q2:** `confirm_deal` в транзакции блокирует строку объявления и сделки (`select_for_update` на `LocalListing` и `Deal`). Если у объявления уже есть `confirmed`-сделка или объявление не в допустимом статусе → 400 «Оголошення вже продано». Подтверждение переводит объявление в `sold` и в той же транзакции отменяет все прочие `proposed`-сделки по нему (статус `cancelled`, поле `cancel_reason = 'sold_to_other'`); их покупатели получают уведомление «Продавець уклав угоду з іншим покупцем».
- [ ] В БД — страховка: частичный `UniqueConstraint(fields=['listing'], condition=Q(status='confirmed'), name='unique_confirmed_deal_per_listing')`.
- [ ] **06-Q3:** предложить сделку можно только по объявлению в статусе `active` или `hidden` (продавец мог скрыть объявление, пока договаривается). Иначе → 400 «Угоду можна запропонувати лише за активним або прихованим оголошенням». `confirm_deal` повторно проверяет статус (объявление могли удалить или продать между предложением и подтверждением).
- [ ] **06-Q4:** уникальность — только среди неотменённых: `UniqueConstraint(fields=['listing', 'buyer'], condition=~Q(status='cancelled'), name='unique_active_deal_listing_buyer')` вместо безусловного. Проверка в `propose_deal` исключает `cancelled`. После отмены тому же покупателю можно предложить снова.
- [ ] Правила переходов в одном месте — `deals/services.py` (`ALLOWED_TRANSITIONS = {proposed: {confirmed, cancelled}}`): `confirmed` и `cancelled` финальные. Повторная отмена `cancelled` → 400 без уведомления (06-Q12).
- [ ] `ProposeDealSerializer` принимает `listing_id` (IntegerField): мусор → 400, несуществующий → 404 (06-Q8).
- [ ] В админке `status`, `listing`, `seller`, `buyer` сделки — только для чтения; отменить сделку админ может экшеном «Скасувати угоду», который вызывает сервис (с уведомлениями) и не трогает `confirmed`.
- [ ] Фронт `/me/deals` и модалка «Продано» показывают `detail` из ответа сервера; после отмены у покупателя статус «Скасовано», у продавца снова доступна кнопка «Продано».

## Шаги
1. Тесты-сначала (см. «Тесты»). Тест гонки — `TransactionTestCase` с двумя потоками; на sqlite `select_for_update` не блокирует, поэтому тест помечается `skipUnless(connection.vendor == 'postgresql')`, а на sqlite проверяется последовательный сценарий (второе подтверждение → 400) и ограничение БД.
2. Миграция. **Причина изменения схемы:** условные ограничения уникальности — одна подтверждённая сделка на объявление (06-Q2) и возможность повторного предложения после отмены (06-Q4); `cancel_reason` — различать отмену стороной и автоматическую при продаже другому. Перед созданием ограничения data-миграция проверяет дубли `confirmed` по объявлению: если есть — оставляет самую раннюю, остальные переводит в `cancelled` с `cancel_reason='duplicate_fix'` и пишет количество в вывод миграции.
3. Сервис: `ALLOWED_TRANSITIONS`, проверки статуса объявления, блокировки, автоотмена прочих `proposed`.
4. `ProposeDealSerializer` с `listing_id`; view на валидированных данных.
5. Админка: readonly-поля, экшен отмены.
6. Фронт: вывод ошибок сервера.
7. Регенерировать `docs/openapi.yaml` (против Postgres). Прогон `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test` (и отдельно тест гонки против Postgres в Docker), build, tsc, Playwright из `frontend/`.

## Тесты
Django (`deals/tests.py`, 23-D85):
- 06-Q2: две `proposed`-сделки по объявлению (покупатели A и B). A подтверждает → A `confirmed`, объявление `sold`, сделка B `cancelled` с `cancel_reason='sold_to_other'`, B получил уведомление. B подтверждает → 400.
- 06-Q2 (Postgres): два потока одновременно подтверждают разные сделки по одному объявлению → ровно одна `confirmed`, вторая 400/`cancelled`.
- 06-Q2: прямое создание второй `confirmed` по тому же объявлению → `IntegrityError`.
- 06-Q3: propose по `sold`, `pending`, `expired`, `rejected` (и `deleted` после 4.3) → 400; по `hidden` → 201. Объявление стало `sold` между propose и confirm (сделкой с другим покупателем) → confirm → 400.
- 06-Q4: propose → cancel → propose тому же покупателю → 201; propose при существующей `proposed` тому же покупателю → 400.
- 06-Q12: cancel уже `cancelled` → 400, уведомление не создано; cancel `confirmed` → 400.
- 06-Q8: `POST /deals/` с `listing_id='abc'` → 400; `listing_id=999999` → 404.
- Админка: POST формы изменения с другим `status` статус не меняет; экшен «Скасувати угоду» отменяет `proposed` и не трогает `confirmed`.

Playwright (`frontend/e2e/c2c-deals.spec.ts`, 23-P38; фикстура 0.4: диалог buyer↔seller по active-объявлению):
- Успех: продавец в `/me/local-listings` жмёт «Продано» → выбирает покупателя → покупатель в `/me/deals` подтверждает → статус «Підтверджено», объявление у продавца «Продано» → покупатель оставляет отзыв 5★ → на странице объявления/продавца рейтинг обновился (бейдж — если порог `SELLER_BADGE_THRESHOLD` в e2e-стеке равен 1).
- Ошибка/обход: покупатель отменяет предложение → у обоих «Скасовано», у продавца снова активна кнопка «Продано» и повторное предложение тому же покупателю проходит; посторонний пользователь через `request` делает `POST /deals/<id>/confirm/` → 403/404, статус сделки не изменился; повторное подтверждение уже подтверждённой сделки через `request` → 400 и текст ошибки виден в UI при повторе через интерфейс.
