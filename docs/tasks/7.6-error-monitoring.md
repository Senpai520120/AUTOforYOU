# Задача 7.6: Мониторинг ошибок

## Контекст
- **12-S13 (важно):** мониторинга ошибок нет. В `requirements.txt:1-25` нет `sentry-sdk` или аналога, в `core/settings.py` нет ни `SENTRY_DSN`, ни `LOGGING`, ни `ADMINS` (проверено grep, см. также `docs/audit/21_SECURITY.md`, строка 50 таблицы). Ошибки 500 backend, падения задач Celery (`celery_worker`, `celery_beat`) и бота видны только в `docker compose logs`, алертов нет. Бриф §4 этап 7: «мониторинг ошибок».

Связанные «желательные» находки, закрываются здесь же:
- 08-Q17: `frontend/app/error.tsx:11-13` и `frontend/app/global-error.tsx:11-13` только вызывают `console.error(error)`, отправки в мониторинг нет. В той же находке: `<a>` вместо `Link` (`app/error.tsx:29`) и `global-error.tsx` не импортирует `globals.css` (стили могут не примениться, не проверено) — исправить попутно, это те же файлы.
- 01-S14 (часть «нет Sentry/ADMINS»): фильтр ПДн в логах делает 7.2, здесь он переиспользуется для событий мониторинга.

Принцип брифа §2: внешний сервис — через адаптер. Пустой DSN → мониторинг выключен, сайт, Celery и бот работают как обычно и не падают. Невалидный DSN тоже не роняет старт.

Вариант по умолчанию (вопроса в `docs/QUESTIONS.md` нет): протокол Sentry через `sentry-sdk`. С ним работают и sentry.io (есть бесплатный план), и self-hosted GlitchTip (бесплатный, открытый, совместим с Sentry SDK). Выбор провайдера — одна переменная `SENTRY_DSN`. Для фронтенда `@sentry/nextjs` не добавляется: ошибки клиента отправляются на backend-эндпоинт и уходят в мониторинг через тот же адаптер. Так один DSN, нет нового npm-пакета, и DSN не попадает в клиентский JS.

## Цель
- [ ] Адаптер `core/monitoring.py`: `init_monitoring(component: str) -> bool` и `capture_message(msg, level, extra)`. При пустом `SENTRY_DSN` ничего не импортирует из `sentry_sdk` и возвращает `False`. При заданном вызывает `sentry_sdk.init` с интеграциями Django, Celery, logging и возвращает `True`. Исключение при инициализации (невалидный DSN) перехватывается, пишется предупреждение в лог, возвращается `False`.
- [ ] Параметры из `.env`: `SENTRY_DSN`, `SENTRY_ENVIRONMENT` (по умолчанию `production` при `DEBUG=false`, иначе `development`), `SENTRY_RELEASE` (по умолчанию `IMAGE_TAG` из 7.5, если есть), `SENTRY_TRACES_SAMPLE_RATE` (по умолчанию `0`, трассировка выключена).
- [ ] ПДн не уходят: `send_default_pii=False`; `before_send` и `before_breadcrumb` пропускают сообщения, значения исключений, URL, заголовки и `extra` через `core.logging_filters.scrub` из 7.2; удаляются `request.cookies`, `request.data`, заголовки `Authorization`, `Cookie`, `X-CSRFToken`, query-строка URL; `user` — только `id`, без email и IP.
- [ ] Инициализация во всех процессах: Django (`core/settings.py` или `core/wsgi.py`/`asgi.py` — место выбрать и описать), Celery (`core/celery.py`, сигнал `celeryd_init`/`worker_process_init`), бот (`telegram_bot/management/commands/run_bot.py`). Тег `component` = `web` / `celery` / `bot`.
- [ ] Ошибки логгеров уровня `ERROR` (`logger.exception`) и необработанные исключения view и задач Celery попадают в мониторинг. `WARNING` — только как breadcrumbs.
- [ ] Ошибки фронтенда (08-Q17): `app/error.tsx` и `app/global-error.tsx` отправляют через `navigator.sendBeacon` (или `fetch` с `keepalive`) на `POST /api/v1/monitoring/client-errors/` минимальный отчёт: `message` (до 500 символов), `digest`, `path` (без query), `component: 'frontend'`. Стек и данные пользователя не отправляются.
- [ ] Эндпоинт `POST /api/v1/monitoring/client-errors/`: `AllowAny`, без CSRF-зависимости от cookie-сессии (только принимает данные, ничего не меняет в БД), свой throttle `client_errors` из `.env` (по умолчанию `20/hour` на IP), лимит размера тела (4 КБ), валидация полей сериализатором. Ответ 204 всегда при валидных данных, в том числе когда мониторинг выключен (тогда событие не отправляется). Невалидные данные → 400. Текст проходит `scrub`.
- [ ] Серверные ошибки рендера Next (SSR) не теряются: в `frontend/instrumentation.ts` хук `onRequestError` отправляет такой же минимальный отчёт на внутренний адрес `INTERNAL_API_URL`. Если в Next 16 API хука отличается, выбрать поддерживаемый способ и описать.
- [ ] 08-Q17 попутно: `Link` вместо `<a>` в `app/error.tsx`, стили `global-error.tsx` применяются (импорт `globals.css` или inline-стили; проверить в браузере).
- [ ] Статус интеграции виден админу: если задача 3.1 сделала реестр статусов интеграций, «Мониторинг ошибок» регистрируется там («не настроено» при пустом DSN, «включено» иначе). Если 3.1 ещё не сделана, пункт переносится в отчёт.
- [ ] Management-команда `manage.py monitoring_test` отправляет тестовое событие и печатает, включён ли мониторинг. Владелец проверяет подключение одной командой.
- [ ] Алерты: в LAUNCH_CHECKLIST описано, как включить уведомления на email/Telegram в Sentry или GlitchTip и как настроить внешний uptime-монитор (бесплатный UptimeRobot или аналог) на `https://DOMAIN/healthz` из 7.3. Сервис `backup` со статусом `unhealthy` (7.4) описан как сигнал для проверки.

## Тесты
Django (`core/tests/test_monitoring.py`, `sentry_sdk.init` замокан, сети нет):
- `SENTRY_DSN=''` → `init_monitoring('web')` возвращает `False`, `sentry_sdk.init` не вызывался.
- `SENTRY_DSN='https://key@example.invalid/1'` → `init` вызван один раз с `send_default_pii=False`, `environment`, `traces_sample_rate=0.0`, в `integrations` есть Django и Celery.
- `sentry_sdk.init` бросает `BadDsn`/`Exception` → функция возвращает `False`, исключение наружу не выходит, в логе предупреждение без DSN.
- `before_send` на событии с email, телефоном, `Authorization`, cookie, `?token=abc` в URL и `user.email` → в результате нет ни одного из этих значений, `user` содержит только `id`.
- `POST /api/v1/monitoring/client-errors/` с валидным JSON → 204; при включённом мониторинге (мок) `capture_message` вызван с `component='frontend'` и `path` без query.
- Тот же запрос при выключенном мониторинге → 204, `capture_message` не отправляет событие.
- Невалидные данные (нет `message`, `message` длиннее лимита, тело > 4 КБ) → 400 (или 413 для тела), событие не отправлено.
- Превышение `client_errors` throttle → 429.
- `GET` на эндпоинт → 405.
- `call_command('monitoring_test')` при пустом DSN → вывод «мониторинг выключен», код 0; при заданном (мок) — событие отправлено.
- Задача Celery, бросающая исключение (eager, мок `capture_exception`/интеграции) → исключение зарегистрировано адаптером (или проверка, что Celery-интеграция подключена).

Playwright (`frontend/e2e/error-monitoring.spec.ts`):
- Успех: при ошибке рендера (перехват API ответа `page.route('**/api/v1/local/**', r => r.fulfill({status: 500}))` на странице, которая бросает ошибку в `error.tsx`, или специальная тестовая ситуация) показывается оформленная страница ошибки со ссылкой «На головну» (`Link`), и браузер отправил `POST /api/v1/monitoring/client-errors/` с ответом 204 (`page.waitForRequest`). В теле запроса нет query-строки текущего URL.
- Ошибка/обход: прямой `request.post` на эндпоинт с мусорным JSON → 400; 25 запросов подряд → получен 429.
