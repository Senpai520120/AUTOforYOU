# Задача 2.1: Модель и API заявки брокеру

## Контекст
Главный сценарий брифа (§1): «расчёт → заявка (имя, телефон, удобный способ связи, параметры расчёта) → брокер мгновенно получает → работает со статусами». Сейчас он обрывается на шаге 3 (`docs/audit/20_SCENARIOS.md`, сценарий 2).

- **02-Q1 (критично)**: заявки после расчёта нет. Нет модели, эндпоинта и статусов. `frontend/components/calculator/CalcBreakdown.tsx:51-53` заканчивается номером расчёта и `warning`. Поиск `Lead`/`Inquiry`/`contact_method` по проекту пуст (подтверждено: в `INSTALLED_APPS`, `core/settings.py:48-80`, приложения заявок нет).
- **09-Q1 (критично, бэкенд-часть)**: у фронта нет эндпоинта для отправки заявки. `frontend/api/pricing.ts:15-21` знает только `calculate` и `myCalculations`.
- `Calculation` (`pricing/models.py:209-231`) пишется и для анонима (`pricing/views.py:328-336`, `user=None`). В нём есть снимки `inputs_snapshot`, `rates_snapshot` и `breakdown`. Их нужно прикладывать к заявке.
- Смежно, 02-S5 (желательно): `Listing.calculation` принимает чужой `Calculation` (`listings/serializers.py:34-41`). В заявке такую ошибку не повторять.
- `on_commit` в проекте нигде не используется (grep по приложениям пуст). Уведомление брокера делает задача 2.2. Здесь только точка вызова в сервисе.
- Роль broker и права на неё появляются в задаче 1.2 (01-S7, 02-S6). Здесь нужна только модель прав: заявку видит её автор, broker и admin.
- Регистрация и выгрузка/удаление данных (задача 1.8) пока не знают о заявках. Заявка содержит ПДн (имя, телефон).

## Цель
- [ ] Новое приложение `leads` с моделью `Lead` (единственное число, по CLAUDE.md) и журналом `LeadStatusChange`.
- [ ] `POST /api/v1/leads/` принимает заявку от гостя и от вошедшего пользователя (Q4 по умолчанию: регистрация не нужна). Поля: имя, телефон, способ связи, необязательный ник или контакт для мессенджера, комментарий, согласие на обработку ПДн (обязательно), `calculation_id` и/или `listing_id` (две точки входа по Q4).
- [ ] Телефон нормализуется в E.164 (`+380XXXXXXXXX`). Неверный формат даёт 400 с ошибкой поля. Без согласия тоже 400.
- [ ] В заявке замораживается копия расчёта: входы, ставки, разбивка, итоги и валюты (`calculation_snapshot` JSON). Если потом удалить или почистить `Calculation` (задача 2.6 чистит анонимные расчёты), заявка не теряет параметры.
- [ ] Чужой `Calculation` приложить нельзя. Если у расчёта есть `user` и он не совпадает с `request.user`, ответ 400. Расчёт гостя (`user=None`) приложить можно.
- [ ] Защита от спама: отдельный throttle scope `lead` (ставка из `.env`, `THROTTLE_LEAD_RATE`), honeypot-поле (заполнено → 201 без создания записи, чтобы бот не понял, что его отсекли), ограничение длины полей.
- [ ] Ответ 201 содержит `id`, `status` и `created_at`. ПДн обратно не отдаются.
- [ ] `GET /api/v1/leads/mine/` отдаёт вошедшему пользователю только его заявки (статус, дата, краткие параметры). Аноним получает 401.
- [ ] Статусы: module-level `LeadStatus(TextChoices)`: `new`, `in_progress`, `contacted`, `won`, `lost`, `spam`. Допустимые переходы задаются словарём в `leads/services.py`. API смены статуса делает 2.4, но сервис `change_status()` и журнал появляются уже здесь.
- [ ] Вся бизнес-логика в `leads/services.py` (`create_lead`, `change_status`). Views и админка только вызывают сервис.
- [ ] `create_lead` вызывает хук уведомления через `transaction.on_commit`. В этой задаче это пустая функция `notify_new_lead(lead_id)`, реализацию пишет 2.2.
- [ ] Админка `LeadAdmin`: список (дата, имя, телефон, способ связи, источник, статус, итог расчёта), фильтры по статусу и источнику, поиск по имени и телефону. Снимок только для чтения. Смена статуса в админке идёт через `change_status` и пишет журнал (inline только для чтения).
- [ ] Заявки учтены в выгрузке и удалении данных пользователя из задачи 1.8: выгружаются, а при удалении аккаунта обезличиваются так же, как остальные ПДн (Q3).
- [ ] `openapi.yaml` перегенерирован против Postgres.

## Шаги
1. Создать приложение `leads`. Модели (миграция `0001_initial`, причина: новой сущности «заявка» в схеме нет):
   - `LeadStatus`, `LeadSource` (`calculator`, `listing`), `ContactMethod` (`phone`, `telegram`, `viber`, `whatsapp`) как `TextChoices` на уровне модуля (ловушка проекта).
   - `Lead`: `user` FK на `settings.AUTH_USER_MODEL` (null, `SET_NULL`), `name` (≤100), `phone` (E.164, ≤16), `contact_method`, `contact_handle` (≤64, blank), `comment` (≤1000, blank), `source`, `calculation` FK `pricing.Calculation` (null, `SET_NULL`), `listing` FK `listings.Listing` (null, `SET_NULL`), `calculation_snapshot` JSONField (default dict), `total_usd` и `total_uah` Decimal (null, копия итогов для списка), `status` (default `new`, индекс), `assigned_to` FK на пользователя (null, для 2.4), `consent_at` DateTime, `created_at`, `updated_at`. Индексы: `(status, -created_at)`.
   - `LeadStatusChange`: `lead` FK, `from_status`, `to_status`, `changed_by` FK (null), `note` (blank), `created_at`.
   - Соответствие `source` приложенному объекту (`calculator` → есть `calculation`, `listing` → есть `listing`) проверяет сериализатор, а не БД: после `SET_NULL` при удалении расчёта или лота заявка должна оставаться валидной.
   - `CheckConstraint` на `status in LeadStatus` (как у `Listing`, `listings/models.py:74-80`).
2. `leads/validators.py`: `normalize_ua_phone(value) -> str`. Принимает `+380XXXXXXXXX`, `380XXXXXXXXX`, `0XXXXXXXXX`, с пробелами, скобками и дефисами. Остальное даёт `ValidationError` с текстом на украинском. Задача 4.2 (10-Q1) может потом вынести валидатор в общее место.
3. `leads/services.py`:
   - `ALLOWED_TRANSITIONS: dict[str, set[str]]`: `new → {in_progress, lost, spam}`, `in_progress → {contacted, won, lost}`, `contacted → {in_progress, won, lost}`, финальные `won/lost/spam → {}` (переоткрытие только admin, флаг `force` в `change_status`).
   - `create_lead(*, user, data, calculation=None, listing=None) -> Lead`: внутри `transaction.atomic()`. Копирует `inputs_snapshot`, `rates_snapshot`, `breakdown`, `is_estimate`, `calculation_id`, `created_at` расчёта в `calculation_snapshot`, итоги в `total_usd/total_uah`. Ставит `consent_at=timezone.now()`, пишет первую запись журнала `'' → new`, затем `transaction.on_commit(lambda: notify_new_lead(lead.pk))`.
   - `notify_new_lead(lead_id)`: заглушка с логированием без ПДн (только `lead_id`), реализация в 2.2.
   - `change_status(lead, new_status, *, by, note='', force=False)`: проверяет переход (иначе `InvalidTransition`), сохраняет статус и пишет `LeadStatusChange`.
4. `leads/serializers.py`: `LeadCreateSerializer` (`consent` BooleanField, `must be True`; `website` как honeypot, write-only; `calculation_id`/`listing_id`; `validate_phone` через `normalize_ua_phone`; `validate`: для `source=calculator` обязателен `calculation_id`, для `source=listing` обязателен `listing_id` и лот должен быть доступен этому пользователю: retail для всех, wholesale только тем, кому его отдаёт `listings/permissions.py`; чужой расчёт → ошибка поля `calculation_id`). `LeadMineSerializer` без телефона и снимка ставок: `id`, `status`, `status_display`, `source`, `total_usd`, `total_uah`, `listing_id`, `created_at`.
5. `leads/views.py`: `LeadCreateView` (`AllowAny`, `ScopedRateThrottle`, `throttle_scope='lead'`; если honeypot заполнен, вернуть 201 с фиктивным телом без записи в БД и написать в лог без ПДн). `MyLeadsView` (`IsAuthenticated`, `filter(user=request.user)`, пагинация). Схемы `extend_schema` для openapi.
6. `core/settings.py`: `'lead': os.environ.get('THROTTLE_LEAD_RATE', '5/hour')` в `DEFAULT_THROTTLE_RATES`, `'leads'` в `INSTALLED_APPS`. В `.env.example` добавить переменную с комментарием.
7. `leads/admin.py`: `LeadAdmin` с `readonly_fields` для снимка, `consent_at`, `user`, `calculation`, итогов. `save_model` при смене `status` зовёт `change_status(..., by=request.user)`. `LeadStatusChangeInline` только для чтения. Удобный вывод снимка: итог и основные входы (марка, год, топливо, цена аукциона).
8. Выгрузка и удаление данных (из задачи 1.8): добавить заявки пользователя в экспорт. При удалении аккаунта `name` → «Видалений користувач», `phone`/`contact_handle`/`comment` очищаются, `user=None`, снимок расчёта остаётся (в нём нет ПДн).
9. Перегенерировать `openapi.yaml` только против Postgres (`DATABASE_URL=postgresql://... python manage.py spectacular --file openapi.yaml`), иначе CI-проверка упадёт.

## Тесты
Django (`leads/tests.py`, запуск вне Docker: `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test leads`), закрывают 23-D37 и часть 23-D38:
- Гость, валидные поля, `calculation_id` гостевого расчёта → 201. `Lead` создан, `calculation_snapshot` совпадает с `Calculation`, `status=new`, есть одна запись журнала.
- Вошедший пользователь со своим расчётом → 201, `lead.user == user`.
- Без `consent` или с `consent=false` → 400, ошибка на поле `consent`.
- Без телефона → 400. `phone='12345'` → 400. `phone='0671234567'` и `'+38 (067) 123-45-67'` → 201 и сохранено `+380671234567`.
- Чужой расчёт (`calculation.user` = другой пользователь) → 400 на `calculation_id`. Несуществующий `calculation_id` → 400.
- `source=listing` с retail-лотом → 201. С wholesale-лотом от обычного пользователя → 400/404 (нет утечки существования лота).
- Honeypot заполнен → 201, `Lead.objects.count() == 0`.
- Throttle: `patch.object(ScopedRateThrottle, 'allow_request', return_value=False)` → 429.
- Ответ 201 не содержит `phone` и `name`.
- `on_commit`: в `self.captureOnCommitCallbacks(execute=True)` вызывается `notify_new_lead` (мок) ровно один раз с `lead.pk`. Без выполнения коллбэков (откат) вызова нет.
- После удаления `Calculation` заявка сохраняет `calculation_snapshot` и итоги.
- `GET /api/v1/leads/mine/`: аноним → 401. Пользователь A видит только свои заявки, заявок B в ответе нет. В ответе нет `phone`.
- `change_status`: допустимый переход пишет журнал. Недопустимый (`new → won`) → `InvalidTransition`. `force=True` разрешает переоткрытие.
- Админка: смена статуса в `LeadAdmin` через `client.post` на change-форму создаёт `LeadStatusChange` с `changed_by=admin`.
- Выгрузка данных пользователя (1.8) содержит его заявки. Удаление аккаунта обезличивает заявку.

Playwright: API без UI в этой задаче. Сценарии формы — в 2.3 (23-P15). Здесь только Django-тесты.
