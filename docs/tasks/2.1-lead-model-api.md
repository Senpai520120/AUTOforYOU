# Задача 2.1: Модель и API заявки брокеру

## Контекст
Главный сценарий брифа (§1): «расчёт → заявка (имя, телефон, удобный способ связи, параметры расчёта) → брокер мгновенно получает → работает со статусами». Сейчас он обрывается на шаге 3 (`docs/audit/20_SCENARIOS.md`, сценарий 2).

- **02-Q1 (критично)**: заявки после расчёта нет. Нет модели, эндпоинта и статусов. `frontend/components/calculator/CalcBreakdown.tsx:51-53` заканчивается номером расчёта и `warning`. Поиск `Lead`/`Inquiry`/`contact_method` по проекту пуст (подтверждено: в `INSTALLED_APPS`, `core/settings.py:48-80`, приложения заявок нет).
- **09-Q1 (критично, бэкенд-часть)**: у фронта нет эндпоинта для отправки заявки. `frontend/api/pricing.ts:15-21` знает только `calculate` и `myCalculations`.
- `Calculation` (`pricing/models.py:209-231`) пишется и для анонима (`pricing/views.py:328-336`, `user=None`). В нём есть снимки `inputs_snapshot`, `rates_snapshot` и `breakdown`. Их нужно прикладывать к заявке.
- Смежно, 02-S5 (желательно): `Listing.calculation` принимает чужой `Calculation` (`listings/serializers.py:34-41`). В заявке такую ошибку не повторять.
- `on_commit` в проекте нигде не используется (grep по приложениям пуст). Уведомление брокера делает задача 2.2. Здесь только точка вызова в сервисе.
- Роль broker и права на неё появляются в задаче 1.2 (01-S7, 02-S6). Здесь нужна только модель прав: заявку видит её автор, broker и admin.
- Регистрация и выгрузка/удаление данных (задача 1.8) пока не знают о заявках. Заявка содержит ПДн (имя, телефон).

## Цель
- [ ] Новое приложение `leads` с моделью `Lead` (единственное число, по CLAUDE.md) и журналом `LeadStatusChange`.
- [ ] `POST /api/v1/leads/` принимает заявку от гостя и от вошедшего пользователя (Q4, решено: регистрация не нужна). Поля: имя, телефон (обязателен), способ связи (звонок / Telegram / Viber), необязательный ник или контакт для мессенджера, **необязательный email (шаг 6: на него уходит копия расчёта и статусы)**, комментарий, согласие на обработку ПДн (обязательно), `calculation_id` и/или `listing_id` (две точки входа по Q4: страница калькулятора и страница лота), **источник заявки (Н-26, шаг 6)**: `utm` (source, medium, campaign, content), `referrer`, `entry_page_url` (страница входа), `page_url` (страница заявки).
- [ ] **Антиспам (Q2):** honeypot всегда, плюс Turnstile через адаптер `integrations/captcha.py` из 1.6 (поле `captcha_token`; без ключа — только honeypot, форма работает). См. Н-33.
- [ ] Телефон нормализуется в E.164 (`+380XXXXXXXXX`). Неверный формат даёт 400 с ошибкой поля. Без согласия тоже 400.
- [ ] В заявке замораживается копия расчёта: входы, ставки, разбивка, итоги и валюты (`calculation_snapshot` JSON). Если потом удалить или почистить `Calculation` (задача 2.6 чистит анонимные расчёты), заявка не теряет параметры.

- [ ] `GET /api/v1/leads/mine/` отдаёт вошедшему пользователю только его заявки (статус, дата, краткие параметры). Аноним получает 401.

Статус `contacted`, `won`, `lost` из прежней версии убраны. Допустимые переходы задаются словарём в `leads/services.py`. API смены статуса делает 2.4, но сервис `change_status()` и журнал появляются уже здесь. Расширенная CRM (назначение, напоминания, контроль скорости ответа, связь с контейнером) — Н-27 (Рост).

- [ ] `create_lead` вызывает хук уведомления через `transaction.on_commit`. В этой задаче это пустая функция `notify_new_lead(lead_id)`, реализацию пишет 2.2.

## Шаги
1. Создать приложение `leads`. Модели (миграция `0001_initial`, причина: новой сущности «заявка» в схеме нет):
   - `LeadStatus`, `LeadSource` (`calculator`, `listing`), `ContactMethod` (`phone`, `telegram`, `viber`; WhatsApp убран по Q4) как `TextChoices` на уровне модуля (ловушка проекта).
   - `Lead`: `user` FK на `settings.AUTH_USER_MODEL` (null, `SET_NULL`), `name` (≤100), `phone` (E.164, ≤16), `email` (EmailField, blank), `contact_method`, `contact_handle` (≤64, blank), `comment` (≤1000, blank), `source`, `utm` (JSONField, whitelist ключей `source/medium/campaign/content`, длина значений ограничена), `referrer` (≤500, blank), `entry_page_url` и `page_url` (≤500, blank), `first_response_at` (DateTime, null), `calculation` FK `pricing.Calculation` (null, `SET_NULL`), `listing` FK `listings.Listing` (null, `SET_NULL`), `calculation_snapshot` JSONField (default dict), `total_usd` и `total_uah` Decimal (null, копия итогов для списка), `status` (default `new`, индекс), `assigned_to` FK на пользователя (null, для 2.4), `consent_at` DateTime, `created_at`, `updated_at`. Индексы: `(status, -created_at)`.
   - `LeadStatusChange`: `lead` FK, `from_status`, `to_status`, `changed_by` FK (null), `note` (blank), `created_at`.
   - Соответствие `source` приложенному объекту (`calculator` → есть `calculation`, `listing` → есть `listing`) проверяет сериализатор, а не БД: после `SET_NULL` при удалении расчёта или лота заявка должна оставаться валидной.
   - `CheckConstraint` на `status in LeadStatus` (как у `Listing`, `listings/models.py:74-80`).
2. `leads/validators.py`: `normalize_ua_phone(value) -> str`. Принимает `+380XXXXXXXXX`, `380XXXXXXXXX`, `0XXXXXXXXX`, с пробелами, скобками и дефисами. Остальное даёт `ValidationError` с текстом на украинском. Задача 4.2 (10-Q1) может потом вынести валидатор в общее место.
3. `leads/services.py`:
   - `ALLOWED_TRANSITIONS: dict[str, set[str]]`: по порядку этапов `new → {in_progress, rejected, spam}`, `in_progress → {contract, rejected}`, `contract → {car_bought, rejected}`, `car_bought → {in_transit, rejected}`, `in_transit → {customs}`, `customs → {delivered}`, финальные `delivered/rejected/spam → {}` (переоткрытие только admin, флаг `force` в `change_status`). Порядок — рабочий вариант, брокер может уточнить на приёмке; это словарь, а не схема БД.
   - `create_lead(*, user, data, calculation=None, listing=None) -> Lead`: внутри `transaction.atomic()`. Копирует `inputs_snapshot`, `rates_snapshot`, `breakdown`, `is_estimate`, `calculation_id`, `created_at` расчёта в `calculation_snapshot`, итоги в `total_usd/total_uah`. Ставит `consent_at=timezone.now()`, пишет первую запись журнала `'' → new`, затем `transaction.on_commit(lambda: notify_new_lead(lead.pk))`.
   - `notify_new_lead(lead_id)`: заглушка с логированием без ПДн (только `lead_id`), реализация в 2.2.
   - `change_status(lead, new_status, *, by, note='', force=False)`: проверяет переход (иначе `InvalidTransition`), сохраняет статус и пишет `LeadStatusChange`.
4. `leads/serializers.py`: `LeadCreateSerializer` (`consent` BooleanField, `must be True`; `website` как honeypot, write-only; `captcha_token` (Q2) проверяется `get_captcha_verifier()` из 1.6; `email` необязателен; `utm` фильтруется по whitelist ключей и обрезается по длине; `calculation_id`/`listing_id`; `validate_phone` через `normalize_ua_phone`; `validate`: для `source=calculator` обязателен `calculation_id`, для `source=listing` обязателен `listing_id` и лот должен быть доступен этому пользователю: retail для всех, wholesale только тем, кому его отдаёт `listings/permissions.py`; чужой расчёт → ошибка поля `calculation_id`). `LeadMineSerializer` без телефона и снимка ставок: `id`, `status`, `status_display`, `source`, `total_usd`, `total_uah`, `listing_id`, `created_at`.
5. `leads/views.py`: `LeadCreateView` (`AllowAny`, `ScopedRateThrottle`, `throttle_scope='lead'`; если honeypot заполнен, вернуть 201 с фиктивным телом без записи в БД и написать в лог без ПДн). `MyLeadsView` (`IsAuthenticated`, `filter(user=request.user)`, пагинация). Схемы `extend_schema` для openapi.
6. `core/settings.py`: `'lead': os.environ.get('THROTTLE_LEAD_RATE', '5/hour')` в `DEFAULT_THROTTLE_RATES`, `'leads'` в `INSTALLED_APPS`. В `.env.example` добавить переменную с комментарием.

Удобный вывод снимка: итог и основные входы (марка, год, топливо, цена аукциона).
8. Выгрузка и удаление данных (из задачи 1.8): добавить заявки пользователя в экспорт. При удалении аккаунта `name` → «Користувач видалений», `phone`/`contact_handle`/`comment` очищаются, `user=None`, снимок расчёта остаётся (в нём нет ПДн).

## Дополнено на шаге 13 (пункты эталона K3.3, O2.1, K4.6, M1.5; Н-26, Н-33)

Источник: `docs/audit/32_NEW_TASKS_INDEX.md` (Н-26 «в 2.1–2.4 уже внесено шагами 6 и 12», Н-33). Поля источника и `first_response_at` в «Цели» уже есть; здесь уточнены правила приёма и проверки, чтобы данные нельзя было испортить и заявка не падала из-за мусора в атрибуции.

### Цель (добавлено)
- [ ] **Атрибуция не блокирует заявку.** Поля источника (`utm`, `referrer`, `entry_page_url`, `page_url`) нормализуются тихо: ошибка в них никогда не даёт 400.
  - `utm`: только словарь; ключи из whitelist `source`, `medium`, `campaign`, `content` (`term` не принимается); значения строки, обрезка по длине (`utm_*` ≤100), пустые отбрасываются; не словарь, вложенные структуры, лишние ключи → отбрасываются, `utm = {}`.
  - `referrer`: только `http`/`https`; сохраняется схема, хост и путь без query и fragment (токены и поисковые запросы в ссылках не должны попадать в БД); другие схемы (`javascript:`, `data:`) → пусто; ≤500.
  - `entry_page_url` и `page_url`: принимается только путь сайта (начинается с `/`; если пришёл полный адрес — берётся путь), без query и fragment, ≤500; иное → пусто.
  - Значения хранятся как текст, экранируются на выводе (2.2: `html.escape`; админка: автоэкранирование Django).
- [ ] **`first_response_at` (K4.6, уточнение):** ставится один раз при первом переходе заявки из `new` в любой статус, кроме `spam` (пометка «спам» — не ответ клиенту); повторное открытие (`force`) значение не сбрасывает.
