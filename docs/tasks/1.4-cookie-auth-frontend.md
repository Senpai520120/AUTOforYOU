# Задача 1.4: Фронтенд на cookie-аутентификации

> Дубль (группа G1): серверный механизм cookie и CSRF делает задача 1.3 (владелец группы). Здесь только клиентская часть, механизм не переписывать.

## Контекст

Бэкенд из задачи 1.3 уже ставит httpOnly-cookie и проверяет CSRF, но пока ещё отдаёт токены в теле ответа (`AUTH_TOKENS_IN_BODY=True`). Фронт по-прежнему работает через `localStorage`.

**08-S1 (критично), 09-S1, 10-S2 (важно): access и refresh хранятся в `localStorage`.**
- `frontend/lib/auth-context.tsx:29-30,50,60-61,70-71,88-89,95` — чтение, запись и удаление токенов.
- `frontend/api/client.ts:4,13,22,27,35-36,71-73` — `Authorization: Bearer` из `localStorage`.
- Все вызовы пакетов пригона и C2C идут через `apiFetch` и `apiUpload`.

**08-Q1 (критично): сессию выкидывает через 15–30 минут.**
- `client.ts:3-15` не сохраняет ротированный refresh (`:13` пишет только access). Старый refresh уже в blacklist (`core/settings.py:350-351`), поэтому второй refresh гарантированно падает.
- Гонка: `Header.tsx:18-23` раз в 30 секунд опрашивает два эндпоинта параллельно. Оба получают 401 и оба шлют один и тот же refresh.
- В `auth-context.tsx:49-67` вторая, расходящаяся реализация refresh, которую никто не вызывает (08-Q3, желательно).

**08-S2 (важно): выход не отзывает refresh.** `auth-context.tsx:28-33` только чистит `localStorage`, эндпоинт `/api/v1/auth/token/logout/` не вызывается.

**08-Q2, 09-Q7 (важно): любой 401 редиректит на `/login`.** `client.ts:31-38` делает это при любом 401 после неудачного refresh. Гость или аноним с протухшим токеном теряет форму калькулятора. Бэкенд-часть (невалидная cookie = аноним) сделана в 1.3.

**11-S5 (важно): страница cookie юридически описывает токены в `localStorage`.** Строки сместились относительно аудита (там `:87-110`): сейчас это `frontend/app/cookies/page.tsx:22-27` (текст «не у файлах cookie, а в localStorage») и `:46-68` (таблица `access`/`refresh` → localStorage). Связанные тексты: `frontend/lib/consent.ts:4`, `frontend/components/ui/CookieBanner.tsx:30`, комментарии `frontend/app/listings/WholesaleHint.tsx:10`, `frontend/lib/server-api.ts:4-6`.

**SSR (бриф §3 «SSR Next.js продолжает работать»).**
- `frontend/lib/server-api.ts:32-40` — `serverGet` ходит в API анонимно, с `next: { revalidate }`. Белый список query — `:20-29`.
- `frontend/app/listings/[id]/page.tsx:8-23` — свой анонимный fetch с `revalidate: 300`.
- Поэтому сейчас B2B-лот по SSR отдаёт 404 (09-Q2, критично, задача 2.9): анониму сервер отдаёт только retail (`listings/views.py:76-77`).
- Задача 1.4 должна **сделать возможным** авторизованный SSR. Переводить на него страницу лота — работа задачи 2.9.

Связанное (желательно, то же место):
- 08-S7 — приватные страницы защищены только на клиенте (`app/me/page.tsx:11-15` и аналоги), нет возврата по `?next=`.
- 08-Q3 — мёртвые `refreshToken`/`tokens` в контексте.
- 08-Q16 — `Content-Type: application/json` на GET вызывает лишний preflight, `res.statusText` пуст на HTTP/2 (`client.ts:23-24,43`).

## Цель

- [ ] Во фронте нет ни одного обращения к `localStorage` с токенами: `grep -rn "localStorage" frontend/{api,lib,app,components}` находит только `cookie_consent` в `lib/consent.ts`.
- [ ] Удалены тип `Tokens` и поля `tokens` и `refreshToken` из `AuthCtx`, если они больше не нужны.
- [ ] Все клиентские запросы идут с `credentials: 'include'`, без заголовка `Authorization`.
- [ ] На небезопасных методах (POST/PUT/PATCH/DELETE, включая `apiUpload`) фронт отправляет `X-CSRFToken` из cookie `csrftoken`. Если cookie нет, сначала вызывается `GET /api/v1/auth/csrf/`.
- [ ] Refresh выполняется одним промисом на все параллельные запросы (single-flight): N одновременных 401 → ровно один `POST token/refresh/`.
  - После успешного refresh исходные запросы повторяются.
  - Если refresh вернул 401, запрос один раз повторяется (другая вкладка могла уже обновить cookie), и только после этого выполняется выход.
- [ ] 401 **не** редиректит на `/login` автоматически (08-Q2, 09-Q7). `apiFetch` бросает ошибку со `status: 401`, `AuthContext` сбрасывает `user`. Редирект делают только защищённые страницы (или общий хук `useRequireAuth()` с `?next=` на текущий путь).
- [ ] Протухший или мусорный токен не мешает гостю пользоваться калькулятором.
- [ ] `logout()` вызывает `POST /api/v1/auth/token/logout/` с CSRF. Сервер блэклистит refresh и удаляет cookie `access` и `refresh` (`Max-Age=0`), фронт сбрасывает состояние и переходит на главную (08-S2). Найдено ревью 1.3: без этого cookie живут после «Вийти» (refresh — 7 дней), а 15 минут любой POST без CSRF получает 403.
- [ ] Инициализация `AuthProvider`: при старте запрашивается `GET /auth/profile/` с cookie. 200 → `user`, 401 → гость. Без чтения хранилища.
- [ ] Бэкенд: `AUTH_TOKENS_IN_BODY=False` по умолчанию — токенов больше нет в теле ответов `token/` и `token/refresh/`.
- [ ] **Авторизованный SSR возможен.** В `lib/server-api.ts` есть `serverGetAuthed<T>(path)`:
  - читает `cookies()` из `next/headers` и передаёт в API **только** cookie `access` (заголовок `Cookie: access=...`);
  - запросы делаются с `cache: 'no-store'`, чтобы ответ одного пользователя не попал в кэш другого;
  - если токена нет или он протух, возвращает анонимный результат (`null`), а клиентская часть после refresh делает `router.refresh()`;
  - при сбое API не бросает исключение.

  Существующий `serverGet` остаётся анонимным и кэшируемым для публичных страниц и SEO. Какие страницы переходят на `serverGetAuthed`, решают задачи, которым это нужно: B2B-лот — 2.9 (09-Q2).
- [ ] Страницы, использующие `serverGetAuthed`, помечены `export const dynamic = 'force-dynamic'`.
- [ ] Тексты про хранение обновлены:
  - `/cookies`: таблица с `access` (httpOnly cookie, 15 минут, из `JWT_ACCESS_MINUTES`), `refresh` (httpOnly cookie, 7 дней), `csrftoken` (cookie, защита от CSRF) и `cookie_consent` (localStorage);
  - раздел 1 и `lib/consent.ts:4`, `CookieBanner.tsx:30`, комментарии `WholesaleHint.tsx` и `server-api.ts` переписаны (11-S5).

  Сроки на странице указаны словами «15 хвилин / 7 днів (налаштовується)» или берутся из API, но не расходятся с `.env`-дефолтами.

## Шаги

1. `lib/csrf.ts`: `getCsrfToken()` читает `document.cookie`. Если cookie нет, вызывает `GET /api/v1/auth/csrf/` с `credentials: 'include'` и читает её снова.
2. `api/client.ts`:
   - общий `request()` с `credentials: 'include'`;
   - `Content-Type` только при наличии тела (08-Q16);
   - `X-CSRFToken` на небезопасных методах;
   - `let refreshing: Promise<boolean> | null` — single-flight;
   - повтор запроса после refresh;
   - при 401 — `throw` с `status`, без `window.location`.

   `apiUpload` использует тот же путь. Поскольку всё выполняется в браузере, обращения к `window`/`document` защитить `typeof window`.
3. `auth-context.tsx`:
   - `useEffect` → `apiGet('/api/v1/auth/profile/')`, ловить 401 → гость;
   - `login()` → `POST token/` (401/400 → «Невірний email або пароль»; различение 429 и 5xx — задача 1.5), затем профиль;
   - `logout()` → `POST token/logout/`, сброс `user` даже при сетевой ошибке;
   - подписка на событие «сессия истекла» из `client.ts` (например, `window.dispatchEvent(new Event('auth:expired'))`) → `setUser(null)`.
4. `use-require-auth.ts`: если после загрузки `user == null`, `router.replace('/login?next=' + encodeURIComponent(pathname))`. На `/login` принимать `next` только вида `/^\/(?!\/)/` — защита от открытого редиректа. Заменить копии в `app/me/*`, `b2b`, `local/new`.
5. `server-api.ts`: добавить `serverGetAuthed` (`import { cookies } from 'next/headers'`, `cache: 'no-store'`, только cookie `access`, обработка ошибок как в `serverGet`).

   Ограничение, записать комментарием: refresh-cookie имеет `Path=/api/v1/auth/` и серверу Next не видна, поэтому SSR не обновляет протухший access. Страница рендерится анонимно, клиент обновляет сессию и вызывает `router.refresh()`.

   Для SSR через nginx (`INTERNAL_API_URL=http://backend:8000`) cookie передаются вручную в заголовке, домен cookie значения не имеет.
6. Бэкенд: `AUTH_TOKENS_IN_BODY=False`. Тест из 1.3 с `override_settings` превращается в тест по умолчанию.
7. Тексты `/cookies`, `consent.ts`, `CookieBanner` — на украинском, согласовано с фактическими cookie.
8. `npm run build`, `npx tsc --noEmit`. Проверить, что страницы с данными остаются `force-dynamic` (ловушка пререндера при build).
9. Полный прогон Playwright (все спеки, не выборочно), включая `auth-cookie-api.spec.ts` из 1.3 (в 1.3 живьём не запускалась) и существующие `ssr.spec.ts`, `catalog.spec.ts`, `negative.spec.ts`, `register.spec.ts`, `home.spec.ts`, `test-1.spec.ts` — все зелёные.
