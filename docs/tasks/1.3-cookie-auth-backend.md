# Задача 1.3: JWT в httpOnly-cookie + CSRF (бэкенд)

## Контекст

**01-S1 (критично): JWT отдаются в теле ответа и принимаются только из заголовка `Authorization`.**
- `users/urls.py:27-28` — стандартные `TokenObtainPairView` и `TokenRefreshView`: access и refresh приходят в JSON, фронт кладёт их в `localStorage` (это чинит задача 1.4).
- `core/settings.py:219-222` — `DEFAULT_AUTHENTICATION_CLASSES` = только `JWTAuthentication` (Bearer).
- `core/settings.py:347-353` — `SIMPLE_JWT`: access 15 мин, refresh 7 дней, `ROTATE_REFRESH_TOKENS` и `BLACKLIST_AFTER_ROTATION` включены. Сроки захардкожены (01-C9, желательно).

**08-S3 (важно): нет CSRF-инфраструктуры для cookie-аутентификации.**
- `CsrfViewMiddleware` подключён (`core/settings.py:88`), но при Bearer не работает.
- `CSRF_TRUSTED_ORIGINS` не задан (grep пуст).
- Нет эндпоинта, который выдаёт CSRF-cookie.
- На фронте нет заголовка `X-CSRFToken` (`frontend/api/client.ts:23-27`, задача 1.4).

**Связанное (желательно, то же место):**
- 01-S13: `LogoutView` (`users/views.py:25-37`) блэклистит любой переданный refresh, не проверяя владельца, и отдаёт клиенту `str(exc)` (`:36`). Требует `IsAuthenticated`, поэтому при протухшем access выйти нельзя.
- 01-C9: сроки токенов не вынесены в `.env`.
- 09-Q7 (закрывается в 1.4, бэкенд-часть здесь): невалидный токен сейчас даёт 401 даже на `AllowAny`-эндпоинтах. Из-за этого аноним с протухшим токеном теряет форму калькулятора.

**Как устроен трафик** (важно для SameSite):
- В Docker и на проде фронт и API на одном origin через nginx (`nginx/nginx.conf:30-52`).
- В dev фронт на `localhost:3000`, API на `localhost:8000`: это same-site, cookie ходят, `CORS_ALLOW_CREDENTIALS = True` уже есть (`core/settings.py:210`).
- SSR Next.js ходит в API напрямую (`INTERNAL_API_URL=http://backend:8000`, `docker-compose.yml:66`), сейчас анонимно (`frontend/lib/server-api.ts:32-40`).

## Цель

- [ ] `POST /api/v1/auth/token/` при успехе ставит два cookie:
  - `access`: `HttpOnly`, `Secure` (из `.env`), `SameSite=Lax`, `Path=/`, `Max-Age` = сроку access;
  - `refresh`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/v1/auth/`, `Max-Age` = сроку refresh.

  Имена, SameSite, Secure и домен читаются из настроек и `.env`.
- [ ] `POST /api/v1/auth/token/refresh/` берёт refresh из cookie (или из тела, для Bearer-клиентов), ротирует его и ставит новые cookie. Старый refresh попадает в blacklist, как сейчас.
- [ ] `POST /api/v1/auth/token/logout/`:
  - работает с протухшим access (`AllowAny`) — берёт refresh из cookie, блэклистит его и удаляет оба cookie;
  - если пользователь аутентифицирован, проверяет, что refresh принадлежит ему (01-S13);
  - при ошибке отдаёт нейтральный текст без `str(exc)`.
- [ ] Новый класс аутентификации `users/authentication.py::CookieJWTAuthentication`:
  - сначала читает заголовок `Authorization: Bearer`, потом cookie `access`;
  - при аутентификации **через cookie** на небезопасных методах (POST/PUT/PATCH/DELETE) выполняет CSRF-проверку, как DRF `SessionAuthentication.enforce_csrf`. Без валидного `X-CSRFToken` ответ 403;
  - Bearer-запросы CSRF не требуют: браузер не добавляет их сам;
  - невалидный или протухший токен **из cookie** даёт анонима (`return None`), а не 401. `AllowAny`-эндпоинты работают, защищённые отвечают 401, потому что `authenticate_header` возвращает `Bearer`.
- [ ] `GET /api/v1/auth/csrf/` (`ensure_csrf_cookie`) ставит cookie `csrftoken`. Она не `HttpOnly`, чтобы фронт мог прочитать её и отправить в заголовке.
- [ ] `CSRF_TRUSTED_ORIGINS` читается из `.env`. В dev по умолчанию `http://localhost:3000,http://127.0.0.1:3000`, в Docker `http://localhost`.
- [ ] Срок жизни токенов берётся из `.env`: `JWT_ACCESS_MINUTES` (15), `JWT_REFRESH_DAYS` (7) (01-C9).
- [ ] **Переходный режим, чтобы всё продолжало работать.** Пока фронт не переведён (задача 1.4), токены **ещё** отдаются и в теле ответа. Это управляется настройкой `AUTH_TOKENS_IN_BODY` (в settings, по умолчанию `True`, с комментарием «выключается в задаче 1.4»). Bearer-аутентификация остаётся рабочей: её используют Django-тесты (`users/tests.py`, `tests/test_e2e.py`, `deals/tests.py` и др.) и сторонние API-клиенты.
- [ ] SSR готов к авторизованным запросам: GET с cookie `access` (переданным сервером Next в заголовке `Cookie`) аутентифицирует пользователя без CSRF. Это основа для 1.4 и для 09-Q2 (B2B-лот, задача 2.9).
- [ ] Эндпоинты, которые не должны аутентифицироваться по cookie, не ломаются: LiqPay callback (`payments/views.py:133-135`, `authentication_classes = []`), Telegram webhook (Django `View`, `csrf_exempt`, `telegram_bot/views.py:63-64`).
- [ ] Swagger и OpenAPI описывают cookie-аутентификацию (`OpenApiAuthenticationExtension` для нового класса), `openapi.yaml` перегенерирован.

## Шаги

1. Настройки. Читать из `.env` и описать в `.env.example`:
   - `AUTH_COOKIE_ACCESS_NAME=access`, `AUTH_COOKIE_REFRESH_NAME=refresh`;
   - `AUTH_COOKIE_SECURE` (по умолчанию `not DEBUG`);
   - `AUTH_COOKIE_SAMESITE=Lax`;
   - `AUTH_COOKIE_DOMAIN` (пусто = host-only);
   - `JWT_ACCESS_MINUTES`, `JWT_REFRESH_DAYS`;
   - `CSRF_TRUSTED_ORIGINS`.

   Не хардкодить домены.
2. `users/cookies.py`. Refresh-cookie ставится с `path='/api/v1/auth/'`, чтобы браузер отправлял его только на эндпоинты auth (refresh и logout). Учесть: из-за этого `proxy.ts` Next не увидит refresh — это ограничение для 1.4, записано там.
3. `CookieJWTAuthentication(JWTAuthentication)`:
   ```
   header → super().authenticate()                              # Bearer, как раньше
   иначе raw = request.COOKIES.get(ACCESS_NAME)
         → validated = get_validated_token(raw); при InvalidToken → return None
         → enforce_csrf(request) для небезопасных методов (CSRFCheck, как в SessionAuthentication)
   ```
   Проверить, что `is_active` и `is_banned` учитываются так же, как в базовом классе.
4. Views:
   - `CookieTokenObtainView(TokenObtainPairView)` — в `post()` после `serializer.is_valid()` вызвать `set_auth_cookies`. Тело: `{'ok': True}` плюс токены, если `AUTH_TOKENS_IN_BODY`.
   - `CookieTokenRefreshView` — refresh из cookie или из тела, ротация через `TokenRefreshSerializer`, новые cookie. Ошибка → 401 с `clear_auth_cookies`.
   - `LogoutView` — `AllowAny`. Refresh из cookie или из тела. Если `request.user.is_authenticated` и `token['user_id'] != request.user.pk` → 400 без blacklist. `TokenError` → нейтральное `{'detail': 'Сесію вже завершено.'}`, cookie удаляются в любом случае.
   - `CsrfView` — `@method_decorator(ensure_csrf_cookie)`, `AllowAny`, отдаёт 204.
5. CSRF на refresh и logout: запросы аутентифицируются cookie-refresh, поэтому явно вызывать CSRF-проверку, если refresh пришёл из cookie. На `token/` (логин) CSRF не требовать: пользователя ещё нет. Против login-CSRF хватает SameSite=Lax. Решение записать комментарием.
6. `DEFAULT_AUTHENTICATION_CLASSES = ('users.authentication.CookieJWTAuthentication',)`. Пройти по views с `authentication_classes` (grep) — убедиться, что ничего не переопределено несовместимо.
7. Поведение 09-Q7: невалидная cookie → аноним. Для Bearer оставить поведение SimpleJWT (401): это явный API-клиент.
8. OpenAPI: extension для `CookieJWTAuthentication` (cookie и bearer), описание в `SPECTACULAR_SETTINGS.DESCRIPTION` (`core/settings.py:276-281`) обновить. `openapi.yaml` генерировать только против Postgres.
9. Прогнать все тесты: Bearer-тесты должны остаться зелёными без правок.

## Тесты

Django (`users/tests.py`, `APIClient` с `enforce_csrf_checks=True` там, где проверяется CSRF):
- 23-D20 (часть 1):
  - `POST token/` → 200. В `Set-Cookie` есть `access` и `refresh` с флагами `HttpOnly`, `SameSite=Lax`, у refresh `Path=/api/v1/auth/`.
  - При `override_settings(AUTH_COOKIE_SECURE=True)` стоит `Secure`.
  - Проверка «токенов нет в теле» появляется в 1.4, когда `AUTH_TOKENS_IN_BODY=False`. Здесь — тест с `override_settings(AUTH_TOKENS_IN_BODY=False)`: тело без `access` и `refresh`.
- `test_cookie_auth_get_profile` — GET `/auth/profile/` только с cookie `access` → 200.
- `test_cookie_auth_post_without_csrf_forbidden` — POST на защищённый эндпоинт (например, `/auth/me/trusted-shops/`) с cookie без `X-CSRFToken` → 403. С токеном из `GET /auth/csrf/` → 201.
- `test_bearer_post_without_csrf_ok` — Bearer + POST без CSRF → 201 (регрессия).
- `test_expired_cookie_on_allowany_is_anonymous` — просроченная или мусорная cookie `access` + `POST /pricing/calculate/` → 200 (09-Q7). На `/auth/profile/` → 401, заголовок `WWW-Authenticate` присутствует.
- 23-D21:
  - refresh из cookie → новые cookie;
  - повторный запрос со **старым** refresh → 401;
  - refresh без CSRF-заголовка при cookie-refresh → 403.
- Logout (01-S13):
  - с протухшим access, но валидной refresh-cookie → 200, refresh в blacklist, `Set-Cookie` с `Max-Age=0` для обоих cookie;
  - чужой refresh в теле при аутентифицированном пользователе → 400, чужой токен **не** в blacklist;
  - мусорный refresh → 400/200 с нейтральным текстом, в ответе нет текста исключения SimpleJWT.
- `test_jwt_lifetimes_from_env` — `override_settings` или проверка чтения `JWT_ACCESS_MINUTES`.
- Регрессия:
  - LiqPay callback без cookie и CSRF → прежний код;
  - Telegram webhook → прежний код (существующие тесты `telegram_bot/tests.py` зелёные; для тестов с aiogram `Update` — `addCleanup(Update.event_type.fget.cache_clear)`).
- Запуск вне Docker: `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test users`.

Playwright: фронт в этой задаче не меняется. Бэкенд-поведение проверяется через `request` API Playwright (`frontend/e2e/auth-cookie-api.spec.ts`, запуск только из `frontend/`):

- обход — `request.post` на защищённый эндпоинт с этой cookie без `X-CSRFToken` → 403 (часть 23-P8).
