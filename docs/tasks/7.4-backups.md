## Цель
- [ ] В compose есть сервис `backup` на образе `postgres:<та же версия, что db>-alpine` (собственный маленький Dockerfile `docker/backup/Dockerfile` с `aws-cli` и `gnupg`), который по расписанию делает `pg_dump -Fc` базы в директорию бэкапов.
- [ ] Время запуска задаётся `BACKUP_TIME` (по умолчанию `03:30`, часовой пояс `Europe/Kyiv`). Директория на хосте — `BACKUP_DIR` (по умолчанию `./backups`, уже в `.gitignore`). Права файлов 600, директории 700.
- [ ] Имя файла: `autoforyou_YYYY-MM-DD_HHMM.dump`. Рядом — контрольная сумма `.sha256`.
- [ ] Ротация: хранится `BACKUP_KEEP_DAILY` ежедневных (по умолчанию 7), `BACKUP_KEEP_WEEKLY` воскресных (4) и `BACKUP_KEEP_MONTHLY` за первое число месяца (3). Старые удаляются только после успешного создания нового.
- [ ] Медиа: если S3 не включён (`S3_BUCKET_NAME` пуст), вместе с дампом делается архив volume `media` (`tar.gz`) с той же ротацией. При S3 медиа не архивируются, в логе сказано почему.
- [ ] Копия вне сервера включается, если заданы `BACKUP_S3_BUCKET` и ключи (`BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_S3_ENDPOINT_URL` для R2/B2/Hetzner/любого S3-совместимого). Перед отправкой файл шифруется `gpg --symmetric --cipher-algo AES256` паролем `BACKUP_ENCRYPTION_PASSPHRASE`. Если bucket задан, а пароля нет, отправка не выполняется и в логе ошибка (незашифрованные ПДн наружу не уходят). Ротация в удалённом хранилище такая же.
- [ ] Ручной бэкап: `./scripts/backup.sh --now` (с хоста, через `docker compose run --rm backup ...` или `exec`). Код возврата 0 только при успешном дампе и проверке `pg_restore --list`.
- [ ] Восстановление: `./scripts/restore.sh <файл.dump|файл.dump.gpg> [--media <архив>]`. Скрипт спрашивает подтверждение (или флаг `--yes`), останавливает `backend`, `celery_worker`, `celery_beat`, `bot`, делает страховочный дамп текущей базы, восстанавливает через `pg_restore --clean --if-exists --no-owner`, запускает сервисы и проверяет `/healthz` (если 7.3 сделана) или `manage.py check`.
- [ ] Проверка восстановления: `./scripts/backup-verify.sh` восстанавливает последний дамп во временный контейнер Postgres (не в рабочую базу), выполняет `manage.py migrate --check` (или `showmigrations` без непримененных) и считает строки в ключевых таблицах (`users_customuser`, `local_listings_*`, `pricing_*`), затем удаляет временный контейнер. Запуск описан как ежемесячная процедура для владельца.
- [ ] У сервиса `backup` есть healthcheck: `unhealthy`, если последний успешный бэкап старше 26 часов (файл-метка времени). Это видно в `docker compose ps` и может использоваться мониторингом (7.6).
- [ ] Ошибка любого шага (дамп, шифрование, отправка) пишется в лог контейнера с понятным текстом, без пароля и ключей. Скрипт не оставляет частично записанные файлы (запись во временный файл и `mv`).
- [ ] Все новые `*.sh` в LF, проходят `shellcheck`.

## Шаги
1. Проверить, что сделала 7.3 (закреплённая версия Postgres, `/healthz`, `logging`). Образ `backup` должен иметь ту же мажорную версию `pg_dump`, что и сервер.
2. `docker/backup/Dockerfile` и скрипты. Подключение к БД через `PGHOST=db`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` из `POSTGRES_*` в `.env` (без разбора `DATABASE_URL` вручную).
3. `backup.sh`: `pg_dump -Fc -Z 6 > tmp && pg_restore --list tmp > /dev/null && mv tmp final`, sha256, архив медиа (если нет S3), шифрование и отправка (если настроено), ротация, метка времени успеха.
4. `rotate.sh`: по дате в имени файла оставить N последних ежедневных, N воскресных и N первых чисел месяца. Удалённая ротация через `aws s3 ls`/`aws s3 rm` с `--endpoint-url`.
5. `loop.sh`: вычислить секунды до следующего `BACKUP_TIME` с учётом `TZ`, `sleep`, запустить `backup.sh`, повторить. Флаг `BACKUP_ON_START=true` делает бэкап сразу при старте (удобно для проверки).
6. `restore.sh` и `backup-verify.sh`. `backup-verify.sh` поднимает `docker run --rm -d postgres:<версия>` во временной сети, восстанавливает и запускает `docker compose run --rm -e DATABASE_URL=... backend python manage.py migrate --check`.
7. CI: в e2e-джобе после поднятия стека (или отдельной джобой) создать пользователя через `manage.py shell -c` или API регистрации, выполнить `scripts/backup.sh --now`, удалить пользователя, выполнить `scripts/restore.sh <файл> --yes`, проверить, что пользователь снова есть. Плюс `scripts/backup-verify.sh`. Плюс `shellcheck` новых скриптов и `scripts/tests/test_backup_rotation.sh`.
8. Проверить вручную на Windows (Docker Desktop): `scripts/*.sh` запускаются из Git Bash, пути `BACKUP_DIR` работают.
9. `DEPLOY_NOTES.md` (только разделы бэкапа), `docs/LAUNCH_CHECKLIST.md`, `ROADMAP.md`, `PROGRESS.md`.

## Для владельца (LAUNCH_CHECKLIST)
- `.env`: `BACKUP_TIME`, `BACKUP_DIR`, `BACKUP_KEEP_DAILY`, `BACKUP_KEEP_WEEKLY`, `BACKUP_KEEP_MONTHLY`.
- `.env` (копия вне сервера, настоятельно рекомендуется): `BACKUP_S3_BUCKET`, `BACKUP_S3_ENDPOINT_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_ENCRYPTION_PASSPHRASE`. Где взять: любой S3-совместимый сервис (Cloudflare R2, Backblaze B2, Hetzner Storage Box/Object Storage, AWS S3), отдельный bucket и ключ только на запись в него.
- Срок хранения копий вне сервера согласовать с политикой конфиденциальности (вопрос юристу и бухгалтеру в LAUNCH_CHECKLIST, ANSWERS шаг 7).
- Пароль шифрования хранить **вне сервера** (менеджер паролей). Без него бэкап из облака не восстановить.
- Проверка после запуска: `./scripts/backup.sh --now` → файл в `BACKUP_DIR` и в bucket; `docker compose ps backup` → `healthy`.
- Раз в месяц: `./scripts/backup-verify.sh` и запись результата.
