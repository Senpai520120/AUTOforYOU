# Задача 0.4: Инфраструктура e2e: авторизация, фикстуры, мобильный проект

## Контекст
- **13-Q18 (важно).** `frontend/playwright.config.ts:10-46` описывает один проект `chromium` (Desktop Chrome, `:34-39`). В нём нет `globalSetup`/setup-проекта, `storageState` и `webServer`. Поэтому нет ни одного авторизованного e2e, мобильного проекта, Firefox и WebKit. `workers: 1`, `retries` только в CI (`:13-15`).
- Токены сейчас лежат в `localStorage` под ключами `access`/`refresh` (`frontend/lib/auth-context.tsx:60-61,88-89`). `storageState` их сохраняет при совпадении origin с `baseURL`. После перехода на cookie (задача 1.4, 01-S1) сохраняться будут cookie, код setup при этом не меняется.
- Вход — `POST /api/v1/auth/token/` (`users/urls.py:27`).
- Модерационного API нет: модерация идёт через админку, в `local_listings/urls.py` нет approve. Значит, активные объявления для e2e создаются фикстурой на бэкенде.
- Management-команды живут в приложениях `integrations`, `local_listings`, `pricing`, `telegram_bot`. У `users` каталога `management/` нет. `core` не входит в `INSTALLED_APPS` (`core/settings.py:48-80`), поэтому команду туда положить нельзя.

Связанные желательные находки:
- **13-S10.** E2E регистрирует реальных пользователей в БД стека и не чистит их (`frontend/e2e/negative.spec.ts:16,49-61`, `register.spec.ts:25`). С `E2E_BASE_URL` на проде это мусорные аккаунты в боевой БД (`playwright.config.ts:21` — любой URL).
- **13-C4.** E2E зависят от данных стека: seed тарифов делает `docker/entrypoint.sh` (`run_seed seed_rates`, `seed_auction_fees`). Фикстур нет.
- **13-C5.** `baseURL` по умолчанию `http://localhost`, `webServer` нет. В CI готовность ждёт шаг `curl` (`.github/workflows/ci-cd.yml`, «Wait for the site»), локально — никто.

CI сейчас: `docker compose up -d --build`, затем `npx playwright install --with-deps chromium` и `npx playwright test` из `frontend/` (`ci-cd.yml`, джоба `e2e`).

## Шаги
**Сессия 1 — бэкенд и CI.**
1. `e2e_seed`:
   - проверки `E2E_SEED_ALLOWED` и `E2E_PASSWORD` через `os.environ`, чтобы не заводить продовую настройку;
   - создание через `get_or_create` по email и заголовку `[E2E] …`;
   - фото из `frontend/e2e/fixtures/` (путь относительно `settings.BASE_DIR`);
   - вывод — сводка «создано/уже было».
2. `e2e_cleanup`: удаление в транзакции. Порядок — чтобы не упереться в `PROTECT`; при необходимости сначала удалить зависимые записи. Команда печатает, что удалено.
3. Django-тесты на обе команды (см. «Тесты»).
4. CI: переменные e2e в генерации `.env`, шаги seed и cleanup, установка трёх браузеров.

**Сессия 2 — Playwright.**
5. `playwright.config.ts`: проекты, `locale`/`timezoneId`, проверка `E2E_BASE_URL` по белому списку в начале файла (`throw new Error('E2E_BASE_URL … не в белом списке; для smoke задайте E2E_ALLOW_REMOTE=1')`).
6. `auth.setup.ts`: ожидание стека, затем вход для buyer, seller, dealer, staff через `request.post('/api/v1/auth/token/')`. Токены записать в `localStorage` через `page.addInitScript` / `page.evaluate` на `baseURL`, затем `page.context().storageState({ path })`. Пароль — `process.env.E2E_PASSWORD`, при отсутствии понятная ошибка.
7. `fixtures.ts`, `auth-smoke.spec.ts`, теги `@smoke`/`@mobile`, `.gitignore`.
8. Прогон:
   - локально: `docker compose -p autoforyou-e2e up -d --build`, `e2e_seed`, затем из `frontend/` `npx playwright test`;
   - убедиться, что проекты не дублируют тесты (`--list`).
9. Документация в `docs/TEST_CASES.md` и `README.md`.

## Тесты
Django (`users`):
- `e2e_seed` без `E2E_SEED_ALLOWED` → `CommandError`, в БД ничего не создано;
- `e2e_seed` без `E2E_PASSWORD` → `CommandError`;
- `e2e_seed` дважды → одинаковое число пользователей, объявлений и лотов (идемпотентность); у всех созданных пользователей email на `@e2e.test`; пароль совпадает с `E2E_PASSWORD` (`check_password`); dealer верифицирован, staff имеет `is_staff`;
- `e2e_cleanup` удаляет только `@e2e.test` и `[E2E]`: пользователь `real@example.com` и его объявление остаются;
- переменные задаются через `mock.patch.dict(os.environ, …)`, сеть не нужна.

Playwright:
- успех — setup-проект создаёт 4 файла `storageState`; `auth-smoke.spec.ts`: buyer видит `/me` со своим email; `@smoke`-спеки проходят в `firefox`; `@mobile`-заглушка проходит в `mobile-chrome` и `mobile-safari`;
- ошибка/обход:
  - при неверном `E2E_PASSWORD` setup падает с понятным сообщением (проверить вручную, описать в `TEST_CASES.md`);
  - `E2E_BASE_URL=https://example.com npx playwright test --list` падает с ошибкой белого списка;
  - гость без `storageState` на `/me` в `auth-smoke.spec.ts` уходит на `/login`.
