# Задача 5.1: Надёжный webhook: экранирование, дубли, коды ответа, прод-режим

## Контекст
Бот работает в двух режимах: polling (`run_bot`, сервис `bot` в compose) и webhook (`TelegramWebhookView`). Оба сейчас ненадёжны.

- **07-S3 (важно):** `make` и `model` подставляются в HTML-сообщения без `html.escape`. В `/latest` заголовок собирается в `telegram_bot/handlers.py:75` (`f'{v.make} {v.model} {v.year}'`) и отправляется с `parse_mode='HTML'` в `handlers.py:95-100`. В посте канала то же в `telegram_bot/tasks.py:58-63`. Символы `<` или `&` в данных импорта ломают отправку: в `/latest` исключение доходит до webhook и даёт 500. Можно подменить разметку и ссылки в посте.
- **07-Q1 (важно):** при привязке `user.telegram_id = telegram_id; user.save(...)` (`handlers.py:121-123`) не учитывает, что `CustomUser.telegram_id` уникален (`users/models.py:37`). Если этот Telegram уже привязан к другому аккаунту, падает `IntegrityError`. Он не перехвачен, webhook (`telegram_bot/views.py:99`, строка `async_to_sync(self._process_update)(token, data)`) отдаёт 500, Telegram повторяет апдейт, пользователь не получает ответа.
- **07-Q6 (важно):** апдейт обрабатывается синхронно внутри HTTP-запроса (`views.py:97-100`). Дедупликации по `update_id` нет. Любое исключение хендлера (07-Q1, 07-S3) даёт 500, и Telegram шлёт тот же апдейт снова, пока не истечёт очередь.
- **20-G4 (важно):** прод-режим противоречив. Сервис `bot` (`docker-compose.yml:70-82`) всегда запускает `docker/bot_entrypoint.sh`, который делает `exec python manage.py run_bot` (строка 8), то есть polling. `run_bot` при каждом старте вызывает `bot.delete_webhook(drop_pending_updates=True)` (`telegram_bot/management/commands/run_bot.py:45`). Webhook, установленный через `set_webhook`, снимается любым рестартом контейнера `bot`, а накопившиеся апдейты теряются. Переключателя режима нет.
  - Уточнение к аудиту: в `20_SCENARIOS.md` написано `restart: unless-stopped`, в коде `restart: on-failure` (`docker-compose.yml:82`). Суть не меняется: контейнер перезапускается после падения и при каждом `docker compose up`, и каждый старт снимает webhook.
  - Для webhook Telegram нужен HTTPS. Его сейчас нет (12-S2, задача 7.1). Эта задача делает переключатель и корректное поведение обоих режимов, а включение webhook на проде — после 7.1.

Связанные «желательные» находки в тех же местах, закрываются здесь же:
- 07-S4: проверка токена привязки и пометка `used` без транзакции и блокировки (`handlers.py:112-125`), два параллельных `/start link_<uuid>` могут оба пройти.
- 07-S8: секрет webhook сравнивается через `!=` (`views.py:87-88`, в текущем файле строка 88 `if incoming != secret`), а не за постоянное время.
- 07-Q9: `drop_pending_updates=True` в `run_bot.py:45` молча выбрасывает сообщения, пришедшие, пока бот лежал (в том числе deep-link привязки).
- 23-D4: очистка кэша `Update.event_type` есть только в `BotRuntimeTestCase.setUp` (`telegram_bot/tests.py:109-114`). Новые тесты этой задачи разбирают `Update` и в других классах.

Вне задачи: `set_webhook` без секрета и дубль `--delete` (07-C4, 07-Q12) — задача 5.4. Тексты сообщений в админке (07-C2) — 5.4. Адаптер Telegram real/demo (07-C3) — 3.4. HTTPS — 7.1.

## Цель
- [ ] Все значения из БД и от пользователя (`make`, `model`, цена, валюта, статус) экранируются `html.escape` перед вставкой в HTML-сообщения: в `/latest` и в посте канала (`tasks.py`). Для этого есть одна общая функция форматирования, а не экранирование по месту.
- [ ] `/latest` с `make = '<b>Tesla & Co'` отвечает сообщением, в котором текст виден буквально, и не падает.
- [ ] Привязка Telegram, уже привязанного к другому аккаунту, не падает. Пользователь получает понятный ответ «этот Telegram уже привязан к другому аккаунту, сначала отвяжите его там». Токен при этом не помечается использованным, аккаунт не меняется. Если Telegram уже привязан к этому же аккаунту — ответ «уже привязано», без ошибки.
- [ ] Проверка и погашение токена выполняются атомарно (`transaction.atomic()` + `select_for_update()` или условный `update(used=True)` с `filter(used=False)`). Из двух одновременных апдейтов с одним токеном проходит ровно один.
- [ ] Webhook всегда отвечает 200 на корректно подписанный апдейт, даже если хендлер упал. Исключение пишется в лог с `update_id` и типом апдейта, без текста сообщения и без `telegram_id`.
- [ ] Повторный апдейт с тем же `update_id` не обрабатывается второй раз (дедупликация через кэш, `cache.add(..., timeout=...)`, TTL из settings). Ответ на повтор — 200.
- [ ] Коды ответа webhook: 503 без токена или секрета (как сейчас), 403 при неверном секрете, 400 при невалидном JSON или JSON без `update_id`, 200 во всех остальных случаях.
- [ ] Секрет сравнивается через `hmac.compare_digest`.
- [ ] Режим получения апдейтов задаётся одной переменной `.env`: `TELEGRAM_UPDATES_MODE=polling|webhook` (по умолчанию `polling`). Имя выбрано так, чтобы не пересекаться с `TELEGRAM_MODE=real|demo` адаптера из 3.4.
- [ ] В режиме `polling` `run_bot` снимает webhook **без** `drop_pending_updates`, накопленные апдейты обрабатываются.
- [ ] В режиме `webhook` `run_bot` не запускает polling и не вызывает `delete_webhook`. Он устанавливает webhook на `SITE_URL + /api/v1/telegram/webhook/` с `TELEGRAM_WEBHOOK_SECRET` и завершается с кодом 0 (сервис `bot` с `restart: on-failure` после этого не перезапускается). Если секрета нет или `SITE_URL` не `https://`, команда завершается с понятной ошибкой и ненулевым кодом, webhook не трогается.
- [ ] Рестарт сервиса `bot` в режиме `webhook` больше не снимает webhook.
- [ ] Очистка `Update.event_type.fget.cache_clear` работает для всех тестов пакета (общий базовый класс или `tearDownModule`), тест-страховка проверяет, что кэш пуст.

## Шаги
1. Создать `telegram_bot/formatting.py`: `listing_card_html(title_parts, price, currency, status)` и общий хелпер `esc()` на `html.escape(str(value), quote=True)`. Перевести `/latest` (`handlers.py:73-100`) и текст поста (`tasks.py:55-63`) на эти функции. URL в кнопках не экранировать как HTML, но собирать только из `SITE_URL` и `pk`.
2. Привязка (`handlers.py:105-126`): внутри `_process` обернуть в `transaction.atomic()`, взять токен через `select_for_update()`. Перед записью проверить `CustomUser.objects.filter(telegram_id=telegram_id).exclude(pk=user.pk).exists()`. Если занят — вернуть `'taken'`, токен не гасить. Если уже этот же пользователь — `'already'`. На всякий случай перехватить `IntegrityError` при `save` и вернуть `'taken'`. Добавить ответы для `'taken'` и `'already'` (тексты пока в коде рядом с остальными; в админку их переносит 5.4).
3. Webhook (`views.py:63-114`):
   - `hmac.compare_digest(incoming.encode(), secret.encode())`;
   - после `json.loads` проверить, что это `dict` с целым `update_id`, иначе 400;
   - `if not cache.add(f'tg:update:{update_id}', 1, timeout=settings.TELEGRAM_UPDATE_DEDUP_TTL): return 200`;
   - вызов `async_to_sync(self._process_update)` обернуть в `try/except Exception`: `logger.exception('Webhook: ошибка обработки update_id=%s', update_id)` и ответ 200. Обработку оставить синхронной: хендлеры короткие, а перенос в Celery потребует отдельной сериализации апдейта. Если по ходу окажется, что время ответа > 5 с, записать это в отчёт, а не переделывать молча.
   - В тестах кэш — `LocMemCache` (проверить `CACHES` при `REDIS_URL=`); в проде Redis, значит дедупликация общая для всех воркеров gunicorn.
4. `run_bot`:
   - прочитать `settings.TELEGRAM_UPDATES_MODE`; неизвестное значение → `CommandError`;
   - `polling`: `await bot.delete_webhook(drop_pending_updates=False)`, затем `start_polling` как сейчас;
   - `webhook`: проверить `TELEGRAM_WEBHOOK_SECRET` и `SITE_URL.startswith('https://')`, иначе `CommandError` с текстом, что именно задать в `.env`. Вызвать `bot.set_webhook(url, secret_token=secret, drop_pending_updates=False)`, вывести `get_webhook_info().url` и выйти. Код установки вынести в функцию (например, `telegram_bot/webhook_setup.py`), чтобы 5.4 переиспользовала её в `set_webhook`.
5. `bot_entrypoint.sh`: оставить проверку токена и `exec python manage.py run_bot`. Добавить строку в лог с режимом. Комментарий в `docker-compose.yml:81` поправить: exit 0 теперь бывает и в режиме webhook.
6. Тесты: вынести `self.addCleanup(Update.event_type.fget.cache_clear)` в общий базовый класс (или `tearDownModule`) и унаследовать от него все классы, которые шлют апдейты. Написать тесты из раздела ниже.
7. Прогнать `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test`, затем `python manage.py check`. Поднять `docker compose up bot` с пустым токеном — сервис завершается с кодом 0, как раньше.

Схема БД не меняется, миграций нет.

## Для владельца (LAUNCH_CHECKLIST)
- `.env`: `TELEGRAM_UPDATES_MODE` — `polling` (по умолчанию, работает без домена и HTTPS) или `webhook` (для прода после настройки HTTPS из задачи 7.1).
- Для `webhook` обязательно: `SITE_URL=https://<домен>`, `TELEGRAM_WEBHOOK_SECRET` (случайная строка 32+ символа, только `A-Z a-z 0-9 _ -`).
- Как проверить: после `docker compose up -d` в логе сервиса `bot` строка «Webhook установлен: https://<домен>/api/v1/telegram/webhook/»; `/start` в боте отвечает; рестарт `docker compose restart bot` webhook не снимает.
- `TELEGRAM_UPDATE_DEDUP_TTL` менять не нужно.
