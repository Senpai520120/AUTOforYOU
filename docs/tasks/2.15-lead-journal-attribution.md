## Цель
- [ ] **`public_id`** у `Lead`: формат `AFY-ГГГГ-NNNN` (например `AFY-2026-0001`), последовательный по календарному году, уникальный индекс. Генерация в `create_lead` под `select_for_update` на строке счётчика года (`LeadCounter(year, last_number)`), в той же транзакции, что и создание заявки. `public_id` **не секрет и не ключ доступа**: по нему нельзя получить заявку по API; публичные ответы отдают его только создателю заявки при создании.
- [ ] **Согласие `partner_transfer`:** обязательный чекбокс «Погоджуюсь на передачу моїх контактів партнеру [назва партнера]»; без него `POST /api/v1/leads/` даёт 400 (ошибка поля `partner_consent`), запись не создаётся. Согласие пишется в `ConsentRecord` (1.14) с версией текста, привязывается к заявке. Если `SiteSettings.partner_name` пуст, чекбокс не активен, а создание заявки возвращает 503 с понятным сообщением (владелец ещё не указал партнёра; подтвердить решение, см. «Вопросы»). `lead.partner_name` **копируется снимком** при создании.
- [ ] **Журнал в Telegram-группу:** новая настройка `LEAD_JOURNAL_CHAT_ID` (`.env`, может совпадать с чатом брокера). Сообщение содержит **только** `public_id` (AFY-ID), марку/модель, бюджет, город и время (UTC). **Имени и телефона в группе нет никогда** (ни с согласием, ни без; решение владельца после промта 02): текст собирает сервис по белому списку полей, шаблон из админки ПДн не подставляет. Контакты клиента брокер получает в личном уведомлении (2.2) и в кабинете (2.4). Из ответа Telegram сохраняется `journal_message_id` (квитанция отправки) и `journal_sent_at`. Сбой отправки повторяется механизмом 2.12 и не блокирует создание заявки. Без `LEAD_JOURNAL_CHAT_ID` отправка выключена, заявки создаются.
- [ ] **Запрет удаления:** у роли `broker` нет права `leads.delete_lead`; в `LeadAdmin` и в API кабинета брокера удаление заявки (и `LeadStatusChange`) недоступно всем, кроме суперпользователя (`has_delete_permission`). Обезличивание аккаунта (1.8) **не стирает** `public_id`, `created_at`, `partner_name`, `journal_message_id`, `partner_status`, `status` и журнал статусов.
- [ ] **Квалификация:** `qualification` (`hot` / `cold` / `unrated`, по умолчанию `unrated`) и четыре булевых поля `q_budget_ok` (бюджет не ниже порога), `q_term_ok` (срок не более трёх месяцев), `q_knows_repair` (знает про ремонт), `q_ready_deposit` (готов к депозиту), все `null` до заполнения. Сервис `qualify_lead(lead, answers, by)` считает: `hot`, если «да» набрано не меньше `hot_min_score` из четырёх; иначе `cold`; пока ответили не на все четыре — `unrated`. **Порог (по умолчанию 3) и сумма бюджета (по умолчанию 8000, USD) — поля настроек в админке** (singleton `LeadJournalSettings`), в коде нет числовых констант. Квалификацию ставит брокер или admin.
- [ ] **`partner_status`** — отдельное поле от `status`: `not_reached` (не додзвонилися), `thinking` (думає), `deposit` (депозит), `bought` (куплено), `rejected` (відмова), по умолчанию пусто. `status` меняет брокер по ходу работы (2.4), `partner_status` вносится по ежемесячной сверке с отчётом партнёра. Изменения `partner_status` пишутся в журнал (модель `LeadPartnerStatusChange`: кто, когда, откуда, куда), удаление записей запрещено. В CSV идут оба поля.
- [ ] **Окно атрибуции:** `attribution_until` = `created_at` + N месяцев, считается при создании. N — поле `attribution_window_months` в `LeadJournalSettings`, по умолчанию 12. Изменение N не меняет уже созданные заявки.
- [ ] **CSV-экспорт заявок:** `GET /api/v1/broker/leads/export.csv` (admin и broker; остальным 403, анониму 401) и действие в `LeadAdmin`. Колонки: `public_id`, дата (UTC), `status`, `partner_status`, `qualification`, `utm_source`, `utm_campaign`, `source`, `city`, `budget_usd`, `partner_consent_at`, `partner_name`, `attribution_until`. **Без** имени, телефона, email, комментария, `referrer` и URL страниц. Фильтры: период и `status` (совпадают с фильтрами списка 2.4). Ячейки с началом `=`, `+`, `-`, `@` экранируются (CSV-инъекция), потоковый вывод (`StreamingHttpResponse`), ответ с `Content-Disposition: attachment`. Каждый экспорт пишется в аудит (кто, когда, фильтр, число строк). Лимит частоты экспорта через throttle scope `lead_export` (`THROTTLE_LEAD_EXPORT_RATE`).
- [ ] **Админ-страница «Воронка за месяц»** (`/admin/leads/funnel/`, только admin/superuser): выбор месяца (по умолчанию текущий), таблицы: всего заявок, из них `hot`, число заявок по `utm.source` («пряме» при пустом), число по `partner_status` (в том числе «не вказано»). Без графиков и без JS (графики — 9.32, Рост). Запросы агрегируют в БД (`values().annotate(Count)`), без ПДн на странице.
- [ ] Права на новые поля: `qualification`, `q_*`, `partner_status` меняют broker и admin; `public_id`, `partner_name`, `attribution_until`, `journal_message_id`, `created_at` — только чтение у всех.
- [ ] `openapi.yaml` перегенерирован против Postgres; интерфейсные строки на украинском; деньги только `Decimal`, поле бюджета с суффиксом валюты.

## Шаги
1. **Модели и миграции** (причина: без постоянного кода, снимка партнёра и журнала статусов нельзя доказать партнёру, что клиент пришёл от нас, а смена названия партнёра или удаление аккаунта сотрёт историю). `LeadCounter(year PK, last_number)`; поля `Lead` из раздела «Цель» (`public_id` — `unique`, `db_index`, заполняется сервисом; для уже существующих заявок data-миграция проставляет коды по `created_at`, год и порядок в пределах года); `LeadPartnerStatusChange`; `LeadJournalSettings` (singleton: `hot_min_score`, `hot_budget_usd` Decimal, `attribution_window_months`). `TextChoices` на уровне модуля (ловушка проекта).
2. **`create_lead`**: в `transaction.atomic()` брать `LeadCounter` через `select_for_update().get_or_create(year=...)`, увеличить, собрать `public_id`; записать `partner_name` из `SiteSettings`, `partner_consent_at` и `ConsentRecord` типа `partner_transfer`, `attribution_until` (через `dateutil.relativedelta` или вычисление месяцев без сторонней зависимости; для 31-го числа брать последний день месяца). Затем `on_commit`: уведомление брокеру (2.2) и `send_journal_message`.
3. **`send_journal_message(lead_id)`**: собрать текст в сервисе по белому списку (AFY-ID, марка/модель, бюджет, город, время UTC), имя и телефон в текст не попадают; экранировать `html.escape`; отправить через клиент бота из 2.2; сохранить `journal_message_id`; ошибка не пробрасывается, повтор делает 2.12 (идемпотентность: если `journal_message_id` уже есть, второй раз не слать).
4. **Сериализатор приёма**: поле `partner_consent` (`BooleanField`, `must be True`, ошибка на украинском), текст чекбокса приходит с названием партнёра из публичного эндпоинта настроек (1.12); ответ 201 дополняется `public_id`. Honeypot и капча остаются как в 2.1 (порядок проверок не менять).
5. **Квалификация и `partner_status`**: сервисы `qualify_lead`, `set_partner_status` с проверкой роли (broker/admin), запись в журнал; поля в `LeadDetailSerializer` брокера (2.4) и PATCH-действия `/api/v1/broker/leads/{id}/qualification/` и `/partner-status/`. Порог читается из `LeadJournalSettings` при каждом расчёте.
6. **Запрет удаления**: убрать `delete_lead` и `delete_leadstatuschange` из прав группы `broker` (data-миграция прав, как у других групп в 1.2), `LeadAdmin.has_delete_permission` и inline: только `request.user.is_superuser`; в API кабинета брокера метод `DELETE` не определять (405). Обезличивание из 1.8: список полей, которые оно очищает, явный (whitelist ПДн), `public_id`, даты, статусы и журнал в него не входят.
7. **CSV**: `leads/exports.py` (генератор строк, функция `csv_safe(value)`), `LeadExportView` с `throttle_scope='lead_export'`, запись в аудит (лог или модель аудита из 1.x, если есть; иначе таблица `LeadExportLog`). Действие в `LeadAdmin` использует тот же генератор.
8. **«Воронка за месяц»**: `leads/funnel.py` возвращает словарь агрегатов; страница в `LeadAdmin.get_urls()`, доступ `admin_site.admin_view` плюс проверка права `leads.view_funnel`; параметр `?month=ГГГГ-ММ` с валидацией (иначе текущий месяц).
9. **Фронт**: чекбокс партнёра в `LeadForm` (не активен, пока название партнёра не пришло); `LeadSuccess` показывает «Назвіть менеджеру код AFY-…» (экран и текст вводит 2.3, здесь только `public_id` из ответа); в кабинете брокера блок квалификации (четыре «так/ні» и бейдж), выбор `partner_status`, кнопка CSV.
10. **Документы**: `.env.example` (`LEAD_JOURNAL_CHAT_ID`, `THROTTLE_LEAD_EXPORT_RATE`), `docs/LAUNCH_CHECKLIST.md`, `openapi.yaml` против Postgres.

## Тесты
Django (`leads/tests.py`, запуск `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test leads`; Telegram и `ConsentRecord` — с моками):
- `public_id`: первая заявка года `AFY-ГГГГ-0001`, вторая `...-0002`; смена года обнуляет счётчик (подмена `timezone.now`); два параллельных создания (`TransactionTestCase` + потоки или проверка вызова `select_for_update`) не дают дубля; уникальный индекс не даёт сохранить дубль вручную; `public_id` не принимается из входных данных.
- `partner_consent`: нет поля или `false` → 400 на `partner_consent`, `Lead.objects.count() == 0`; `true` → 201, `ConsentRecord` типа `partner_transfer` с версией текста; `partner_name` пуст в настройках → 503, записи нет; после смены `SiteSettings.partner_name` старая заявка сохраняет прежнее название.
- Журнал: в тексте сообщения есть `public_id`, марка/модель, бюджет, город, время UTC; имени, телефона, email и комментария нет ни с согласием `partner_transfer`, ни без него (проверка на тестовых значениях). `journal_message_id` сохраняется; сбой Telegram не ломает создание заявки; повтор не шлёт дубль при заполненном `message_id`; без `LEAD_JOURNAL_CHAT_ID` отправки нет. Вставка `<script>` в имя экранируется.
- Удаление: пользователь `broker` — `DELETE` через API 405, в админке `has_delete_permission` ложь, `POST` на delete-форму → 403; admin без суперправ → 403; суперпользователь удаляет успешно. Обезличивание аккаунта оставляет `public_id`, `created_at`, `partner_name`, `status`, `partner_status`, `journal_message_id`, журнал статусов и очищает имя, телефон, комментарий.
- Квалификация: 4 из 4 и 3 из 4 → `hot`; 2 из 4 → `cold`; не все четыре ответа → `unrated`. Изменить `hot_min_score` на 4 в админке → 3 из 4 становится `cold`. Изменить сумму порога бюджета → меняется вычисление `q_budget_ok` там, где оно автоматическое. Обычный пользователь и аноним → 403/401.
- `partner_status`: допустимые значения; недопустимое → 400; смена пишет `LeadPartnerStatusChange`; запись журнала нельзя удалить; `status` и `partner_status` меняются независимо.
- `attribution_until`: по умолчанию `created_at` + 12 месяцев; N=6 → +6; 31 августа + 6 месяцев → последний день февраля; изменение N не меняет старые заявки.
- CSV: admin и broker получают 200 и `text/csv`; клиент (не staff) → 403; аноним → 401; в файле нет имени, телефона, email, комментария, `referrer`, URL (проверка строки заголовка и содержимого на тестовых значениях); имя вида `=HYPERLINK(...)` в `city`/`utm_source` экранировано префиксом; фильтр по периоду и `status` работает; throttle → 429; запись аудита создана.
- Воронка: тестовые 10 заявок за месяц (разные `utm.source`, `hot`/`cold`, `partner_status`) дают верные числа; заявки соседнего месяца не учитываются; не-admin → 403/редирект на вход; в HTML нет телефонов и имён; неверный `?month=` → текущий месяц, не 500.
- Админка: колонки и фильтры `qualification` и `partner_status` присутствуют; `public_id` и `attribution_until` только для чтения.
Playwright (`frontend/e2e/lead-journal.spec.ts`):
- Успех: отправить заявку с галочкой партнёра → на экране код `AFY-…`; брокер входит, видит заявку, ставит четыре «так» → бейдж «Гаряча», выбирает `partner_status` «Депозит», скачивает CSV (файл без телефона).
- Ошибка/обход: отправка без галочки партнёра → сообщение об ошибке, запрос не создаёт заявку; кнопка отправки заблокирована, пока название партнёра не загружено; broker на `DELETE`/в админке удаление недоступно (403); клиент без роли по прямой ссылке на CSV получает 403.
