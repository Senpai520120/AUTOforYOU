# Задача 2.14: Источник визита при регистрации и подаче объявления (first-touch)

> Источник: Н-37 (`docs/audit/38_PARITY_O_P.md`, O2.2, O2.3; `docs/audit/32_NEW_TASKS_INDEX.md`). Решение владельца (ANSWERS, шаг 8): UTM, реферер и страница входа сохраняются при регистрации, подаче объявления и заявке; до отправки формы лежат в `sessionStorage` без согласия на cookie, третьим лицам не передаются. Волна: [ВОЛНА-1]. Оценка: 1 сессия. Проверка security-reviewer: **обязательна** (ПДн, поля видны только admin).

## Контекст
- Заявку брокеру (источник `utm`, `referrer`, `entry_page_url`, `page_url`) делают 2.1–2.4 (Н-26). Фронтовый хелпер захвата `frontend/lib/attribution.ts` создаёт 2.3; здесь он только используется. Whitelist ключей UTM (`source`, `medium`, `campaign`, `content`) и ограничения длины введены в 2.1 (`leads/serializers.py`, шаг 4 задачи 2.1).
- Регистрация: `RegisterSerializer` (`users/serializers.py:8-37`, `fields` на `:22`), `RegisterView` (`users/views.py:41`), форма `frontend/app/register/page.tsx` (тело запроса `:26`). `CustomUser` (`users/models.py:24-45`) источник не хранит.
- Подача объявления: `LocalListingListCreateView` (`local_listings/views.py:124`), `LocalListingCreateSerializer` (`local_listings/serializers.py:149-224`, `read_only_fields` на `:164`), модель `LocalListing` (`local_listings/models.py:64`), форма `frontend/components/local/LocalListingForm.tsx`. Публичные сериализаторы объявлений перечисляют поля явно (`local_listings/serializers.py:68-146`), `UserProfileSerializer` тоже (`users/serializers.py:40-58`): новые поля туда не попадут, пока их не добавят руками. Это инвариант, его надо закрепить тестом.
- Админки: `CustomUserAdmin` (`users/admin.py:34`), `LocalListingAdmin` (`local_listings/admin.py:92`), `ModerationQueueAdmin` (`:153`, её видит модератор по Q10). Поля источника должны видеть только admin.
- В политике конфиденциальности строка про `sessionStorage` и UTM уже внесена задачей 1.12 (шаг 8), `/cookies` не меняется.
- Вопрос юристу о том, считать ли `sessionStorage` без согласия допустимым, остаётся открытым (ANSWERS его уже решил как «без согласия, одна строка в политике»; подтверждение юристом — LAUNCH_CHECKLIST).

## Цель
- [ ] У `CustomUser` три поля источника первого касания: `first_touch_utm` (JSON, whitelist), `first_touch_referrer`, `first_touch_entry_url`. Пишутся **один раз** при регистрации и дальше не меняются (в том числе через профиль и API).
- [ ] У `LocalListing` те же три поля `utm`, `referrer`, `entry_page_url` — источник на момент подачи. Не меняются при редактировании, не копируются в публичные ответы и в выгрузку другим пользователям.
- [ ] Общая функция очистки `clean_attribution(data) -> dict` в одном месте (используют заявка 2.1, регистрация и объявление): оставляет только разрешённые ключи UTM, обрезает значения по длине, отбрасывает не-строки; у `referrer` и `entry_page_url` **удаляются query и fragment** (в реферере и URL бывают токены и чужие ПДн), допускаются только `http`/`https`, длина ограничена.
- [ ] Регистрация и форма объявления отправляют `attribution` из `lib/attribution.ts` (когда он пуст — запрос идёт без него и работает как раньше). Ошибка или мусор в `attribution` не блокируют регистрацию и подачу (поле отбрасывается, регистрация проходит).
- [ ] В админке поля источника видны и доступны только для чтения у admin/superuser (право `users.view_attribution`); `moderator` и `broker` их не видят, в том числе через `ModerationQueueAdmin`.
- [ ] Поля не попадают ни в один публичный и пользовательский API: каталог, карточка, `owner`-ответ, профиль, выгрузка данных чужих пользователей. В выгрузке самого пользователя (1.8) его собственный источник регистрации есть.
- [ ] При обезличивании аккаунта (Q3) `first_touch_*` очищаются; у объявлений поля остаются обезличенными (без `entry_page_url` и `referrer`), как и остальные данные объявлений в архиве.

## Шаги
1. `core/attribution.py`: `ALLOWED_UTM_KEYS`, `MAX_VALUE_LEN`, `clean_attribution(raw) -> {'utm': {...}, 'referrer': str, 'entry_url': str}`; чистка URL через `urllib.parse` (схема `http`/`https`, отрезать `query`/`fragment`, обрезать длину). Покрыть модульными тестами.
2. Миграции (причина: без записи источника первого касания нельзя понять, какой ролик или канал привёл пользователя и объявление, и собрать это задним числом нельзя). Поля необязательные, по умолчанию пусто; существующие записи не трогаем.
3. `RegisterSerializer`: необязательное write-only поле `attribution` (`DictField`, не обязательное); в `create` пишется один раз; исключение внутри очистки не должно ронять регистрацию.
4. `LocalListingCreateSerializer`: то же при создании; `LocalListingUpdateSerializer` (`local_listings/serializers.py:225`) поле не принимает.
5. Админки: `readonly_fields` и показ полей только при `request.user.has_perm('users.view_attribution')` (в `get_fields` / `get_readonly_fields`), группа admin получает право в миграции 1.2-группы или data-миграцией этой задачи.
6. Фронт: в `register/page.tsx` и `LocalListingForm.tsx` в тело запроса добавляется `attribution: getAttribution()`; пустое значение — поле не отправляется. Хранение остаётся в `sessionStorage`, cookie не используются.
7. Выгрузка и обезличивание (1.8): добавить поля пользователя в экспорт, очистку при Q3.

## Тесты
Django (`core/tests.py`, `users/tests.py`, `local_listings/tests.py`):
- `clean_attribution`: лишние ключи отброшены, длинные значения обрезаны, не-строки отброшены, `https://t.me/x?token=SECRET#a` → без query и fragment, `javascript:alert(1)` → пусто.
- Регистрация с `attribution` сохраняет поля; без `attribution` — пусто и 201; мусор (`attribution='x'`, список) → 201 без полей; повторный PATCH профиля с `first_touch_utm` не меняет значение.
- Подача объявления сохраняет источник; редактирование его не меняет и не принимает.
- Публичный каталог, карточка, ответ владельца, `GET /auth/profile/` и ответ `GET /auth/me/` не содержат полей источника (проверка набора ключей ответа).
- Админка: admin с правом видит поля только для чтения; `moderator` и `broker` не видят их ни в `CustomUserAdmin`, ни в `ModerationQueueAdmin`.
- Обезличивание очищает `first_touch_*`.
Playwright (`frontend/e2e/attribution.spec.ts`):
- Успех: открыть `/calculator?utm_source=tiktok&utm_campaign=test`, перейти на `/register`, зарегистрироваться → в теле `POST` регистрации есть `attribution.utm.source=tiktok`, значения лежат в `sessionStorage`, в cookie их нет; проверка в БД/админ-API фикстуры: у нового пользователя `first_touch_utm.source=tiktok`.
- То же для подачи объявления (новый аккаунт, форма `/local/new`): `attribution` уходит в `POST`.
- Ошибка/обход: подмена значения в `sessionStorage` на мусор и очень длинную строку → регистрация проходит, источник пустой или обрезан; визит без UTM → `attribution` не отправляется, регистрация работает; пользователь не может записать источник через PATCH профиля (запрос отклонён или поле проигнорировано).
