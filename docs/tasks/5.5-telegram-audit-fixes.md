## Цель
- [ ] **F9:** привязка Telegram в `atomic` с `select_for_update` по токену привязки и по `telegram_id`; если Telegram уже привязан к другому аккаунту — понятный ответ пользователю («Цей Telegram уже прив'язано до іншого акаунту»), webhook отвечает 200, без `IntegrityError` и без повторов от Telegram. Токен одноразовый даже при гонке.
- [ ] **F10:** уведомления отправляются через `telegram_bot/sender.send_message` / провайдер 3.4b; задача `send_notification` — `base=ResilientTask` (`core.tasks`), повторы на `TelegramNetworkError` и `TelegramRetryAfter` (последнее — `self.retry(countdown=retry_after)`, не проглатывается общим `except`); после исчерпания повторов — запись в `FailedTask` (8.9) и `record_error('telegram', ...)`. Имя задачи и сигнатура не меняются.
- [ ] **F12:** секрет webhook сравнивается `hmac.compare_digest`; пустой секрет по-прежнему → 503.

## Тесты
Django (все внешние вызовы замоканы; мутацией):
- **F9:** два аккаунта, один `telegram_id` → второй получает сообщение «вже прив'язано», `IntegrityError` не вылетает, webhook 200, у второго `telegram_id` пуст; параллельная привязка одним токеном (Postgres, `skipUnless`) → одна привязка; повторное использование токена → отказ.
- **F10:** мок `Bot.send_message` бросает `TelegramNetworkError` → задача ушла в retry, а не вернула «sent: False»; `TelegramRetryAfter(5)` → `retry(countdown=5)`; после исчерпания повторов создан `FailedTask`; в логах нет `telegram_id` и текста сообщения; без токена → `{'sent': False, 'reason': 'not_configured'}` без повторов.
- **F12:** запрос с неверным секретом → 403/401 (текущий код ответа сохранить), с верным → 200, без секрета в настройках → 503; тест, что используется `compare_digest` (мок).
- 401/403: webhook без заголовка секрета → отказ, БД не меняется.
Playwright: UI не затронут; существующие e2e (уведомление о заявке в `OutboxMessage` при `TELEGRAM_MODE=demo`) остаются зелёными.
