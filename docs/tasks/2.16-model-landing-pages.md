## Шаги
1. **Приложение `landings`**, модели `ModelLandingPage`, `LandingSettings` (singleton с `max_published`), миграция `0001_initial` (причина: тексты и входы расчёта для страниц должен править владелец в админке без релиза). `TextChoices` на уровне модуля; поля денег с суффиксом валюты (`auction_price_usd`), `Decimal`.
2. **`landings/services.py`**: `build_landing_calculation(page, *, now=None) -> dict | None` (собирает `LandedCostInputs` из полей страницы, берёт активные ставки на дату, вызывает чистую функцию, добавляет `is_estimate: true`, `rates_valid_from`, валюты и курс снимком; при отсутствии активных ставок или неполных входах возвращает `None`); `can_publish(page)`. Модуль без обращений к HTTP; БД только для чтения ставок через `build_rate_snapshot_from_db`.
3. **Админка**: `ModelLandingPageAdmin` со списком (марка/модель, slug, опубликована, итог расчёта или «немає розрахунку»), действие «Опублікувати вибрані» (пропускает страницы без расчёта и сообщает, какие и почему), предупреждение при превышении `max_published`, предпросмотр расчёта в карточке (только чтение). Поля расчёта и публикации валидируются в `clean()`.
4. **API**: `GET /api/v1/landings/` (опубликованные: slug, марка, модель, итог, `updated_at`; кэш), `GET /api/v1/landings/<slug>/` (страница + расчёт; 404, если не опубликована или расчёт не получается; throttle для анонима общий). Ответы без служебных полей и без ПДн, `GET` ничего не пишет в БД.
5. **Приём заявки с `landing_slug`** (в `leads/`): сериализатор принимает `landing_slug`, находит опубликованную страницу, вызывает `build_landing_calculation`, пишет результат в `calculation_snapshot` и `total_usd/total_uah`, ставит `source=landing`. Неизвестный или неопубликованный slug → 400. Расчёты, присланные клиентом, игнорируются. Уведомление брокеру (2.2) в теме содержит модель.
6. **Фронт**: серверные страницы `/prigon` и `/prigon/[slug]` с `revalidate`, `generateMetadata`, canonical, OG, 404 через `notFound()`; `LandingCalc` — только отображение (без расчётов); форма заявки с предзаполнением; липкая панель `LandingMobileBar` (скрыта на ≥ `md`, не перекрывает футер и cookie-плашку); ссылка на калькулятор передаёт входы в query (как принято в 2.6).
7. **Sitemap**: в `frontend/app/sitemap.ts` добавить `/prigon` и опубликованные `/prigon/<slug>` с `lastModified`; при недоступном API sitemap не падает (пустой список страниц, остальное остаётся).
8. **`seed_landing_pages`**: читает `landing_models.json`, создаёт страницы со статусом «чернетка», заполняет тексты-заготовки на украинском без цифр, сообщает, какие страницы ждут цены; опция `--dry-run`. В `docs/LAUNCH_CHECKLIST.md` — как внести цены и опубликовать.
9. **Документы**: `CLAUDE.md`, `openapi.yaml` против Postgres, `docs/LAUNCH_CHECKLIST.md`.

## Тесты
Django (`landings/tests.py`, `leads/tests.py` — в части приёма `landing_slug`; запуск `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test landings leads`):
- Страница с полными входами и активными ставками: `GET /api/v1/landings/<slug>/` → 200, `is_estimate` равно `true`, итоги — `Decimal`-строки, есть `rates_valid_from`, значение равно прямому вызову `calculate_landed_cost` с теми же ставками (сверка с эталоном).
- Без расчёта: нет активных ставок или не заполнены обязательные входы → `is_published=True` не сохраняется (ошибка `clean()`), действие «Опублікувати» пропускает такую страницу, API → 404, в `sitemap`-списке её нет. Ставки истекли после публикации → API 404.
- Неопубликованная страница → 404; список `GET /api/v1/landings/` её не содержит; служебные поля не отдаются.
- Изменение ставки в админке (новая запись с `valid_from`) меняет итог страницы без правки кода (ставки не хардкожены); `GET` не создаёт `Calculation` и не пишет в БД (`assertNumQueries` на запись/счётчик объектов).
- Заявка с `landing_slug`: 201, `lead.source == landing`, `calculation_snapshot` содержит входы страницы, ставки, разбивку, `is_estimate`, дату ставок; суммы, присланные клиентом, игнорируются; неверный или неопубликованный slug → 400; `entry_page_url` = `/prigon/<slug>`.
- `seed_landing_pages`: создаёт 30 страниц как черновики, повторный запуск не дублирует и не перезаписывает правки; страницы без цены остаются неопубликованными; `--dry-run` ничего не пишет.
- `max_published`: превышение лимита → предупреждение, не ошибка; изменение значения в `LandingSettings` до 50 снимает предупреждение (проверка, что в коде нет числа 30).
- Slug уникален; недопустимые символы в slug → ошибка валидации.
Playwright (`frontend/e2e/landing.spec.ts`; фикстура создаёт опубликованную страницу с расчётом):
- Успех: открыть `/prigon/<slug>` → виден H1, итог под ключ, надпись «орієнтовно», дата ставок, срок; `<link rel="canonical">` и OG-теги присутствуют; в `/sitemap.xml` есть адрес страницы; форма предзаполнена маркой/моделью; отправка заявки (с согласиями) → экран успеха с кодом; в мобильном viewport липкая панель «Залишити заявку» видна и открывает форму.
- Ошибка/обход: неопубликованная или несуществующая страница → 404 (и нет в sitemap); при недоступном API страница показывает честную ошибку, а не пустой расчёт и не устаревшие цифры; отправка формы без обязательного согласия не создаёт заявку; подмена суммы в запросе заявки не меняет итог в `calculation_snapshot` (проверка через админ-API фикстуры).
