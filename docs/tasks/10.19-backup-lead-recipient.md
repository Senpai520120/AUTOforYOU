# Задача 10.19: Запасной получатель заявок (второй chat_id)

## Контекст
Источник: `docs/audit/41_REVIEW_2026-11-11.md`, находка C7. Размер S, P1.
Сейчас одному брокеру уходит одно Telegram-сообщение: `leads/tasks.py` `_telegram_step` шлёт в `notify.broker_chat_id()` (`LeadNotificationSettings.telegram_chat_id`, иначе `TELEGRAM_BROKER_CHAT_ID`). Если чат брокера недоступен (бот заблокирован, чат удалён), остаются только резервный email и досыл 10.6. Статус доставки пишется в `Lead.telegram_status` / `Lead.telegram_error`. Журнал партнёру (2.15) идёт отдельно в группу `LEAD_JOURNAL_CHAT_ID` (`leads/services.py:send_journal_message`) и от брокерского чата не зависит.
Модель `Partner` здесь не делаем (9.46, когда появится второй брокер).

## Цель
- `LeadNotificationSettings.backup_telegram_chat_id` (blank, тот же валидатор числового chat_id). Только в админке, не в .env.
- Поведение: основной chat_id не принял сообщение после всех попыток (Telegram-ошибка, обрыв, исчерпаны повторы) -> то же сообщение уходит в запасной (одна попытка в цикле, без `self.retry`). Основной не задан, запасной задан -> сообщение идёт в запасной (заявка не теряется), основной не подменяется: поле не копируется, в `launch_check` остаётся ERROR о пустом основном.
- Видно в админке: заявка получает `telegram_status=sent`, а `telegram_error` = `via_backup:<код ошибки основного>` (или `via_backup:no_primary`). Новых полей и схемы в `Lead` нет. Если запасной тоже не принял: `failed`, `telegram_error` = `backup_failed:<код основного>`.
- Запасной = основной (тот же id) игнорируется (без двойной отправки). Нет токена бота / Telegram выключен: запасной не пробуем (тот же бот), `skipped`.
- Журнал партнёра (2.15) не меняется: записи по заявке одна, на неё запасной получатель не влияет. Повтор Telegram идемпотентен по `telegram_status=sent`.
- `launch_check`: запасной не задан -> WARNING (не ERROR); задан -> OK.
- Логи: только `lead_id` и имя класса/код ошибки, без chat_id, имени, телефона. Тексты админки по-украински.
