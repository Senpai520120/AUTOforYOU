# Задача 3.1: Каркас адаптеров и страница статуса интеграций

## Контекст
Бриф §2 требует, чтобы у каждого из 8 провайдеров (курс НБУ, VIN/NHTSA, carVertical, Opendatabot, источник лотов, LiqPay, SMTP, Telegram) были интерфейс, real- и demo/sandbox-реализация, переключение одной переменной `.env`, честное «не настроено» и статус в админке. Сводная таблица провайдеров (`docs/audit/03_integrations.md`, раздел «Сводная таблица провайдеров») показывает, что полного набора нет ни у одного из них.

Что сейчас в коде:
- **03-C1 (важно):** `.env.example:47-48` (`LIQPAY_PUBLIC_KEY=your_liqpay_public_key`, `LIQPAY_PRIVATE_KEY=your_liqpay_private_key`) и `.env.example:52-53` (`OPENDATABOT_API_KEY=your_opendatabot_api_key`, `APIFY_TOKEN=your_apify_token`) содержат непустые плейсхолдеры. Если скопировать `.env.example` в `.env`, фабрики считают ключ заданным и включают real-режим с заведомо неверным ключом (`integrations/providers.py:252-257`, `:369-374`). Вместо честного «не настроено» получаются ошибки внешнего API. В `.env.docker.example:52-53,77-78` эти переменные пустые, там всё корректно.
- 03-C4, 03-C5: режим провайдера определяется только наличием ключа. Явного переключателя `*_MODE` нет. Фабрики VIN и BidFax жёстко возвращают stub (`integrations/providers.py:244-249`).
- 03-C5: статуса интеграций в админке нет. `integrations/admin.py:6-19` показывает только кэши `VinReport` и `RegistryReport`.
- 03-Q12 (желательно): провайдеры ничего не логируют, ошибки превращаются в dict через широкий `except Exception` (`integrations/providers.py:85`, `:212`, `:365`). Админ о сбоях не узнает.
- 03-C9 (желательно): таймауты 10 с и 60 с захардкожены (`integrations/providers.py:82`, `:209`, `:358`).
- У НБУ (`pricing/nbu.py:14-68`), NHTSA (`integrations/providers.py:70`, класс без ABC), LiqPay (`payments/liqpay_client.py:27-40`) и Telegram (`aiogram.Bot` напрямую в `integrations/tasks.py:89`, `telegram_bot/tasks.py:72`, `telegram_bot/views.py:109`) общего интерфейса нет. Их переводят на каркас задачи 3.2–3.4, а эта задача даёт им общую основу.
- SMTP: `core/settings.py:335-344`. По умолчанию console-backend, признака «не настроено» нет (01-C7).
- Утечка ключа Opendatabot в ответ и кэш (03-S1) закрывается в задаче **1.1**. Здесь её не дублировать: хелпер маскировки секретов, созданный в 1.1, переиспользовать в каркасе. Если в 1.1 хелпер не выделен, вынести его в `integrations/base.py` и перевести 1.1-код на него без изменения поведения.
- Файла `docs/audit/22_CONFIG.md`, на который ссылается ТЗ, в репозитории нет (`docs/audit/STATUS.md:48` — «в процессе»). Данные о конфигурации взяты из разделов «Готовность к конфигурации» отчётов 01, 02, 03, 06, 07.

## Цель
- [ ] Есть общий модуль `integrations/base.py` с базовым классом адаптера и описанием статуса:
  - `ProviderStatus`: `key`, `title`, `mode` (`real` / `demo` / `off`), `configured: bool`, `reason` (понятный текст на украинском: «Не налаштовано: немає OPENDATABOT_API_KEY»), `env_vars` (только имена переменных), `last_success_at`, `last_error_at`, `last_error` (текст без секретов).
  - `BaseProvider`: `key`, `mode`, `is_configured()`, `status()`. Real- и demo-реализации наследуют его.
  - Каждый ответ адаптера содержит `configured` и `demo`. В режиме `off` (или `real` без ключа) ответ не содержит фейковых полей данных.
- [ ] Единое правило выбора реализации — одна переменная `.env` на провайдера, `<ПРОВАЙДЕР>_MODE=auto|real|demo|off`:
  - `auto` (по умолчанию): ключ задан и не является плейсхолдером → `real`, иначе `off` («не налаштовано»).
  - `demo`: demo-реализация, каждый ответ с `demo: true`. Нужна для dev, e2e и показа.
  - `real` без ключа → статус «помилка конфігурації», ответы `configured: false`, сайт не падает.
  - `off` → провайдер выключен.
  - Для провайдеров без ключа (НБУ, NHTSA) `auto` = `real`.
- [ ] Плейсхолдеры считаются «не настроено» (03-C1): пустая строка и значения вида `your_*`, `your-*`, `changeme`, `xxx`, `<...>`. Проверка сделана одной функцией `is_placeholder(value)` в каркасе.
- [ ] В `.env.example` ключи LiqPay, Opendatabot и Apify пустые или закомментированы (03-C1). Добавлены строки `*_MODE` со значением `auto` и комментарием на украинском.
- [ ] Реестр провайдеров `integrations/registry.py` знает все 8 ключей: `nbu`, `vin_decode` (NHTSA), `vin_report` (carVertical), `opendatabot`, `lots` (Apify/ручной ввод), `liqpay`, `email` (SMTP), `telegram`. Пока провайдер не переведён на адаптер (это задачи 3.2–3.4), его статус считается по настройкам `settings`, без вызова внешнего API.
- [ ] **Расширяемый реестр (ANSWERS, шаг 8):** реестр не фиксирован на 8 ключах. Адаптер регистрирует себя сам: декоратор/функция `register_provider(key, title, status_fn, env_vars, checklist_anchor)` в `integrations/registry.py`, вызывается из модуля самого адаптера (при `AppConfig.ready()`). Базовые 8 ключей регистрируются здесь, остальные добавляют свои задачи: капча (`captcha`, Turnstile, 1.6), мониторинг (`monitoring`, Sentry/ошибки, 7.6), хранилище (`storage`, S3/медиа, 7.2), аналитика (`analytics`, GA4), пиксели (`pixel_meta`, `pixel_tiktok`) — все видны на странице статуса. Отсутствие регистрации не ломает страницу; дубликат ключа → понятная ошибка при старте.
- [ ] Журнал здоровья: модель `IntegrationHealth` (`provider_key` unique, `last_success_at`, `last_error_at`, `last_error` до 500 символов, `error_count`). Её обновляет общий хелпер `record_success(key)` / `record_error(key, exc)`. В `last_error` и в лог секреты не попадают: query-строка URL отрезается, значения ключей из `settings` маскируются.
- [ ] Общие настройки HTTP-вызовов в каркасе: `INTEGRATIONS_HTTP_TIMEOUT` (секунды, по умолчанию 10) и кортеж ретраябельных сетевых исключений `RETRYABLE_EXCEPTIONS` (исключения `httpx.TransportError`, `urllib.error.URLError`, `OSError`). Задачи 3.2–3.4 используют их вместо своих констант (03-C9).
- [ ] Страница админки «Статус інтеграцій» (`/admin/integrations/status/`) доступна только `is_staff` с правом `integrations.view_integrationhealth`. На ней таблица по всем 8 провайдерам: название, режим, настроен ли, причина, имена переменных `.env`, последний успех, последняя ошибка, ссылка на раздел `docs/LAUNCH_CHECKLIST.md`. Значения ключей не показываются нигде, даже маскированными (только «задано / не задано / плейсхолдер»).
- [ ] На главной странице админки есть ссылка на статус интеграций. Если хотя бы один провайдер в `real` без ключа или с ошибкой за последние 24 часа, рядом стоит пометка.
- [ ] Django system check (`manage.py check`): предупреждение `integrations.W001`, если провайдер в `real` без ключа, и `integrations.W002`, если при `DEBUG=False` какой-либо провайдер в `demo`. Ошибок `check` не вызывает: сайт должен стартовать.

## Шаги
1. Написать `integrations/base.py`: `ProviderStatus` (dataclass), `BaseProvider`, `is_placeholder()`, `resolve_mode(key, has_credentials, needs_credentials=True)`, `mask_secrets(text)` (переиспользовать хелпер из 1.1), `RETRYABLE_EXCEPTIONS`, `record_success` / `record_error`.
2. Добавить в `core/settings.py` переменные `NBU_MODE`, `VIN_DECODE_MODE`, `VIN_REPORT_MODE`, `OPENDATABOT_MODE`, `LOTS_MODE`, `LIQPAY_MODE`, `EMAIL_MODE`, `TELEGRAM_MODE` (все по умолчанию `auto`) и `INTEGRATIONS_HTTP_TIMEOUT`. Недопустимое значение → system check-ошибка с понятным текстом. Это единственный случай, когда `check` падает: опечатка в `.env`.
3. Написать `integrations/registry.py` со словарём `key → функция статуса`. Для каждого из 8 провайдеров статус пока считается по `settings`: какие переменные нужны, заданы ли, не плейсхолдер ли. Например, `email` настроен, если `EMAIL_BACKEND` — smtp и заданы `EMAIL_HOST` и `DEFAULT_FROM_EMAIL`. `telegram` показывает отдельными строками токен, канал, B2B-канал и секрет webhook (07-C5 — сам статус Telegram доделывает 3.4).
4. Модель `IntegrationHealth` и миграция. **Причина изменения схемы:** админу нужно видеть время последнего успеха и последней ошибки провайдера (бриф §2, 03-C5). Из `settings` это не вычислить, а логи админ не читает.
5. Кастомный view в админке через `AdminSite.get_urls` (или `ModelAdmin.get_urls` у `IntegrationHealthAdmin`) и шаблон страницы статуса. Сама `IntegrationHealth` в админке только для чтения: без добавления, изменения и удаления.
6. `integrations/checks.py`: зарегистрировать checks W001, W002 и ошибку недопустимого режима.
7. Поправить `.env.example`: пустые ключи, строки `*_MODE=auto` с комментариями. В `.env.docker.example` добавить `*_MODE`. Полную сверку шаблонов делает 7.7, здесь только интеграционные разделы.
8. Создать или дополнить `docs/LAUNCH_CHECKLIST.md` разделом «Інтеграції»: общая схема `*_MODE`, где смотреть статус. Подробности по каждому провайдеру допишут 3.2–3.4.
9. Адаптеры провайдеров не должны глотать исключение сетевого предохранителя `ExternalNetworkBlocked` (`core/test_runner.py:16`, наследник `RuntimeError`): в `BaseProvider` и во вспомогательных обёртках вызовов не ловить его широким `except Exception` (03-Q12) — либо ловить узкие `RETRYABLE_EXCEPTIONS`, либо перевыбрасывать (`except ExternalNetworkBlocked: raise` перед широким обработчиком). `record_error` для него не вызывать. Иначе тест без мока провайдера пройдёт «зелёным» с ответом-ошибкой.
10. Тесты (см. ниже). Прогон `DATABASE_URL= REDIS_URL= .venv/Scripts/python.exe manage.py test`, затем Playwright из `frontend/`.

## Тесты
Django (`integrations/tests.py`, все внешние вызовы замоканы):
- `is_placeholder`: `''`, `your_opendatabot_api_key`, `your-key`, `changeme` → True; реальная строка вида `a1b2c3...` → False.
- `resolve_mode`: `auto` + ключ → `real`; `auto` + плейсхолдер → `off`, `configured: false` (03-C1); `demo` → `demo`; `real` без ключа → `configured: false` и причина «помилка конфігурації»; `auto` для провайдера без ключа (`nbu`) → `real`. Часть контракта 23-D66, остальное — в 3.2–3.4.
- Реестр: для каждого из 8 ключей `status()` возвращается без исключений при пустом окружении (`override_settings` со всеми ключами пустыми). Ни в одном статусе нет значения ключа, только имена переменных.
- `record_error` с исключением, текст которого содержит `?apikey=SECRET123` и значение `settings.OPENDATABOT_API_KEY` → в `IntegrationHealth.last_error` и в логе (`assertLogs`) нет `SECRET123`.
- Расширяемость: тестовый адаптер, зарегистрированный через `register_provider`, появляется на странице статуса без правки реестра; повторная регистрация того же ключа → ошибка; статус незарегистрированного набора (только базовые 8) строится без исключений.
- Страница статуса (23-D67): superuser → 200, в HTML есть все зарегистрированные названия (базовые 8 как минимум). `is_staff` без права → 403. Обычный пользователь → редирект на логин админки (302). Аноним → 302.
- System checks: `LIQPAY_MODE=real` без ключа → в `run_checks()` есть `integrations.W001`; `DEBUG=False` + `NBU_MODE=demo` → `W002`; `NBU_MODE=foo` → ошибка.
- Модель `IntegrationHealth` в админке: add, change и delete запрещены (POST на add → 403).
- Сетевой предохранитель не проглатывается: тестовый адаптер на каркасе `BaseProvider` делает реальный сетевой вызов (мок провайдера убран) → тест падает с `ExternalNetworkBlocked` и сообщением «Внешний сетевой запрос в тесте: <host>:<port>. Замокайте провайдер»; адаптер не возвращает dict с ошибкой, `IntegrationHealth` не обновляется.

Playwright (`frontend/e2e/integrations-status.spec.ts`, 23-P27; запускать только из `frontend/`, e2e-окружение с пустыми ключами):
- Успех: вход в `/admin/` под суперпользователем из фикстуры задачи 0.4 → ссылка «Статус інтеграцій» → таблица минимум из 8 строк (плюс зарегистрированные другими задачами), у Opendatabot статус «Не налаштовано» и имя переменной `OPENDATABOT_API_KEY`, значения ключа на странице нет.
- Ошибка или обход: обычный пользователь (buyer) открывает `/admin/integrations/status/` → страница входа админки, таблицы нет.
