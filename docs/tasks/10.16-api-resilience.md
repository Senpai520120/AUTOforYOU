# Задача 10.16: Устойчивость API

## Контекст
Источник: `docs/audit/41_REVIEW_2026-11-11.md`, находки E3 и G.
- NUL-байт (`%00`) в query публичных GET (`local/cities/?q=`, фильтры каталога): PostgreSQL отвергает `\x00` в строках, ответ 500.
- Throttle заявки (`leads/views.py`, scope `lead`) и калькулятора (`pricing/views.py`, scope `calculator`) ходит в Redis через `ScopedRateThrottle`; недоступный Redis даёт 500.
- `serverGet` (`frontend/lib/server-api.ts`) без таймаута: медленный бэкенд вешает рендер. `/api/v1/site-settings/` запрашивают по отдельности `CookieBanner`, `AnalyticsLoader`, `PartnerVinLink`, `use-site-config`, `FallbackContact`, `LeadForm`.

## Цель
- Любой query-параметр с NUL (`\x00` или `%00`) в любом запросе: 400 `{"detail": ...}`, одним общим middleware.
- Redis недоступен: заявка (201) и расчёт (201) проходят, в логе `warning` без ПДн, владельцу один алерт в час на процесс.
- `serverGet` / `serverGetAuthed` прерываются через 5 с (`SERVER_FETCH_TIMEOUT_MS`), результат `null`, страница рендерится.
- На сервере один запрос `site-settings` за рендер; на клиенте один за загрузку страницы (`/calculator`).

## Решение владельцу (допущение, можно поменять)
**Fail-open** при недоступном кэше для throttle заявки и калькулятора: запрос пропускается. Основания: заявку по-прежнему защищают капча и идемпотентность (10.13); отказ клиенту из-за сбоя Redis дороже, чем временно снятый лимит. Остальные throttle (вход, телефоны, письма) НЕ затронуты и остаются строгими. Чтобы изменить: в `leads/views.py` и `pricing/views.py` вернуть `ScopedRateThrottle`.
Алерт: `core.tasks._send_failed_task_alert`; дедуп файлом-маркером в `tempfile.gettempdir()` по mtime (Redis лежит), не чаще раза в час на контейнер (остаток: контейнеров несколько, значит алертов до их числа в час).
Ошибки кэша: `core.throttles.cache_errors()` включает `django_redis.exceptions.ConnectionInterrupted`: так `DefaultClient` оборачивает сбой Redis в проде.
**Капча НЕ fail-open.** Honeypot-капча гасит одноразовый nonce в кэше; без Redis `require_captcha` кидает ошибку кэша. Вместо 500 заявка отвечает 503 «Тимчасово недоступно, спробуйте пізніше» (`LeadForm` на 503 показывает `FallbackContact`, 10.7), лог без ПДн и алерт. Итог: при включённой капче и упавшем Redis заявки не принимаются, посетитель видит запасной контакт. Решение владельца: оставить так.
Не сделано: NUL в пути URL и в теле запроса (только query).

## Шаги
1. `NulByteQueryMiddleware` (после CORS, до остального): NUL в `QUERY_STRING` -> 400.
2. `FailOpenScopedRateThrottle` в `core/throttles.py`; подключить в заявке и калькуляторе.
3. `serverGet`: `AbortSignal.timeout`; поскольку fetch с `signal` Next не мемоизует, дедуп через `React.cache`; `getSiteSettings` с единым revalidate.
4. Клиент: `fetchSiteSettings()` (общий промис, TTL 60 с, ошибка не кешируется, `force` для «Спробувати ще раз»).
