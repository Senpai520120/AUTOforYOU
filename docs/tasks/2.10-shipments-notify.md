## Контекст
Сценарий 5 из `docs/audit/20_SCENARIOS.md` («Контейнер: создание → смена статусов → уведомления клиенту») проходит до шага 3. Шага 4 (уведомление) нет.

- **04-Q2** (важно): смена статуса контейнера не проверяется и ни о чём не уведомляет.
  - Граф переходов `Shipment.VALID_TRANSITIONS` (`shipments/models.py:17-25`) и метод `advance_status()` (`:65-75`) нигде не вызываются, это мёртвый код.
  - Статус меняется только в админке. `ShipmentAdmin.save_model` (`shipments/admin.py:26-33`) пишет любой статус без проверки, в том числе назад и через шаг, и создаёт `TrackingEvent`.
  - При создании контейнера начальное событие не пишется: условие `if change and ...`, `:29`.
  - Inline `TrackingEventInline` (`shipments/admin.py:7-11`, `extra = 1`) позволяет вручную добавить событие с произвольным статусом. Вместе с авто-событием получается дубль.
  - Уведомлений клиенту нет вообще. В `Notification.Type` нет типа для контейнера (`notifications/models.py:6-15`). В `notifications/`, `telegram_bot/`, `integrations/` нет упоминаний `Shipment`.
  - Готовые механизмы уведомлений: in-app — `notifications.services.create_notification` (`notifications/services.py:4-12`), Telegram — Celery-задача `integrations.tasks.send_notification` (`integrations/tasks.py:47-104`).
- **20-G3** (важно): клиента к контейнеру привязывают только вручную, через `filter_horizontal = ('vehicles', 'watchers')` (`shipments/admin.py:19`, поле `Shipment.watchers` — `shipments/models.py:47-50`). Связи с заявкой, сделкой или расчётом клиента нет. Уведомления «ваше авто добавлено в контейнер» нет. Клиенту в кабинете написано «Зверніться до менеджера щоб додати контейнер» (`frontend/app/me/shipments/page.tsx:49`).
- Желательные находки того же места, берутся в задачу:
  - **09-Q18 / 08-Q6 (частично)**: в `/me/shipments` запрос `meApi.shipments().then(...).finally(...)` без `catch` (`frontend/app/me/shipments/page.tsx:34`), ошибка выглядит как пустой список;
  - **04-Q9**: нет истории событий. API деталей `shipments/views.py:51` фронт не использует. Порт выводится сырым кодом.
  - **04-Q5**: N+1 в админке: `vehicle_count` → `obj.vehicles.count()` (`shipments/admin.py:22-23`).
- Вне задачи: приватные tracking-фото и EXIF (04-S4, задача 1.10); роль broker (01-S7, задача 1.2); дубль `MyShipmentsView`/`ShipmentListView` (04-Q4, желательно, не берём).

## Цель
- [ ] **04-Q2**: единственный путь сменить статус — сервис `shipments.services.change_status(shipment, new_status, *, actor, note='', photo=None)`. Он проверяет `VALID_TRANSITIONS`, работает в `transaction.atomic`, пишет ровно один `TrackingEvent` и ставит уведомления через `transaction.on_commit`. Недопустимый переход → исключение `InvalidTransition`, статус и события не меняются.
- [ ] **04-Q2**: админка вызывает сервис.
  - Недопустимый переход в форме → ошибка валидации у поля «Статус», без 500.
  - Создание контейнера пишет начальное событие.
  - Inline событий только для чтения: статус нельзя задать вручную, но можно добавить комментарий или фото к событию через действие или сервис. Дублей нет.
  - `advance_status()` в модели либо удалён и заменён сервисом, либо стал тонкой обёрткой над сервисом. Мёртвого кода нет.
- [ ] **04-Q2**: при смене статуса каждый watcher получает:
  - in-app `Notification` типа `SHIPMENT_STATUS` со ссылкой `/me/shipments`, заголовком «Контейнер <номер>: <статус>» и ETA;
  - Telegram-сообщение через `send_notification`, если аккаунт привязан.
  Без токена бота или без привязки — молчаливый пропуск с записью в лог, как сейчас, без ПДн. Письмо на email отправляется, если в проекте уже есть почтовый механизм (1.6/1.7). Иначе email не делается, и это записано в `PROGRESS.md`.
- [ ] **20-G3**: добавление пользователя в `watchers` любым путём (админка, сервис `add_watchers`) создаёт уведомление `SHIPMENT_ADDED` «Ваше авто додано до контейнера <номер>» (in-app + Telegram). Повторное добавление того же пользователя не шлёт второе уведомление.
- [ ] **20-G3** (если задача 2.1 выполнена): из заявки брокеру (модель `Lead` из 2.1) в админке есть действие «Додати клієнта до контейнера». Оно вызывает `add_watchers`. Если заявка гостевая, без аккаунта, действие показывает сообщение «Клієнт не зареєстрований — надішліть запрошення» и ничего не создаёт: аккаунт автоматически не заводится. Если 2.1 ещё не сделана, эта часть переносится (см. «Примечание для ROADMAP»).
- [ ] `/me/shipments`:
  - ошибка API показывается как ошибка, а не как пустой список;
  - у контейнера раскрывается история событий из `GET /api/v1/shipments/<id>/` (статус, дата, комментарий);
  - порт выводится подписью (`arrival_port_eu_display`), а не кодом.
- [ ] Права: менять статус и watchers в админке может staff или роль broker (1.2). Клиентское API остаётся только для чтения.

## Шаги
1. `shipments/services.py`:
   - `InvalidTransition(Exception)`;
   - `change_status(...)`: `select_for_update`, проверка `can_transition_to`, `save(update_fields=['status','updated_at'])`, `TrackingEvent.objects.create(...)`, затем `transaction.on_commit(lambda: notify_status_changed(shipment.pk, event.pk))`;
   - `add_watchers(shipment, users, *, actor)`;
   - `notify_status_changed` / `notify_watcher_added`: `create_notification` + `send_notification.delay(user_id, text, buttons=[{'text': 'Відкрити', 'url': f'{SITE_URL}/me/shipments'}])`.
   Базовый URL сайта брать из `settings.SITE_URL` (`core/settings.py:414`, `.env` `SITE_URL`), без хардкода домена. Тексты — в одном месте сервиса.
2. `shipments/signals.py`: `m2m_changed` на `Shipment.watchers.through`, `action == 'post_add'` → `on_commit` → `notify_watcher_added` только для новых `pk_set`. `post_add` и так приходит только с реально добавленными pk. Подключить в `ShipmentsConfig.ready()`.
3. `ShipmentAdmin`:
   - `ModelForm.clean_status` проверяет переход относительно сохранённого значения;
   - `save_model`: при изменении статуса вызывает сервис (статус из формы не сохранять напрямую), при создании пишет начальное событие;
   - `TrackingEventInline`: `extra = 0`, `can_delete = False`, `readonly_fields` на `status`, `created_at`;
   - `vehicle_count` через `annotate(Count('vehicles'))` в `get_queryset` (04-Q5).
   Права broker — через Django permissions группы/роли из 1.2.
4. `advance_status()` — сделать обёрткой над `change_status` или удалить, проверив grep, что он нигде не вызывается.
5. Новые значения `Notification.Type` + миграция. Поле `type` имеет `max_length=30`: названия типов проверить на длину.
6. Действие для заявок (при наличии 2.1): промежуточная форма выбора контейнера → `add_watchers([lead.user])`.
7. Фронт `/me/shipments`: `catch` → состояние ошибки; раскрытие истории с запросом деталей по клику; подпись порта. Если в `/me/shipments` используются `useSearchParams`, обернуть в `Suspense`.
