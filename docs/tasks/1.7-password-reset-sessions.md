# Задача 1.7: Сброс и смена пароля, отзыв всех сессий

## Контекст
- **01-S3** (важно): в `users/urls.py:25-36` нет ни сброса, ни смены пароля, ни отзыва всех сессий. `UserProfileSerializer` не содержит пароля (`users/serializers.py:40-58`). `LogoutView` (`users/views.py:25-37`) отзывает только один переданный refresh.
- **08-S5** (важно): на фронте нет ссылки «Забули пароль?» (`frontend/app/login/page.tsx:49-51` — есть только «Немає акаунту? Реєстрація»), нет страниц сброса, в кабинете `frontend/app/me/page.tsx:17-28` нет раздела безопасности и кнопки «Вийти на всіх пристроях».
- **01-Q1** (важно): таблицы `token_blacklist` (`OutstandingToken`/`BlacklistedToken`) растут бесконечно: при `ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION` (`core/settings.py:347-351`) каждый refresh — новая строка, а в `CELERY_BEAT_SCHEDULE` (`core/settings.py:373-393`) нет `flushexpiredtokens` и `clearsessions`.
- Связанная желательная **01-S12**: бан в админке (`users/admin.py:8-21`) не отзывает refresh-токены — закрывается тем же сервисом отзыва сессий.
- Access-токен живёт 15 минут (`core/settings.py:348`). Blacklist работает только для refresh, поэтому без отдельной метки «токены до момента X недействительны» украденный access продолжает работать до истечения.
- Отправка писем: `EMAIL_BACKEND` по умолчанию console (`core/settings.py:335-338`), `DEFAULT_FROM_EMAIL` из `.env` (`core/settings.py:344`). Адрес сайта для ссылок в письмах — `SITE_URL` (`core/settings.py:414`, дефолт — реальный домен, это 01-C6, чинится в 7.7).
- Требование брифа §3: «сброс пароля по email (ссылка одноразовая, с ограниченным сроком), смена пароля в кабинете, отзыв всех сессий при смене».
- После задач 1.3/1.4 JWT живут в httpOnly-cookie, есть собственный класс аутентификации по cookie и хелперы установки/очистки cookie — эта задача их переиспользует.

## Цель
- [ ] `POST /api/v1/auth/password-reset/` `{email}` — всегда 200 с одинаковым текстом, существует аккаунт или нет. Если существует и активен — уходит письмо со ссылкой `{SITE_URL}/password-reset/confirm?uid=…&token=…`.
- [ ] Ссылка одноразовая (Django `PasswordResetTokenGenerator`: после смены пароля токен становится недействительным) и истекает через `PASSWORD_RESET_TIMEOUT` секунд из `.env` (по умолчанию 3600).
- [ ] `POST /api/v1/auth/password-reset/confirm/` `{uid, token, new_password, new_password2}` — проверка валидаторами `AUTH_PASSWORD_VALIDATORS`, 400 на неверный или просроченный токен с нейтральным текстом, после успеха — отзыв всех сессий.
- [ ] `POST /api/v1/auth/password-change/` (IsAuthenticated) `{old_password, new_password, new_password2}` — неверный старый пароль → 400; после успеха отзываются все сессии, текущему устройству выдаётся новая пара cookie.
- [ ] `POST /api/v1/auth/logout-all/` (IsAuthenticated) — отзывает все сессии пользователя, включая текущую, и очищает cookie.
- [ ] Единый сервис `users/services.py: revoke_all_sessions(user)`: все `OutstandingToken` пользователя → `BlacklistedToken`, поле `CustomUser.tokens_valid_after = now()`. Класс аутентификации из 1.3 отклоняет access-токен с `iat` < `tokens_valid_after` (401).
- [ ] Бан в админке (`users/admin.py:8-21`) вызывает `revoke_all_sessions` (01-S12).
- [ ] Отдельный throttle-scope `password_reset` (`THROTTLE_PASSWORD_RESET_RATE`, по умолчанию `5/hour`) на запрос сброса и подтверждение.
- [ ] Celery beat: ежедневно `flushexpiredtokens` и `clearsessions` (01-Q1).
- [ ] Фронт: ссылка «Забули пароль?» на `/login`; страницы `/password-reset` и `/password-reset/confirm`; раздел `/me/security` со сменой пароля и кнопкой «Вийти на всіх пристроях»; пункт меню в `/me`. Тексты на украинском, ошибки сервера показываются текстом.
- [ ] Письмо сброса — на украинском, без хардкода домена и отправителя (только `SITE_URL`, `DEFAULT_FROM_EMAIL`).

## Шаги
1. Миграция `users`: `CustomUser.tokens_valid_after = DateTimeField(null=True, blank=True)`. Причина: blacklist SimpleJWT действует только на refresh, а бриф требует отзыва всех сессий сразу, включая живой access.
2. `users/services.py`: `revoke_all_sessions(user)` — `BlacklistedToken.objects.get_or_create` для каждого `OutstandingToken(user=user)`, затем `tokens_valid_after=timezone.now()`. В классе аутентификации (1.3) сравнивать `token['iat']` с `user.tokens_valid_after`.
3. Сериализаторы: `PasswordResetRequestSerializer`, `PasswordResetConfirmSerializer` (uid через `urlsafe_base64_decode`, `default_token_generator.check_token`, `validate_password(new, user)`), `PasswordChangeSerializer` (`check_password(old)`).
4. Views: `PasswordResetRequestView` (AllowAny, одинаковый ответ, письмо только активному пользователю; ошибки SMTP логировать без email, клиенту — тот же 200), `PasswordResetConfirmView` (AllowAny), `PasswordChangeView` и `LogoutAllView` (IsAuthenticated). Явные `permission_classes` и `throttle_scope`. URL — kebab-case.
5. `core/settings.py`: `PASSWORD_RESET_TIMEOUT = int(os.environ.get('PASSWORD_RESET_TIMEOUT', '3600'))`; `'password_reset': os.environ.get('THROTTLE_PASSWORD_RESET_RATE', '5/hour')`; в `CELERY_BEAT_SCHEDULE` — `users.tasks.flush_expired_tokens` раз в сутки (задача вызывает `call_command('flushexpiredtokens')` и `call_command('clearsessions')`).
6. `users/admin.py`: в `ban_users` после бана — `revoke_all_sessions(user)`.
7. Фронт: формы с `useState`, отправка через клиент из 1.4 (cookie + CSRF). После смены пароля — сообщение «Пароль змінено, інші пристрої вийшли з акаунту». После logout-all — очистка контекста и переход на `/login`. `/me/security` — client-страница с noindex в `me/layout.tsx` (уже есть).
8. `.env.example`: `PASSWORD_RESET_TIMEOUT`, `THROTTLE_PASSWORD_RESET_RATE` с комментарием.
9. Перегенерировать `openapi.yaml` (только против Postgres).

## Тесты
Django (`users/tests.py`, почта — `locmem`):
- 23-D25: сброс для существующего email → 200 и 1 письмо со ссылкой на `SITE_URL`; для несуществующего → 200 с тем же телом и 0 писем; неактивный/забаненный → 0 писем.
- Подтверждение с валидным токеном → 200, вход новым паролем работает; повторное использование той же ссылки → 400; просроченный токен (`override_settings(PASSWORD_RESET_TIMEOUT=1)` + сдвиг времени) → 400; слабый новый пароль → 400; `new_password2` не совпадает → 400.
- 23-D26: смена пароля без cookie → 401; неверный старый пароль → 400; успех → все прежние refresh в blacklist (`POST token/refresh/` со старым → 401), старый access → 401, новая пара cookie работает.
- `logout-all`: аноним → 401; после вызова все refresh пользователя отозваны, cookie очищены; сессии другого пользователя не затронуты.
- Бан через admin-action → refresh забаненного → 401 (23-D32, 01-S12).
- Throttle: `override_settings` со scope `password_reset: '2/min'` → третий запрос 429.
- Задача `flush_expired_tokens` вызывает обе команды (мок `call_command`), задача есть в `CELERY_BEAT_SCHEDULE`.
Playwright (`frontend/e2e/password.spec.ts`, фикстуры авторизации из 0.4):
- 23-P10 успех — «Забули пароль?» → email → письмо перехватывается (Mailpit в e2e-стеке, если его не добавила 0.4 — добавить сервис в профиль e2e `docker-compose.yml`) → ссылка → новый пароль → вход. Ошибка/обход — повторное открытие той же ссылки и искажённый токен → понятное сообщение, пароль не меняется.
- 23-P11 успех — смена пароля в `/me/security`, вход с новым паролем. Обход — второй контекст браузера того же пользователя после смены выброшен на `/login`; неверный старый пароль → текст ошибки.
