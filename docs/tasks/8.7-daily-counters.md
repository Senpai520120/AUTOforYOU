# Задача 8.7: Собственные дневные счётчики без ПДн (`DailyMetric`)

> Источник: Н-41a (`docs/audit/38_PARITY_O_P.md`, P1.2, P1.4, O2.x; ANSWERS, шаги 4 и 8: сбор событий с первого дня, без согласия, без персональных данных; `docs/audit/32_NEW_TASKS_INDEX.md`). Волна: [ВОЛНА-1]. Оценка: 1 сессия. Security-reviewer не обязателен (данные агрегированы, ПДн не пишутся; проверяется тестом). Дашборд, графики, конверсии и выручка — этап 9 (9.32), здесь только сбор и просмотр таблицы в админке.

## Контекст
- Анонимные расчёты удаляются по сроку `ANON_CALCULATION_TTL_DAYS` (2.6, шаг 5: `pricing/tasks.py: purge_anonymous_calculations`), поэтому число расчётов и заявок по дням потом не восстановить. Конверсию «расчёт → заявка» можно считать, только если счётчики ведутся с первого дня.
- Точки событий в коде: расчёт — `CalculateView` после `Calculation.objects.create(...)` (`pricing/views.py:328-336`); регистрация — `RegisterView` / `RegisterSerializer.create` (`users/views.py:41-44`, `users/serializers.py:33-37`); заявка — `leads/services.py: create_lead` (2.1); подача объявления — `LocalListingListCreateView` (`local_listings/views.py:124`) и переход в `pending` (4.2); показ телефона — `LocalListingContactView` (`local_listings/views.py:364-378`, журнал и лимиты 4.5). Визиты калькулятора — только на фронте (`frontend/app/calculator/page.tsx`), серверного события нет.
- 4.5 хранит журнал показов телефона (`ContactView`, 90 дней) отдельно; он нужен для антифрода и не заменяет счётчик. 8.8 (события объявлений) пишет по тому же конвейеру `record_metric`; здесь только общий конвейер.
- Принцип проекта: ничего не хранить без нужды (бриф §3). Счётчики — целые числа по дню и ключу, без user, IP, URL, user-agent и любых идентификаторов. Согласие не требуется, потому что нет ни cookie, ни ПДн.
- Throttle-настройки в проекте задаются через `DEFAULT_THROTTLE_RATES` с чтением из `.env` (`core/settings.py:233-238`). `core` — не приложение (`CLAUDE.md`), поэтому нужно новое приложение `metrics`. Расписание: `CELERY_BEAT_SCHEDULE` (`core/settings.py:373`).

## Цель
- [ ] Новое приложение `metrics` с моделью `DailyMetric` (`date`, `key`, `value` — большое целое; уникальность `(date, key)`). `key` — module-level `TextChoices` `MetricKey`: `calculator_visit`, `calculation`, `lead`, `registration`, `listing_submitted`, `phone_view`, `mobile_bar_click`. Добавление новых ключей — одной строкой (задача 8.8 и этап 9 расширяют перечень).
- [ ] Единая точка записи `metrics.services.record_metric(key, amount=1, day=None)`: атомарный инкремент (`F()`), создаёт строку при первом событии, не падает при гонке, использует день по `Europe/Kyiv` (`timezone.localdate()`), **не принимает ни одного идентификатора** кроме ключа. Вызывается через `transaction.on_commit`, чтобы откатившаяся операция не засчитывалась. Любая ошибка внутри логируется (без данных) и **никогда** не ломает бизнес-операцию.
- [ ] Серверные хуки: после создания `Calculation` (`calculation`), после регистрации (`registration`), после создания заявки (`lead`), после создания объявления (`listing_submitted`), после успешного показа телефона (`phone_view`, включая гостей). Расчёт считается при создании, а не при очистке, поэтому очистка 2.6 счётчик не уменьшает.
- [ ] Публичный `POST /api/v1/metrics/event/` (`AllowAny`, явный `permission_classes`) с телом `{"key": "calculator_visit"|"mobile_bar_click"}`: принимает **только** эти два ключа (whitelist), любые другие и лишние поля отбрасываются с 400/204; отдельный throttle scope `metrics_event` (ставка из `.env`). Ответ 204, тело пустое. IP и user-agent не сохраняются, в логи не пишутся.
- [ ] Фронт: хелпер `frontend/lib/metrics.ts` (`sendMetric(key)`, fire-and-forget, ошибки глушатся). Визит калькулятора считается один раз за вкладку/сессию (флаг в `sessionStorage`, без cookie), страница `/calculator` вызывает его при первом показе. Для `mobile_bar_click` хелпер вызывает 6.6.
- [ ] Админка `DailyMetricAdmin`: таблица только для чтения (add, change, delete запрещены), фильтры по ключу и дате; доступна admin/superuser, `moderator` и `broker` её не видят. Строки не чистятся (агрегаты без ПДн).
- [ ] Ручная пересборка не нужна; страница-дашборд и графики не входят (9.32).

## Шаги
1. Приложение `metrics`, модель и миграция (причина: нужны счётчики по дням с первого дня, а исходные события — расчёты, визиты — не сохраняются или удаляются).
2. `record_metric`: `get_or_create` с последующим `update(value=F('value') + amount)`; при `IntegrityError` повторить обновление. Тест на гонку (два потока или последовательный вызов после искусственного `IntegrityError`).
3. Публичный эндпоинт с сериализатором-whitelist, throttle, `permission_classes=[AllowAny]`, `authentication_classes=[]`, чтобы не требовать CSRF и не тащить сессии.
4. Хуки на сервере через `transaction.on_commit`; в `phone_view` учитываются и гости (4.5).
5. Фронт: `metrics.ts`, вызов при открытии `/calculator`, единичность за сессию.
6. Админка и права, `CLAUDE.md`.

## Тесты
Django (`metrics/tests.py`, `pricing/tests.py`, `users/tests.py`, `local_listings/tests.py`; `captureOnCommitCallbacks(execute=True)`):
- `record_metric` три раза за день → одна строка со значением 3; новый день → новая строка; день берётся по `Europe/Kyiv` (граница полуночи).
- Исключение внутри `record_metric` (мок БД) не ломает бизнес-операцию: расчёт, регистрация и заявка проходят, в логах нет телефона, email и IP.
- Расчёт → `calculation +1`; откат транзакции → счётчик не изменился; очистка анонимных расчётов (2.6) значение не уменьшает.
- Регистрация → `registration +1`; заявка (2.1) → `lead +1`; создание объявления → `listing_submitted +1`; показ телефона гостю и авторизованному → `phone_view +1`.
- `POST /metrics/event/` с `calculator_visit` → 204 и +1; с `registration`, `lead`, пустым ключом, списком, лишними полями → ошибка и счётчик не изменился; превышение лимита → 429. Ответ без тела, в таблице нет ни одного поля идентификатора (проверка по `_meta`).
- Админка: add/change/delete → 403, `moderator` и `broker` раздел не видят.
Playwright (`frontend/e2e/metrics.spec.ts`; чтение значений через админ-фикстуру 0.4):
- Успех: открыть `/calculator` в новом контексте → один запрос `POST /api/v1/metrics/event/` с телом `{key:'calculator_visit'}`, без cookie и без идентификаторов; перезагрузка в той же вкладке не отправляет второй; расчёт и отправка заявки увеличивают `calculation` и `lead` на 1.
- Ошибка/обход: бэкенд счётчиков недоступен (`page.route` → 500 или `abort`) → калькулятор и заявка работают без видимых ошибок; ручной `POST` с чужим ключом (`lead`) из браузера отклонён и счётчик не растёт.
