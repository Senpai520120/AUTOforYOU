# Задача 12.4: SSR не должен делить один anon-лимит между всеми посетителями

## Контекст
SSR фронта (Next) ходит в `INTERNAL_API_URL=http://backend:8000` в обход nginx и без `X-Forwarded-For`:
`frontend/lib/server-api.ts` (`fetchJson`, `serverGetAuthed`), `frontend/lib/landings.ts`,
`frontend/app/sellers/[id]/page.tsx`, `frontend/lib/og-card.tsx`.
При `NUM_PROXIES=1` DRF `get_ident` без XFF берёт `REMOTE_ADDR` = IP контейнера фронта. Все посетители и
краулеры делят один счётчик `anon` (60/час; `core/settings.py` ~265, 273, 353–358, 398) → 429 живым людям.

## Цель
- Доказано тестом: на SSR-пути «разные посетители» делят счётчик и получают 429, через nginx — нет.
- Доверенный SSR-запрос считается по реальному IP посетителя в отдельном scope `ssr` (по умолчанию 600/hour).
- Запрос снаружи (через nginx) доверенным стать не может, даже с утёкшим ключом.
- Ключ не задан или короче 32 символов — функция выключена, поведение как раньше.

## Файлы
Изменить: `core/settings.py` (`SSR_INTERNAL_KEY`, `THROTTLE_SSR_RATE`, класс троттла, `if _TESTING:`),

## Шаги
1. Проверка: Django-тест-доказательство. `NUM_PROXIES=1`, низкая ставка anon через override. N «посетителей» по
   SSR-пути (одинаковый REMOTE_ADDR фронта, без XFF) — следующий получает 429. Те же «посетители» через
   nginx-путь (разный XFF) — каждый проходит.
2. Backend: `SSR_INTERNAL_KEY` из env (пусто или < 32 символов = выключено; в `if _TESTING:` обнулить).
   Middleware: запрос «доверенный SSR» только если `X-SSR-Key` совпал (`hmac.compare_digest`) И нет
   `HTTP_X_FORWARDED_FOR` (nginx всегда ставит XFF). Для доверенного: IP из `X-SSR-Client-IP`
   (валидация `ipaddress.ip_address`, невалидный игнорируется) подставляется в `REMOTE_ADDR`,
   `request.ssr_trusted = True`. Для недоверенного заголовки `X-SSR-*` ни на что не влияют.
3. Троттлинг: наследник `AnonRateThrottle` вместо стандартного в `DEFAULT_THROTTLE_CLASSES`. Доверенный SSR —
   scope `ssr` (`THROTTLE_SSR_RATE`, по умолчанию `600/hour`, пометка «ПРОВЕРИТЬ с владельцем»), бакет по IP
   посетителя. Остальные — обычный `anon`. Scoped-лимиты (calculator и др.) считаются по посетителю через REMOTE_ADDR.
4. nginx: в `proxy-common.conf` сбрасывать входящие `X-SSR-Key` и `X-SSR-Client-IP` (`proxy_set_header ... "";`).
5. Frontend: `SSR_INTERNAL_KEY` в `config.server.ts` (server-only); в `server-api.ts` хелпер `ssrHeaders()`
   (ключ + `x-real-ip` из `next/headers`, ставит nginx; вне request-контекста — без IP, try/catch).
   Применить в `fetchJson`, `serverGetAuthed`, `landings.ts`, `sellers/[id]`, `og-card`.
6. Env: `SSR_INTERNAL_KEY` в сервисы backend и frontend `docker-compose.yml` (`${SSR_INTERNAL_KEY:-}`), в
   `.env.example` и `.env.e2e.example` с комментарием: `python -c "import secrets;print(secrets.token_urlsafe(48))"`.

## Тесты
Django (без сети, данные из `tests/factories.py`):
1. Тест-доказательство (шаг 1).
2. Доверенный SSR с разными `X-SSR-Client-IP` — у каждого свой бакет (scope `ssr`); один посетитель упирается в свой лимит.
3. Подделка снаружи: верный ключ + XFF → не доверенный, `X-SSR-Client-IP` не применяется, считается `anon` по XFF.
4. Неверный ключ / пустой ключ в настройках / короткий ключ → не доверенный, `X-SSR-Client-IP` игнорируется.
5. Невалидный `X-SSR-Client-IP` при верном ключе → `REMOTE_ADDR` не подменён.
6. Ключ выключен — поведение как до задачи.
Мутации: убрать проверку XFF / `compare_digest` → тесты 3/4 красные.
Playwright: новых UI-сценариев нет; существующий smoke-набор должен остаться зелёным (страницы с `headers()` рендерятся).

## Компромисс (записать в PROGRESS)
Заголовки входят в ключ кэша Next fetch, поэтому IP в кэшируемых запросах раздул бы кэш (по записи на каждый IP).
Решение (после ревью безопасности): `ssrKeyHeaders()` — кэшируемые fetch (`fetchJson`, `landings.ts`, `og-card.tsx`)
шлют только `X-SSR-Key`, без IP и без `headers()`; кэш общий. `ssrVisitorHeaders()` (ключ + IP из `x-real-ip`) —
только no-store запросы (`serverGetAuthed`, `sellers/[id]`); вызов `headers()` делает такие страницы динамическими.
Backend: доверенный SSR с валидным IP — scope `ssr` (по посетителю, `THROTTLE_SSR_RATE`, 600/hour); без IP —
scope `ssr_shared` (общий бакет по IP фронта, `THROTTLE_SSR_SHARED_RATE`, 6000/hour, ПРОВЕРИТЬ с владельцем).
Побочный эффект: кэшируемые страницы (каталог, лендинги) по-прежнему считаются общим бакетом, а не по посетителю;
лимит по посетителю действует только на no-store запросы и эндпоинты, к которым ходит клиент (браузер, через nginx).
IP посетителя нормализуется: IPv4-mapped IPv6 -> IPv4, IPv6 -> сеть /64, адрес с `%scope` невалиден.
Нормализация в middleware (REMOTE_ADDR = строка сети): get_ident, аудит (HMAC) и блокировка входа используют адрес
только как ключ. Предупреждение `core.W001`: `NUM_PROXIES>=1` без валидного `SSR_INTERNAL_KEY`.
Sentry: `x-ssr-key` и `x-ssr-client-ip` вырезаются в `core/monitoring.py`. Хвост: автотест конфигурации nginx
(сброс `X-SSR-*`).
