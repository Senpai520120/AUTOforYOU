# Задача 2.18: «Clean» в форме калькулятора и реальные таблицы buyer fee на dev/проде

Источник: проверка владельцем двух лотов Copart 2026-11-08 (dev-стек): 2015 GMC Acadia (лот 63561446, Buy Now $1400, MN) и 2013 Ford Fusion (лот 67506716, Buy Now $5840, NJ). Оба лота Clean.

## Контекст
- `GET /api/v1/pricing/rates/` отдаёт `options.title_types` только `any` и `salvage`. Список строится не во view, а в `pricing/calculator.py:737` (`choice('title_type')` по активным `AuctionFeeTier`, `build_form_options`, стр. 705+). `clean` туда не попадает, если в БД нет активного тира с `title_type='clean'`.
- `CalculateInputSerializer` принимает `clean`; gate fee для clean — `AuctionFixedFee` ($79 против $95 salvage).
- В репозитории уже есть реальные таблицы: `pricing/data/auction_fee_tiers.csv`, `pricing/data/auction_fixed_fees.csv` (Copart, `clean`, сверка 2026-11-06), команды `seed_auction_fees` (`--update`) и `check_fee_tables` (`pricing/management/commands/`).
- Buyer fee $350.40 для $5840 — ровно 6%: это старый placeholder-тир (`any`/`salvage`, процент), а не таблица из CSV. Гипотеза: на dev-БД не выполнен `seed_auction_fees --update`. Проверить, а не принимать на веру.
- Пункты 2 и 5 исходного разбора объединены: причина общая (данные тарифов).

## Проверено 2026-11-08 (основная сессия)
- Гипотеза подтверждена: на dev-стеке `check_fee_tables` даёт 461 расхождение с `pricing/data/*.csv`; в БД есть только `copart any/salvage` и `iaai any`, без `clean`.
- В эталонном CSV у Copart типы участника `public` и `licensed`, а `broker` нет, хотя форма по умолчанию считает с `member_type=broker` (`FORM_DEFAULTS`). Нужно решить, какой тип участника брать по умолчанию и нужна ли таблица для `broker`.
