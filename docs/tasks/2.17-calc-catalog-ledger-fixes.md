# Задача 2.17: Тиры аукционных сборов, дата расчёта, фильтр цены, санитайзер FailedTask (E9, E10, E11, B6-hotfix)

Источник: `docs/audit/SECURITY_AUDIT_2026-10-25.md`, разделы E и B. Агент проверки: `security-reviewer` для E11 (ПДн в учёте упавших задач), остальное — `test-runner`.

## Контекст
- **E9 (недочёт), `pricing/models.py:84`:** перекрывающиеся диапазоны `bid_min..bid_max` у `AuctionFeeTier` проходят `clean()`; применяемый тир решает `pk`. Ошибка владельца в админке молча меняет сумму сбора в расчётах.
- **E10 (недочёт), `pricing/serializers.py:34`:** `calculation_date` не ограничен: гость видит будущие (ещё не вступившие) тарифы.
- **E11 (недочёт), `task_ledger/sanitize.py:17-19`:** короткие строки без пробелов хранятся открыто после `scrub` (токен, IBAN, VIN не маскируются). Сейчас таких аргументов в задачах нет — защита держится на договорённости.
- **B6 (важно), `local_listings/filters.py:42-51`:** `?price_min=abc` → 500 на публичном каталоге `/api/v1/local/listings/` (ловится `ValueError`, а летит `ValidationError`). Каталог открыт уже в ВОЛНЕ-1 (`C2C_ENABLED`), поэтому здесь минимальный hotfix; полная валидация параметров сериализатором и мультивалютность — задача 4.4 (в ней добавлена ссылка).

## Цель
- [ ] **E9:** `AuctionFeeTier.clean()` отклоняет пересечение диапазонов в пределах одного аукциона/периода (`valid_from`/`valid_to`); сообщение на украинском: «Діапазон перетинається з існуючим тиром». Существующие данные не ломаются: проверка при сохранении; management-команда или `check` перечисляет уже существующие пересечения (только вывод).
- [ ] **E10:** `calculation_date` в будущем → 400 `{"calculation_date": ["Дата не може бути в майбутньому"]}`. Нижней границы нет (оценка прошлых расчётов допустима); если владелец захочет «сегодня − N» — отдельное решение (вопрос в QUESTIONS), число не придумываем.
- [ ] **E11:** `sanitize` по умолчанию сохраняет аргумент задачи как `<str:len>` / `<int>`; открыто — только значения из allowlist имён аргументов (`task_ledger/sanitize.py`), allowlist в коде рядом с функцией и в тесте.
- [ ] **B6:** некорректный `price_min`/`price_max` → 400 `{"price_min": ["Некоректне значення"]}` (или `{"detail": ...}` по принятому в 2.8/4.4 формату), не 500. Остальные параметры каталога не меняются.

## Тесты
Django (мутацией проверить каждый):
- **E9:** создание тира, пересекающегося с существующим → `ValidationError`; смежные (`0–999.99`, `1000–…`) допустимы; редактирование существующего тира не конфликтует с самим собой; тиры разных периодов не конфликтуют.
- **E10:** `calculation_date = завтра` → 400, ответ не содержит ставок; сегодня и вчера → 200/422 по обычным правилам; гость (аноним) получает тот же 400.
- **E11:** аргумент задачи — строка-токен без пробелов (`'123456:ABC-DEF…'`), IBAN `UA…`, VIN из 17 символов → в `FailedTask.args` только `<str:N>`; аргумент с именем из allowlist сохраняется как есть; регрессия: существующие тесты ledger зелёные.
- **B6:** `GET /api/v1/local/listings/?price_min=abc` → 400 с ключом `price_min`; `price_max=1e999`/`--` → 400; корректное число → 200; аноним получает 400, не 500.
Playwright: успех — калькулятор считает расчёт на сегодняшнюю дату; ошибка/обход — запрос расчёта с будущей `calculation_date` через `request` → 400; каталог `/ua?price_min=abc` не падает белым экраном (страница показывает каталог или сообщение «Некоректні параметри фільтра»).
