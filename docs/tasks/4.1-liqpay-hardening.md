# Задача 4.1: Платежи LiqPay: подпись, сумма, sandbox, идемпотентность, #24

## Контекст
Платежи есть в двух местах. Общий checkout `POST /api/v1/payments/liqpay/checkout/` (`payments/views.py:66-115`) фронт не вызывает (grep по `frontend/` не находит ни `liqpay/checkout`, ни `payments/`). Checkout продвижения `POST /api/v1/local/listings/<pk>/promote/` (`local_listings/views.py:402-453`) берёт цену из `PromotionTariff`. Оба сценария обслуживает один callback `payments/views.py:133-182`.

Что сейчас в коде:
- **06-S1 (критично):** при пустом `LIQPAY_PRIVATE_KEY` (дефолт `''`, `core/settings.py:302`) подпись равна `base64(sha1('' + data + ''))` (`payments/liqpay_client.py:44-46`). `decode_callback` сравнивает с ней (`payments/liqpay_client.py:98-103`), поэтому любой может собрать «подписанный» callback и перевести платёж в `completed`: бесплатное продвижение или unlock.
- **06-S2 (критично, issue #24):** общий checkout берёт `amount`, `currency`, `purpose` и `listing_id` от клиента (`payments/serializers.py:23-34`). `validate_listing_id` проверяет только существование `Listing` и не проверяет владельца (`payments/serializers.py:41-48`). Во view `Listing.objects.get(pk=...)` берётся без прав (`payments/views.py:83-86`). После оплаты 0.01 callback вызывает `Payment.unlock_listing()` (`payments/views.py:177-178`), и тот переводит **любой** `Listing` в `in_stock` (`payments/models.py:76-79`). Цены для `listing_unlock`/`listing_vip` нет нигде (06-C1), докстринг сериализатора прямо ссылается на #24 (`payments/serializers.py:18-20`).
- **13-S6 (важно):** тесты закрепляют клиентскую сумму: `payments/tests.py:30-35` (`test_valid_payload_creates_pending_payment` проверяет `payment.amount == Decimal('100.00')` из запроса), `tests/test_e2e.py:291-298` (`_checkout()` шлёт `amount: '100.00'` и чужой `listing_id`). На `_checkout()` опираются все тесты класса `TestLiqPayPaymentFlow` (`tests/test_e2e.py:276-399`), включая тесты callback и идемпотентности.
- **06-S3 (важно):** callback не сверяет `amount`, `currency`, `action` из данных LiqPay с `Payment` (`payments/views.py:154-179`).
- **06-S4 (важно):** `map_status` засчитывает `sandbox` как `completed` всегда (`payments/liqpay_client.py:111`), в том числе при `LIQPAY_SANDBOX=false`.
- **06-S7 (важно):** `result_url` и `server_url` задаёт клиент (`payments/serializers.py:33-34`, `payments/views.py:80-81`). Это открытый редирект через LiqPay и возможность увести callback на чужой сервер.
- **06-S8 (важно):** callback без транзакции и `select_for_update` (`payments/views.py:158-179`). Идемпотентность только для `completed→completed` (`:166-169`). Цепочка `completed→failed→completed` применяет тариф повторно (`_apply_local_listing_promote`, `payments/views.py:20-50`). `reversed` меняет статус, но эффект (ТОП, продление, unlock) не откатывает.
- **06-C3 / сценарий 3, шаг 8 (`docs/audit/20_SCENARIOS.md`):** checkout продвижения не передаёт `server_url`/`result_url` (`local_listings/views.py:435-441`). В проде callback придёт, только если URL вручную прописан в кабинете LiqPay, а пользователь не возвращается на сайт. Страницы возврата на фронте нет.
- 10-C1: баннер «Тестовий режим (SANDBOX)» в `frontend/components/local/PromoteModal.tsx:70-74` показывается всегда, даже при `LIQPAY_SANDBOX=false`.
- Желательные того же места: 06-S10 (сравнение подписи через `!=`, `payments/liqpay_client.py:99`), 06-S13 (ответ callback раскрывает текст ошибки подписи и `order_id`, `payments/views.py:149,162`), 06-Q14 (`unlock_listing` в модели, `_apply_local_listing_promote` во views: `payments/models.py:76-79`, `payments/views.py:20-50`).
- Адаптер LiqPay (интерфейс, real/demo, `LIQPAY_MODE`, статус «не налаштовано», 06-C2) делает задача **3.4** на каркасе **3.1**. Здесь используется её провайдер. Если к началу задачи провайдер из 3.4 не даёт признака `is_configured()`, проверку «ключ задан и не плейсхолдер» сделать здесь через `integrations.base.is_placeholder` из 3.1.
- HTTPS (12-S2) делает задача 7.1. Без него внешний POST callback в проде не дойдёт; эта задача только строит правильные URL.

## Цель
- [ ] **06-S2, #24:** общий checkout больше не принимает сумму от клиента. Эндпоинт `payments/liqpay/checkout/` скрыт флагом `PAYMENTS_LEGACY_CHECKOUT_ENABLED` (по умолчанию `false`) и в этом состоянии отвечает 404 без создания `Payment`. Код не удаляется (бриф §6). Если флаг включён, view всё равно игнорирует `amount`, `currency`, `result_url`, `server_url` из запроса, требует, чтобы `listing.seller == request.user` (иначе 403), и принимает только `purpose`, для которых есть серверная цена. В этой задаче таких нет: `listing_unlock`/`listing_vip` → 400 «Серверний прайс для цього призначення не налаштовано». Серверный прайс для них — отдельная задача после решения владельца (см. «Примечание для ROADMAP»).
- [ ] **06-S1:** если LiqPay не настроен (пустой или плейсхолдерный `LIQPAY_PRIVATE_KEY`/`LIQPAY_PUBLIC_KEY`, либо `LIQPAY_MODE=off`), callback отвечает 503 `{"detail": "Оплата не налаштована"}` и не трогает БД; checkout продвижения отвечает 503 с тем же текстом и не создаёт `Payment`. В `demo`-режиме из 3.4 оплата не проводится через liqpay.ua; поведение demo описано в 3.4, но callback с подписью пустым ключом не принимается ни в одном режиме.
- [ ] Подпись сравнивается через `hmac.compare_digest` (06-S10).
- [ ] **06-S3:** callback сверяет `amount` (как `Decimal`), `currency` и `action == 'pay'` с `Payment`. При расхождении — `Payment.status = failed`, `liqpay_raw` сохранён, запись в лог уровня WARNING (без ПДн), эффект не применяется, ответ 200 (чтобы LiqPay не ретраил бесконечно) с нейтральным телом.
- [ ] **06-S4:** статус `sandbox` засчитывается как оплата только при `LIQPAY_SANDBOX=true`. При `false` он даёт `failed` и WARNING в логе.
- [ ] **06-S7, 06-C3:** `server_url` и `result_url` строятся только на сервере: `server_url = {SITE_URL}/api/v1/payments/liqpay/callback/`, `result_url = {SITE_URL}/me/local-listings?payment={order_id}`. Оба передаются и в checkout продвижения. Значения из запроса игнорируются.
- [ ] **06-S8:** обработка callback — в `transaction.atomic()` с `Payment.objects.select_for_update().get(order_id=...)`. Эффект применяется ровно один раз: новое поле `Payment.applied_at`; применяем, только если `applied_at is None`. Переходы `completed→failed`/`completed→pending` не меняют статус оплаченного платежа (только логируются). `reversed` после применения откатывает эффект один раз (новое поле `Payment.reverted_at`): TOP — `promoted_until` уменьшается на `duration_days` тарифа, но не раньше `now`; RENEW — `expires_at` уменьшается на `duration_days`, если результат в прошлом, статус `active→expired`; BUMP — `bumped_at` сбрасывается в значение до оплаты (хранится в `Payment.effect_snapshot`), legacy `listing_unlock` — статус `Listing` возвращается из снимка.
- [ ] Логика эффекта перенесена из views/models в `payments/services.py` (`apply_payment_effect`, `revert_payment_effect`), view только вызывает сервис (06-Q14). `Payment.unlock_listing` остаётся тонкой обёрткой над сервисом, чтобы не ломать импорты.
- [ ] Ответы callback не раскрывают `order_id` и текст ошибки подписи: неверная подпись → 400 `{"detail": "invalid"}`, неизвестный `order_id` → 200 `{"ok": false}` (детали в лог) (06-S13).
