# Задача 6.8: LCP на мобильном ниже 2,5 с (баннер cookie и главная)

## Контекст
Замер 7.7a, сессия 2 (2026-11-03): Lighthouse 12.8.2, mobile, simulated throttling, локальный e2e-стек в Docker на Windows. Оценки 95–100, но цель эталона `docs/MARKETPLACE_STANDARD.md` O6 (LCP < 2,5 с на мобильном) не выполнена ни на одной из страниц:

| Страница | Perf | LCP, мс | LCP-элемент | CLS |
|---|---|---|---|---|
| `/` | 97 (A11y 100, BP 100, SEO 100) | 2530 | `<h1 class="text-4xl font-extrabold mb-3">` | 0 |
| `/calculator` | 96 | 2742 | `<p class="text-sm flex-1">` из `frontend/components/ui/CookieBanner.tsx:69` | 0.002 |
| `/prigon/e2e-toyota-camry` | 95 | 2869 | тот же текст баннера cookie | 0 |
| `/ua` | 96 | 2705 | не зафиксирован | не зафиксирован |

Прочее на `/`: TBT 60 мс, FCP 0,8 с. Превышение небольшое, запуск не блокирует (поэтому [РОСТ], а не [ЗАПУСК]).

Что известно из кода:
- `CookieBanner` подключён в `frontend/app/layout.tsx:53`, рендерится на всех страницах.
- `CookieBanner.tsx:26` читает согласие через `useSyncExternalStore`, серверный снимок `'unknown'` (строка 21), на сервере баннер возвращает `null` (строка 52). Значит, баннер появляется только после гидратации.
- Текст абзаца (строки 69–74) меняется после ответа `GET /api/v1/site-settings/` (эффект на строках 34–48: `hasGa4`, `hasCf`), то есть абзац перерисовывается уже после появления.
- Баннер `fixed bottom-0`, на мобильном занимает заметную часть вьюпорта, поэтому его текст становится самым крупным элементом.

Гипотезы (проверить замером, не принимать на веру):
1. Баннер, появившийся после гидратации, остаётся LCP-кандидатом и сдвигает LCP на момент гидратации.
2. h1 на главной ждёт загрузки шрифта или гидратации; шрифты и `font-display` не проверялись.
3. Локальный Docker на Windows даёт пессимистичные цифры: на реальном сервере цель может выполняться без правок.

Ограничения: Consent Mode (задача 3.5) и поведение согласия из 1.14 ломать нельзя. Пользовательские тексты баннера остаются на украинском и не меняются по смыслу.

## Цель
- LCP < 2,5 с (mobile, Lighthouse) на `/`, `/calculator`, `/prigon/e2e-toyota-camry`, а также `/ua` по замеру на собранном стеке (`npm run build` + запуск, без dev-режима).
- Либо зафиксировано в PROGRESS с цифрами, что на реальном сервере (стенд с прод-сборкой) цель выполнена, а локальное превышение — артефакт замера.
- Баннер cookie не является LCP-элементом ни на одной из трёх страниц, либо его вклад в LCP объяснён и устранён.
- CLS остаётся ≤ 0,1 (сейчас 0–0,002), баннер не вызывает сдвига контента.
- Логика согласия не меняется: показ при отсутствии согласия, повторный показ по версии документов, Consent Mode v2 (3.5), блокировка GA4 до «Прийняти всі».

Не трогать: `frontend/lib/consent*` (логика согласия и Consent Mode), backend, `cars/`, `frontend/e2e/test-1.spec.ts`.

## Шаги
1. Поднять e2e-стек по правилам CLAUDE.md (раздел E2E), снять базовый замер Lighthouse mobile для четырёх страниц, минимум 3 прогона на страницу, брать медиану. Записать в PROGRESS как «до».
2. По отчёту Lighthouse (LCP breakdown: TTFB, load delay, render delay) определить, на чём теряется время на `/` и на баннере.
3. Проверить шрифты: источник, `font-display`, preload. Если шрифт блокирует h1, поправить.
4. Баннер: выбрать минимальное изменение из проверяемых вариантов:
   - уменьшить вклад баннера в LCP (меньший по площади текстовый блок, компактная вёрстка на мобильном, текст без перерисовки после ответа API: подставлять вариант текста сразу, а не после `site-settings`);
   - показывать баннер с задержкой после LCP страницы (не раньше первого paint основного контента), если это не нарушает требование показа до согласия;
   - серверное чтение cookie согласия, чтобы SSR не рендерил баннер тем, кто уже согласился (только если замер покажет выгоду; учесть `force-dynamic`).
   Не выбирать вариант, который скрывает баннер от пользователя или откладывает запрос согласия без причины: вопрос юридически значимый, при сомнении записать вопрос владельцу.
5. Повторить замер тем же способом, записать «после» в PROGRESS.
6. Если на локальном стеке цель не достигается, но разница только в среде, снять замер на стенде с реальным сервером (когда он будет) и зафиксировать результат; без стенда задача закрывается только с пометкой «цель подтвердить на сервере» и пунктом в LAUNCH_CHECKLIST.
7. Прогнать e2e согласия (`cookie-banner.spec.ts`, `consent.spec.ts`), затем `bash scripts/e2e-cleanup.sh` и вернуть dev-стек.

## Тесты

Playwright:
- успех: существующие спеки 1.14 и 3.5 (`frontend/e2e/cookie-banner.spec.ts`, `frontend/e2e/consent.spec.ts`) остаются зелёными; баннер виден новому гостю на мобильном и десктопе, «Прийняти всі» и «Лише необхідні» сохраняют выбор.
- ошибка/обход: при недоступном `GET /api/v1/site-settings/` баннер всё равно показывается и работает (маршрут мокается через `page.route`); GA4 не загружается до «Прийняти всі»; если выбран вариант с задержкой показа, тест ждёт баннер через `expect(...).toBeVisible()`, а не по таймеру.
- новый тест на изменённое поведение: если текст баннера перестанет зависеть от ответа API, проверить обе формулировки (с GA4 и без) по тексту, не по CSS-классу.
