# Задача 2.5: Корректность расчёта: пенсионный сбор, EV, тарифы, курс

## Контекст
Ядро калькулятора (`pricing/calculator.py`) чистое и на Decimal, но подбор тарифов лежит во view, и там несколько ошибок, из-за которых клиент и брокер видят неверные цифры (`docs/audit/02_pricing.md`).

- **02-Q6 (важно)**: подбор тарифов, выбор брекета пенсионного сбора и фоллбэк курса (~100 строк) — во view `pricing/views.py:160-251` (плюс `_lookup_tier`/`_lookup_fixed_fees` в `pricing/views.py:48-87`). Это нарушает CLAUDE.md §1 («бизнес-логика — в `pricing/calculator.py`»). Тесты импортируют эти функции из view: `pricing/tests.py:584,602,669`.
- **02-Q4 (важно)**: при перекрытии периодов побеждает старая или случайная запись. `UsLandRoute` сортируется по `valid_from` по возрастанию (`pricing/views.py:180-186`), `OceanFreightRate` и `EuToUaDeliveryRate` не сортируются вообще (`:188-200`), фиксированные сборы тоже (`:76-87`). В `DateRangeModel` (`pricing/models.py:6-11`) нет проверки `valid_to >= valid_from` и пересечений.
- **02-Q5 (важно)**: фоллбэк курса «ближайший предыдущий» на деле берёт самый новый курс, даже позже `calculation_date` (`pricing/views.py:202-224`, сортировка `reverse=True` по всем датам без фильтра `<= calc_date`).
- **02-Q2 (важно, ждёт Q5)**: брекет пенсионного сбора выбирается по `цена аукциона × курс` (`pricing/views.py:239-251`), а ставка применяется к `pre_pension_uah` — полной стоимости с логистикой и налогами (`pricing/calculator.py:211-214`). На границах брекета получается не та ставка.
- **02-Q7 (важно, ждёт Q5)**: таможенная стоимость = аукцион + US land + фрахт до порта ЕС, без доставки до границы Украины (`pricing/calculator.py:182-183`). Юридически не проверено.
- **02-Q3 (важно)** и **09-Q4 (важно)**: акциз EV/PHEV = `ev_rate × battery_kwh` (`pricing/calculator.py:189-190`). `battery_capacity_kwh` необязателен с default 0 и к тому же `IntegerField` (`pricing/serializers.py:19`). В UI поля нет, в списке топлива нет PHEV (`frontend/app/calculator/page.tsx:68-75`, `frontend/api/pricing.ts:4-13`). Итог: акциз электромобиля всегда 0.
- Связанные желательные в том же месте: 02-C6 (формула возрастного коэффициента min 1 / max 15 в коде, `pricing/calculator.py:148-155`), 02-Q9 (`calculation_date=None` сохраняется строкой `'None'`, `pricing/views.py:326`), 02-Q10 (фактическая дата курса не пишется в снимок, `pricing/views.py:300,309`), 02-S4 (снимок `Calculation` редактируется в админке: `total_usd`, `total_uah`, `user`, `is_estimate`, `pricing/admin.py:70-75`).
- Q5 (открыт): как правильно считать базу пенсионного сбора и таможенную стоимость. По умолчанию: всё остальное делать сразу, эти две формулы сделать настраиваемыми в админке с текущим поведением по умолчанию и переключить после ответа.

## Цель
- [ ] Подбор тарифов — чистая функция `select_rates(catalog, params, on_date) -> SelectedRates` в `pricing/calculator.py` без обращений к БД. На вход — списки объектов тарифов (из `pricing/cache.py`) и параметры. На выход — выбранные записи или список недостающих. View только загружает каталог, вызывает функции, сохраняет `Calculation` и формирует ответ (02-Q6).
- [ ] При нескольких активных записях на дату побеждает запись с самым поздним `valid_from`, при равенстве — с большим `pk`. Правило одинаковое для всех тарифных моделей (02-Q4).
- [ ] В админке нельзя сохранить тариф с `valid_to < valid_from` и тариф, чей период пересекается с другим тарифом того же ключа (например, тот же маршрут `auction_location + us_port`). В БД стоит `CheckConstraint valid_to >= valid_from` (02-Q4).
- [ ] Курс берётся с максимальной датой `<= calculation_date`. Если такого нет — тариф считается отсутствующим (422), а не берётся курс «из будущего». Фактические даты курсов USD→UAH и USD→EUR пишутся в снимок и в ответ (02-Q5, 02-Q10).
- [ ] Пенсионный сбор: брекет выбирается внутри чистого калькулятора по базе, которая задана в данных. Настройка `CustomsCalcRule` (с `valid_from/valid_to`) хранит `pension_bracket_base` и `pension_rate_base`. Значения по умолчанию воспроизводят текущие цифры. После ответа на Q5 их меняют в админке без правки кода (02-Q2).
- [ ] Таможенная стоимость: флаг `customs_value_includes_eu_to_ua` в той же `CustomsCalcRule`. По умолчанию `False` (как сейчас), переключается после ответа на Q5 (02-Q7).
- [ ] Возрастной коэффициент берёт `age_coeff_min`, `age_coeff_max` и `age_offset_years` из `CustomsCalcRule` (02-C6).
- [ ] Правило, по которому считали (id и значения полей `CustomsCalcRule`), лежит в `rates_snapshot`.
- [ ] EV и PHEV: `battery_capacity_kwh` — `DecimalField` (например 75.5). Для `electric` и `phev` он обязателен и больше 0, иначе 400 с ошибкой поля. Если у активной ставки акциза для этого топлива `ev_excise_eur_per_kwh` пустой → 422 «нет ставки акциза EV» (02-Q3).
- [ ] На фронте в калькуляторе есть PHEV и поле «Ємність батареї (кВт·год)». Поле видно и обязательно только для электро и PHEV (09-Q4). Списки справочников из API — задача 2.6, здесь только это поле и опция.
- [ ] `calculation_date=None` не превращается в строку `'None'` в `inputs_snapshot`. Decimal сохраняются строкой, даты — ISO (02-Q9).
- [ ] Снимок `Calculation` в админке только для чтения (все поля readonly, `has_add_permission=False`, `has_change_permission` только просмотр) (02-S4).
- [ ] `is_estimate: true` по-прежнему в каждом ответе (CLAUDE.md). Метки `# ПРОВЕРИТЬ по действующему законодательству` у ставок акциза и пенсионного сбора сохраняются.

## Шаги
1. **Чистый подбор (02-Q6).** В `pricing/calculator.py` добавить:
   - `@dataclass RateCatalog`: списки `auction_fee_tiers`, `auction_fixed_fees`, `us_land_routes`, `ocean_freight`, `eu_to_ua`, `exchange_rates`, `excise_rates`, `pension_brackets`, `customs_rules`.
   - `_pick_active(items, on_date, predicate)`: фильтр по `_is_active` и предикату, выбор `max(key=(valid_from, pk))`.
   - `select_rates(catalog, params, on_date) -> SelectedRates` с полем `missing: list[str]`. Логику `_lookup_tier` и `_lookup_fixed_fees` перенести сюда без изменения смысла (приоритет точного `title_type`, затем `any`).
   - Курс: `max(date)` среди записей пары с `date <= on_date`.
   Функции без импорта Django и ORM.
2. **View.** `CalculateView.post`: сериализатор → `RateCatalog` из `pricing_cache` → `select_rates` → при `missing` 422 (формат ответа `{'error', 'missing'}` сохранить, на него опирается фронт 2.6) → `calc_auction_fees` → `build_rate_snapshot_from_db` → `calculate_landed_cost` → `Calculation.objects.create`. Обработку исключений (02-S1) делает 2.6, здесь не расширять `try`.
3. **Периоды (02-Q4).** В `DateRangeModel`: `overlap_key_fields: tuple[str, ...] = ()` и `clean()`: `valid_to >= valid_from`; пересечение с записями того же ключа (исключая себя), где ключ задан у каждой модели (`UsLandRoute`: `auction_location, us_port`; `OceanFreightRate`: `us_port, eu_port`; `EuToUaDeliveryRate`: `eu_port`; `AuctionFeeTier`: `auction, member_type, payment_type, title_type, bid_min`; `AuctionFixedFee`: `auction, fee_type, title_type`; `CustomsExciseRate`: `fuel_type, engine_cc_min`; `PensionFundBracket`: `min_value_uah`; `CustomsCalcRule`: без ключа — одно правило на дату). Миграция `0007` (причина: запретить некорректные периоды на уровне БД): `CheckConstraint(condition=Q(valid_to__isnull=True) | Q(valid_to__gte=F('valid_from')), name='%(class)s_valid_range')` в `Meta` абстрактной модели. Перед миграцией проверить, что в сид-данных нарушений нет. Если есть — data-миграция, которая их исправляет (с объяснением в отчёте).
4. **Курс (02-Q5, 02-Q10).** В `RateSnapshot` добавить `usd_to_uah_date`, `usd_to_eur_date`. В `rate_snapshot_to_dict` — тоже. В ответе `exchange_rate_date` — фактическая дата курса USD→UAH.
5. **Правило растаможки (02-Q2, 02-Q7, 02-C6).** Модель `CustomsCalcRule(DateRangeModel)`, миграция `0005` (причина: формулы, зависящие от законодательства, должны быть данными, CLAUDE.md §3):
   - module-level `PensionBase(TextChoices)`: `auction_price` (цена аукциона × курс), `customs_value` (таможенная стоимость в грн), `customs_value_with_taxes` (таможенная + пошлина + акциз + НДС), `total_before_pension` (текущая формула `pre_pension_uah`).
   - поля: `pension_bracket_base` (default `auction_price`), `pension_rate_base` (default `total_before_pension`), `customs_value_includes_eu_to_ua` (default `False`), `age_coeff_min` (1), `age_coeff_max` (15), `age_offset_years` (0), `note` (TextField, «ПРОВЕРИТЬ по действующему законодательству»).
   - Data-миграция `0006` создаёт правило с этими дефолтами (`valid_from` = дата применения миграции), чтобы цифры на сид-тарифах не изменились.
