# Задача 1.17: Аккаунты — отзыв сессий в админке, регистр email, лимиты (D1–D9)

Источник: `docs/audit/SECURITY_AUDIT_2026-10-25.md`, раздел D. После задачи **обязательна проверка `security-reviewer`** (аккаунты и права). Задача дополняет 1.5 (перебор), 1.7 (сброс пароля) и 1.2 (роли), но их не переделывает.

## Контекст
- **D1 (важно), `users/admin.py:58`, `:110`:** смена пароля через админку («Змінити пароль») и `manage.py changepassword` **не отзывает сессии**: `session_version` не растёт, старые access/refresh работают (подтверждено пробой). Сценарий: аккаунт угнан, владелец или админ меняет пароль, а у атакующего токен остаётся.
- **D2 (важно), `users/views.py:125`, `users/models.py:118`:** вход чувствителен к регистру email, регистрация и сброс — нет (`John.Doe@…` не входит как `john.doe@…`, подтверждено 401). Возможны дубли аккаунтов, отличающиеся регистром.
- **D3 (недочёт), `users/serializers.py:33`:** `validate_password` вызывается без `user`, `UserAttributeSimilarityValidator` не работает: пароль = email принят (201).
- **D4 (недочёт), `users/views.py:255`, `:346`:** письма сброса и «вже є акаунт» лимитированы только по IP. Атака: с пула IP бомбить чужой ящик и портить репутацию домена.
- **D5 (недочёт), `core/settings.py:21`:** `_TESTING = 'test' in sys.argv` срабатывает на `celery -Q test` или `--hostname test`: в проде отключаются проверка SECRET_KEY, HSTS, капча, почта уходит в locmem.
- **D6 (недочёт), `users/admin.py:128`:** `is_superuser`, `is_staff`, `groups`, `user_permissions` правит любой staff с правом `change_customuser` (сейчас никому не выдано — скрытая эскалация прав).
- **D7 (недочёт), `users/serializers.py:44`:** телефон при регистрации не валидируется (`UA_PHONE_VALIDATOR` только в профиле).
- **D8 (недочёт), `users/services.py:35`:** проверка «уже есть pending-заявка дилера» без транзакции — два параллельных POST дают две заявки.
- **D9 (недочёт), `core/test_runner.py:58`:** сетевой предохранитель не перехватывает `connect_ex` и `sendto` (UDP).

## Цель
- [ ] **D1:** любая смена пароля (форма «Змінити пароль» в админке, `changepassword`, API) вызывает `revoke_all_sessions(user)`: `session_version` растёт, старые access/refresh → 401. Предпочтительна централизованная реализация (переопределение `set_password` для существующего пользователя либо сигнал), а не только форма админки: так закрывается и `changepassword`.
- [ ] **D2:** вход, регистрация, сброс и поиск пользователя используют один регистр: email хранится в нижнем регистре, `get_by_natural_key` — `email__iexact`, в БД `UniqueConstraint(Lower('email'))`. Миграция приводит существующие email к нижнему регистру; **если найдены дубли — миграция останавливается и выводит список, автоматически не сливает** (решение владельца).
- [ ] **D3:** `validate_password(password, user=CustomUser(email=…, …))` в `validate()`; пароль, совпадающий с email, → 400.
- [ ] **D4:** отдельный лимит по HMAC-хэшу адреса (например, `password_reset_email` ~3/час; значение — в `THROTTLE_*` из settings, цифра из аудита «~3/час» — предложение, подтвердить) для сброса пароля и письма «вже є акаунт»; ответ тот же (не раскрывает существование аккаунта).
- [ ] **D5:** `_TESTING = sys.argv[1:2] == ['test']`; проверено, что `scripts/test-backend.*`, CI и `python -m django test` по-прежнему определяются как тестовый запуск.
- [ ] **D6:** поля `is_superuser`, `is_staff`, `groups`, `user_permissions` в `UserAdmin` — только чтение для не-superuser; сервер отклоняет подмену POST'ом.
- [ ] **D7:** `RegisterSerializer` валидирует телефон тем же `UA_PHONE_VALIDATOR`; пустой телефон остаётся допустимым, если он необязателен.
- [ ] **D8:** частичный `UniqueConstraint` на pending-заявку дилера на пользователя; параллельный второй POST → 409.
- [ ] **D9:** предохранитель `core/test_runner.py` перехватывает `socket.connect_ex` и `sendto` через `_check_address`.

## Тесты
Django (каждый — с проверкой мутацией):
- **D1:** staff меняет пароль пользователю через админку → старый access и refresh → 401, новый вход работает; то же для `call_command('changepassword')`; чужому админ-действию аноним → редирект на логин.
- **D2:** вход как `John.Doe@x` и `john.doe@x` — один и тот же аккаунт (200); регистрация второго аккаунта с другим регистром → 400/ответ как для существующего; на уровне БД дубль по `Lower(email)` → `IntegrityError`; миграция на данных с дублями — понятная ошибка и список.
- **D3:** пароль = email → 400.
- **D4:** 4-й запрос сброса на один адрес с разных IP → 429 (или тот же нейтральный ответ без письма — по выбранному варианту, `mail.outbox` не растёт); письмо «вже є акаунт» — то же; чужой адрес не раскрывается.
- **D5:** подпроцесс/мок `sys.argv = ['celery', '-Q', 'test']` → `_TESTING` ложно; `['manage.py', 'test']` → истинно.
- **D6:** staff с правом `change_customuser` (без superuser) не может изменить `is_superuser`/`groups` (поле readonly + POST с подменой не меняет значения); superuser может.
- **D7:** телефон `abc` → 400; корректный украинский → 201.
- **D8:** две pending-заявки на одного пользователя → `IntegrityError` на уровне БД; второй POST → 409 (на Postgres — поток-тест `skipUnless(vendor == 'postgresql')`).
- **D9:** `socket.socket().connect_ex(('example.com', 80))` и `sendto` в тесте → предохранитель роняет тест.
- 401/403: эндпоинты регистрации/сброса остаются публичными (`AllowAny`), профиль и admin-действия без прав → 401/403 (общая матрица `tests/test_authz_matrix.py`).
Playwright: успех — регистрация, вход с другим регистром email проходит; ошибка/обход — повторная регистрация с тем же адресом в другом регистре показывает нейтральное сообщение, а не «аккаунт создан»; смена пароля в профиле разлогинивает второй контекст браузера (уже есть в 1.7 — расширить сценарием «админ сменил пароль»: сессия второго контекста недействительна после перезагрузки).
