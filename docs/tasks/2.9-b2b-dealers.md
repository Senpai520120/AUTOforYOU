## Контекст
Сценарий 4 из `docs/audit/20_SCENARIOS.md` («Дилер: заявка → верификация → B2B-доска») проходит до шага 6 и рвётся на шаге 7.

- **09-Q2** (критично): карточки B2B-доски ведут на `/listings/<id>` (`frontend/components/listings/ListingCard.tsx:26`, используется в `frontend/app/b2b/page.tsx:78,87`). SSR-страница лота запрашивает API **анонимно**: `fetch` без заголовков, `next: { revalidate: 300 }` (`frontend/app/listings/[id]/page.tsx:12-23`, запрос на `:14`). Анониму сервер отдаёт только retail (`listings/views.py:76-77`), поэтому любой оптовый лот у дилера открывается как 404. Чинится только при cookie-аутентификации: SSR должен переслать cookie пользователя. Это задача **1.4** (09-S1, JWT пока в `localStorage`, `frontend/api/client.ts:4,13,22,71`).
- **04-Q3** (важно): истёкший срочный выкуп остаётся вверху B2B-доски. Сортировка идёт по булеву полю `ordering = ['-is_express_buyout', '-created_at']` (`listings/views.py:103`), а не по фактической активности (`get_is_express_active`, `listings/serializers.py:25-31`). Фронт тоже группирует по `l.is_express_buyout` (`frontend/app/b2b/page.tsx:54-55`), поэтому истёкший лот попадает в секцию «Терміновий викуп».
- **09-Q10** (важно): на `/b2b` запрос `listingsApi.b2bBoard({}).then(setData).finally(...)` без `catch` (`frontend/app/b2b/page.tsx:23`). 403, 500 и сбой сети показываются как «Оптових лотів поки немає» (`:64-67`). Грузится только первая страница (`:53`), пагинации и фильтров нет, хотя API их поддерживает (`listings/views.py:100-107`, `frontend/api/listings.ts:27-28`).
- **09-Q8** (важно): заявка дилера читает `err.detail` (`frontend/app/dealers/apply/page.tsx:64`), а клиент кладёт тело ответа в `err.data` (`frontend/api/client.ts:43`). 409 «У вас уже есть заявка на рассмотрении.» (`users/views.py:136-137`) и ошибки полей 400 (`users/views.py:129`) до пользователя не доходят.
- **20-G1** (важно): о новой заявке дилера никто не узнаёт. `apply_for_dealer` только создаёт запись (`users/services.py:20-37`), ни email, ни Telegram, ни in-app. При этом пользователю обещано «Менеджер розгляне її та повідомить вас на email» (`frontend/app/dealers/apply/page.tsx:35`).
- Связанные находки того же места:
  - **09-S2 / 04-S6**: `/b2b` проверяет доступ по `user.role === 'admin'` (`frontend/app/b2b/page.tsx:17`). По ROADMAP 09-S2 закрывается в задаче 1.2. Если к началу 2.9 это не сделано, заменить на `user.is_verified_dealer || user.is_staff` здесь.
  - **09-Q9** (желательно): страница заявки не проверяет текущую заявку. `dealersApi.getApplication` не используется (`frontend/api/dealers.ts:17-18`), и уже верифицированный дилер снова видит форму. Берётся в задачу.
  - 01-Q2 / 04-Q6 / 04-S7 (одобрение только через сервис, отзыв верификации) — задача 1.2, здесь не делать.

## Цель
- [ ] **09-Q2**: verified dealer и staff открывают оптовый лот по ссылке с B2B-доски и видят карточку (200, не 404). Для гостя и buyer тот же URL по-прежнему 404.
- [ ] **09-Q2**: SSR-запрос лота с cookie пользователя не кэшируется между пользователями. Для него `cache: 'no-store'`: ответ дилера не должен попасть гостю из data cache Next. У оптового лота `robots: noindex` и нет og-метаданных с ценой.
- [ ] **04-Q3**: на доске выше идут только лоты с **активным** срочным выкупом (`is_express_buyout=True` и `express_buyout_until` пусто или в будущем). Истёкшие сортируются как обычные. В `ordering_fields` нет сортировки по сырому булеву флагу. На фронте секция «Терміновий викуп» строится по `is_express_active`.
- [ ] **09-Q10**: `/b2b` различает «лотов нет» и ошибку. 403 → «Доступ обмежено», 5xx/сеть → сообщение об ошибке с кнопкой «Спробувати ще раз». Есть пагинация и фильтры (поиск, статус, макс. цена), параметры хранятся в URL.
- [ ] **09-Q8**: форма заявки дилера показывает `detail` из 409 и ошибки полей 400 под соответствующими полями. Разбор ошибки — через общий хелпер (например `frontend/lib/api-errors.ts`), который потом можно переиспользовать для 10-Q6.
- [ ] **09-Q9** (желательно): `/dealers/apply` при загрузке запрашивает `GET /api/v1/dealers/application/`. Pending → «Заявка на розгляді», approved/verified → ссылка на `/b2b`, rejected → форма и причина отказа. Для анонима форма не мелькает до редиректа.
- [ ] **20-G1**: после создания заявки (`transaction.on_commit`) менеджер получает уведомление:
  - in-app `Notification` новому типу `DEALER_APPLICATION` для всех пользователей с ролью broker/admin (роль из 1.2);
  - Telegram через брокерский канал из задачи 2.2 (chat_id брокера из админки или `.env`, 07-C1), если он настроен.
  Если ничего не настроено, заявка всё равно создаётся без ошибки, а сбой отправки только логируется, без ПДн в логе. Текст на экране успеха соответствует реальному каналу ответа.
