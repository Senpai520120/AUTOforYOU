# Задача 9.55: Runbook и сторож для Celery и бэкапа

## Контекст
`/healthz` (`core/health.py`) проверяет только БД и Redis. Если `celery_worker` или `celery_beat` остановились, заявка лежит в БД, монитор зелёный, брокер ничего не получает. Инструкции на случай сбоя нет, а сервер обслуживает один человек.

## Цель
- Beat раз в 5 минут ставит задачу, worker пингует внешний сервис-сторож (`CELERY_HEARTBEAT_URL`). Нет пинга — сторож сам шлёт оповещение.
- После успешного бэкапа `docker/backup/backup.sh` пингует `BACKUP_HEARTBEAT_URL`. Сбой пинга не портит бэкап.
- Пустой адрес выключает пинг. Секретный адрес не попадает в логи.
- `docs/RUNBOOK.md`: сценарии сбоев с проверкой, действием и откатом; доступы; учения.

**Вне этой сессии (остаток, ◐):** алерт на рост `FailedTask`.

## Файлы
Изменить: `core/tasks.py`, `core/settings.py`, `core/launch.py`, `docker/backup/backup.sh`, `docker/backup/Dockerfile`, `docker-compose.yml`, `.env.example`, `.env.docker.example`, `docs/LAUNCH_CHECKLIST.md`, `scripts/tests/test_backup_rotation.sh`.
Создать: `core/tests_heartbeat.py`, `docs/RUNBOOK.md`.
Не трогать: `.env`, `cars/`.

## Шаги
1. Задача `core.tasks.send_celery_heartbeat`, запись в `CELERY_BEAT_SCHEDULE` с `expires` меньше периода, чтобы при мёртвом worker пинги не копились и не давали ложный зелёный сигнал.
2. Пинг в конце успешного `backup.sh`, `curl` в образе бэкапа.
3. Шаблоны env, `launch_check`, чек-лист.
4. Runbook.

## Тесты
Django: `core/tests_heartbeat.py` — пустой адрес, пинг, сетевая ошибка и ошибка статуса без адреса в логе, неверный адрес, расписание.
Shell: `scripts/tests/test_backup_rotation.sh` — пинг при успехе, нет пинга при неудаче, сбой пинга не меняет код возврата.
Playwright: не требуется, интерфейса нет.

## Для владельца (LAUNCH_CHECKLIST)
Завести две проверки у сервиса-сторожа и заполнить `CELERY_HEARTBEAT_URL`, `BACKUP_HEARTBEAT_URL`. Провести учения из `docs/RUNBOOK.md` на сервере.

## Готово, когда
Тесты зелёные, мутация ловится, `check-infra.sh` чистый, runbook сверен со скриптами.
