# Задача 2.12: Надёжность доставки заявки брокеру (резервный email, досыл, предупреждение админам)

> Источник: Н-28 (`docs/audit/36_PARITY_K_L.md`, K5.2, K5.3, L2.1; `docs/audit/32_NEW_TASKS_INDEX.md`). Волна: [ВОЛНА-1]. Оценка: 1 сессия. Security-reviewer не обязателен (но в письме брокеру есть ПДн: проверить тестом «в логах нет телефона и имени»).

## Контекст
- Задача 2.2 шлёт заявку брокеру только в Telegram: при отсутствии токена или chat_id ставит `telegram_status=skipped_not_configured`, при сбое сети три повтора по 30 с и `failed`; дальше только ручной admin-action «Надіслати брокеру повторно» (`docs/tasks/2.2-lead-broker-notify.md`, цель и шаги 5-9). Резервного канала и автоматического досыла нет. Решение владельца (ANSWERS, шаг 6): резервный email, асинхронные письма с `EMAIL_TIMEOUT`, периодический досыл неотправленных заявок.
- Настройки получателя живут в одном месте: `LeadNotificationSettings` (singleton из 2.2). Резервные адреса добавляются туда же (2.2 это прямо оставляет за Н-28).
- Письма сейчас синхронные: `send_mail(..., fail_silently=True)` в запросе (`users/services.py:74`, `local_listings/services.py:62`), `EMAIL_TIMEOUT` в `core/settings.py:339-344` нет. Асинхронную отправку с `EMAIL_TIMEOUT` и сервис `send_email(to, subject, body)` делает 3.4 (`docs/tasks/3.4-nbu-smtp-liqpay-telegram-adapters.md`, цель про `send_email_task`; сервис возвращает «поставлено в очередь / не настроено»). Здесь он только используется, второй отправитель не создаётся.
- Расписание Celery: `core/settings.py:373-394` (`CELERY_BEAT_SCHEDULER` — `DatabaseScheduler`, `:368`). В тестах без `REDIS_URL` Celery eager (`:363-365`), `on_commit` срабатывает только в `captureOnCommitCallbacks(execute=True)`.
- Типы in-app уведомлений: `notifications/models.py:6-15` (типа «заявка не доставлена» нет). Получатели «админы» — по ролям из 1.2.
- Код приложения `leads` ещё не написан (2.1, 2.2): ссылки на файлы даны по этим задачам, при выполнении сверить фактические имена.

## Цель
- [ ] Если Telegram не настроен, выключен или заявка ушла в `failed` после ретраев, брокеру автоматически уходит письмо с теми же данными (имя, телефон, способ связи, авто, итог, источник, ссылка на заявку). Заявка при этом создаётся всегда, ответ API не зависит от почты.
- [ ] Адреса брокера: `LeadNotificationSettings.broker_emails` (по одному в строке, валидация email), если пусто — `.env` `BROKER_NOTIFY_EMAIL`. В коде адресов нет. Тема и текст — шаблоны в админке (`email_subject_template`, `email_body_template`) с теми же плейсхолдерами, что и у Telegram-шаблона 2.2, значения вставляются как есть (письмо текстовое, HTML не используется), переводы строк в теме вычищаются (защита от инъекции заголовков).
- [ ] У `Lead` появляются `email_status` (`pending`, `sent`, `skipped_not_configured`, `failed`), `email_sent_at`, `email_error` (код ошибки без текста письма и без ПДн), счётчик попыток `notify_attempts`, `last_notify_attempt_at`, `undelivered_alerted_at`. Список `LeadAdmin` показывает оба статуса.
- [ ] Заявка считается доставленной, если хотя бы один канал в `sent`.
- [ ] Периодическая задача `leads.tasks.resend_undelivered_leads` по расписанию раз в `LEAD_NOTIFY_RETRY_MINUTES` (`.env`) берёт недоставленные заявки старше этого интервала и повторяет оба канала (идемпотентно: `sent` не отправляется второй раз). Лимит `LEAD_NOTIFY_MAX_ATTEMPTS` (`.env`).
- [ ] После исчерпания попыток админы получают одно in-app уведомление (новый тип `lead_undelivered`, ссылка на заявку в админке) и запись в лог (только `lead_id`). Повторно по той же заявке не шлётся (`undelivered_alerted_at`).
- [ ] Если не настроен ни один канал (оба `skipped_not_configured`), досыл не зацикливается, а в списке заявок виден явный красный предупреждающий баннер «Жоден канал сповіщення брокера не налаштовано» (`messages.warning`, как в 2.2).
- [ ] Нет синхронного `send_mail` в `leads/`; письмо ставится только через сервис 3.4 и только из `transaction.on_commit` или задачи Celery.

## Шаги
1. Миграции (причина: нужно хранить статус второго канала и попытки, иначе досыл и предупреждение нельзя сделать): `NotifyStatus` как module-level `TextChoices` (уже есть из 2.2, переиспользовать). Дефолтные шаблоны письма — текст на украинском с плейсхолдерами, редактируются в админке.
2. `leads/notify.py`: `render_new_lead_email(lead, settings_obj) -> (subject, body)` с `defaultdict(str)` для неизвестных плейсхолдеров; `broker_emails()` — настройки, затем `.env`; пустой список → `skipped_not_configured`.
3. `leads/tasks.py`: `notify_broker_email(lead_id, force=False)` — идемпотентна по `email_status == sent`; вызывает `send_email` из 3.4; результат «не настроено» → `skipped_not_configured`, ошибка → `failed` и код ошибки, `notify_attempts += 1`.
4. `resend_undelivered_leads`: выбирает заявки, где ни один канал не `sent`, хотя бы один канал не `skipped_not_configured`, `notify_attempts < LEAD_NOTIFY_MAX_ATTEMPTS`, и последняя попытка старше интервала; ставит обе задачи с `force=False`. Для исчерпавших лимит — шаг 5. Выборка с `LIMIT` и `select_for_update(skip_locked=True)` внутри короткой транзакции, чтобы два воркера не слали одно и то же.
5. Предупреждение админам: получатели — `admin`/`superuser` (хелпер из 1.2), одно уведомление на заявку.
6. Расписание в `CELERY_BEAT_SCHEDULE` (период из `LEAD_NOTIFY_RETRY_MINUTES`); в `.env.example` комментарии, в LAUNCH_CHECKLIST — как проверить (тестовая заявка → Telegram и email).

## Тесты
Django (`leads/tests.py`; Telegram и `send_email` замоканы, почта через `mail.outbox`, `captureOnCommitCallbacks(execute=True)`):
- Telegram `sent` → письмо не уходит. Telegram не настроен → ровно одно письмо на адреса из настроек, `email_status=sent`, заявка 201.
- Адресов в настройках нет, `BROKER_NOTIFY_EMAIL='b@example.com'` в `override_settings` → письмо на него; нигде нет адресов → `skipped_not_configured`.
- `send_message` бросает `ConnectionError` до `failed` → письмо ушло; сбой SMTP (мок `send_email` бросает) → создание заявки не падает, `email_status=failed`, в `email_error` нет текста письма и телефона.
- Имя с переводом строки `Ivan\r\nBcc: x@y` → в теме нет `\n`; `{foo}` в шаблоне → пустая строка.
- Досыл: заявка с обоими `failed` и старой последней попыткой → задача повторяет оба канала; `sent` не отправляется повторно; свежая попытка (моложе интервала) не трогается; два последовательных запуска не дублируют письма.
- Лимит попыток исчерпан → одно `Notification(type='lead_undelivered')` админам, второй запуск не создаёт ещё одно; оба канала `skipped_not_configured` → попытки не растут, баннер в changelist.
- Логи (`assertLogs`) не содержат телефона и имени; в `leads/` нет `send_mail(` (grep в тесте или шаг проверки).
Playwright: нет UI для клиента. Сквозной сценарий «заявка из калькулятора → видна в админке с обоими статусами» проверяется Django-тестом на changelist `LeadAdmin` (200, в HTML есть номер заявки и оба статуса).

### Решения владельца после промта 02
Журнал в группу (AFY-ID, марка/модель, бюджет, город, время UTC) и личное уведомление брокеру (с контактами) — **два отдельных канала**: у каждого свои статус, `message_id`/статус отправки, счётчик попыток и повтор. Сбой одного не влияет на другой.

- [ ] Досыл журнал-группы (`LEAD_JOURNAL_CHAT_ID`, 2.2/2.15): неотправленная запись повторяется периодической задачей отдельно от личного уведомления (Telegram/email брокеру), `message_id` сохраняется при успехе, окончательное падение уходит в учёт 8.9 и предупреждение админам. Журнал не входит в условие «заявка доставлена»: доставленность определяется личным уведомлением брокеру.
- [ ] Повтор не дублирует сообщение, если `message_id` уже записан (идемпотентность). Повтор журнала берёт тот же белый список полей, ПДн в группу не уходят ни при первой отправке, ни при повторе. Повтор личного уведомления (с контактами) уходит только брокеру, не в группу.
- [ ] Тесты Django (моки): сбой группы → повтор журнала отправляет один раз, личное уведомление не повторяется; сбой личного уведомления → повтор только его, журнал не дублируется; повтор после успеха ничего не шлёт; в тексте повтора журнала нет имени и телефона.
