# Задача 10.1: Полная сумма «РАЗОМ» в USD (с акцизом, ПДВ и пенсионным сбором)

## Контекст
Источник: `docs/audit/41_REVIEW_2026-11-11.md`, находка A1, п.1. Решение владельца (2026-11-19, `docs/ANSWERS.md`): «РАЗОМ» в USD = полная сумма, включая акциз, ПДВ и пенсионный сбор, по курсу из снимка расчёта (тому же, что у `total_uah`).

Что сейчас:
- `pricing/calculator.py:257`: `total_usd = total_logistic_usd + duty_usd + after_customs_usd`. Акциз, ПДВ и пенсионный сбор (`customs_total_uah`) в него не входят, хотя `total_uah` (стр. 281–282) их включает. Клиент видит USD заметно ниже реальной цены под ключ.
- `LandedCostBreakdown.total_usd` (стр. 154) попадает в `to_dict()` (стр. 166) и в `Calculation.breakdown` (JSON); отдельная колонка `Calculation.total_usd` (`pricing/models.py:565`) пишется в `pricing/views.py:225`.
- `total_usd` читают: `leads/services.py:121,155,161` (снимок и `Lead.total_usd`), `leads/admin.py:213`, `landings/services.py:167,214`, `landings/serializers.py:10,25`, `landings/admin.py:38,48`, тесты `pricing/tests.py:283–295,788–795`, `landings/tests.py` (85, 143, 203, 528–543).
- Фронт: `components/calculator/CalcBreakdown.tsx:72–74` («РАЗОМ» = `b.total_usd`), `components/landing/LandingCalc.tsx:62` (`landing-total-usd` = `c.total_usd`), `app/prigon/[slug]/page.tsx:88` (`budgetFrom(p.calculation.total_usd)`), типы `lib/types.ts:88,194`.
- Тесты, которые завязаны на текущее поведение: `e2e/landing.spec.ts:51–52,74` (сверяют `landing-total-usd` и бюджет с `api.calculation.total_usd`), `e2e/calculator-ua-delivery.spec.ts:27`, `e2e/catalog.spec.ts:82`, `e2e/mobile.spec.ts:81`, `e2e/calculator-config.spec.ts:145`.

### Выбор имени (обоснование)
Выбран вариант «**новое поле `total_usd_full`, старое `total_usd` не меняется**», а не «`total_usd` становится полным». Причины:
1. Сохранённые снимки (`Calculation.breakdown`, `Lead.calculation_snapshot`) и колонки `Calculation.total_usd`, `Lead.total_usd` уже содержат старое значение. Если сменить смысл `total_usd`, старые и новые записи окажутся несравнимыми под одним именем, а миграция данных невозможна (курс и ставки зафиксированы в снимке, пересчёт задним числом был бы подменой истории).
2. Не ломаются существующие клиенты API и тесты, читающие `total_usd`; добавление поля обратно совместимо.
3. Новое поле живёт в JSON-снимке (`breakdown`), миграция схемы БД не нужна. У старых снимков поля нет: фронт и админка читают `total_usd_full ?? total_usd` (старый расчёт честно показывает старое значение).

Формула: `total_usd_full = (total_uah / usd_to_uah)`, `Decimal`, `quantize(TWO_PLACES, ROUND_HALF_UP)`, курс — `rates.usd_to_uah` того же `RateSnapshot`, что у `total_uah`. Это эквивалентно `total_logistic + after_customs + customs_total_uah / rate` (пошлина учитывается один раз, внутри `customs_total_uah`; прибавлять `duty_usd` сверху нельзя — будет двойной счёт). `is_estimate: true` сохраняется.

## Цель
1. `LandedCostBreakdown` содержит `total_usd_full: Decimal`; он попадает в `to_dict()` (строкой) и в замороженный снимок `Calculation`/`Lead`. `total_usd` не меняется.
2. `total_usd_full ≈ total_uah / usd_to_uah` (расхождение не больше 0.01 USD) и всегда `>= total_usd` (акциз, ПДВ, пенсионный сбор неотрицательны; пошлина в обоих).
3. Ответ API калькулятора: `breakdown.total_usd_full` присутствует; верхнеуровневый `total_usd` и колонка `Calculation.total_usd` прежние.
4. Ответ лендинга (`landings/services.py`) содержит `total_usd_full` рядом с `total_usd` (в `calculation` и в `lead_calculation_snapshot`); сериализатор лендинга его пропускает.
5. UI: строка «РАЗОМ» в `CalcBreakdown.tsx` и `landing-total-usd` в `LandingCalc.tsx` показывают `total_usd_full` (fallback на `total_usd` для старых данных); `defaultBudgetUsd` на `/prigon/[slug]` берётся из `total_usd_full`.
6. Подпись/пояснение у итога (украинский): «Разом (з митом, акцизом, ПДВ і пенсійним збором), орієнтовно». Сумма «без митних платежів» остаётся в данных; в UI не показывается, если не нужна для строк таблицы.

## Тесты
Django (`pricing/tests.py`, `landings/tests.py`, `leads/tests.py`; наследоваться от `tests.base.CleanCacheTestCase`, данные из `tests/factories.py`, без сети):
- `abs(total_usd_full * usd_to_uah - total_uah) <= 0.01 * usd_to_uah` — на нескольких наборах входов (ДВС, EV/PHEV с нулевой пошлиной, гибрид); `total_usd_full >= total_usd`; `total_usd_full - total_usd` ≈ `(excise_uah + vat_uah + pension_fund_uah) / usd_to_uah` (пошлина не удваивается).
- Полная сумма считается по курсу из снимка (`RateSnapshot.usd_to_uah`), а не по текущему: смена курса после расчёта не меняет сохранённый `Calculation.breakdown['total_usd_full']`.
- `total_usd` и колонка `Calculation.total_usd` не изменились (регресс по `pricing/tests.py:788–795`, значение `8365.00` остаётся).
- Снимок `Calculation` содержит оба поля; `to_dict()` отдаёт оба строкой; `isinstance(str)`, `Decimal(...)` разбирается (не float).
- Лендинг: `calculation.total_usd_full` в ответе API, в `lead_calculation_snapshot` и в `Lead.calculation_snapshot` после заявки (подмена клиентом `total_usd_full='1'` игнорируется — по аналогии с `landings/tests.py:534–543`).
- Старый снимок без `total_usd_full` (фикстура-словарь) не роняет админку лендингов и leads (fallback), `is_estimate` остаётся `true`.
- Ошибка/обход: расчёт без ставки (`MissingRate`) по-прежнему даёт `None` на лендинге; поле не появляется без расчёта.

Playwright (`e2e/landing.spec.ts`, `e2e/calculator*.spec.ts`; стек и правила — раздел «E2E» в CLAUDE.md):
- Успех: `landing-total-usd` == `round(api.calculation.total_usd_full)` и строго больше `round(api.calculation.total_usd)`; значение бюджета в форме заявки (`getByLabel(/Бюджет/)`) == `round(total_usd_full)`; в калькуляторе строка «РАЗОМ» в колонке USD равна `breakdown.total_usd_full` и больше суммы без таможенных платежей.
- Ошибка/обход: подмена `total_usd`/`total_usd_full` в теле заявки с лендинга (как `landing.spec.ts:95`) не меняет сохранённый снимок (на сервере остаётся расчёт); у лендинга без расчёта нет `landing-total-usd`.
