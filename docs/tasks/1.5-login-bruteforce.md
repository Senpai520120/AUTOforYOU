# Задача 1.5: Защита от перебора: лимит по IP и аккаунту, блокировка

## Контекст

**01-S2 (критично): нет лимита попыток входа по аккаунту и нет временной блокировки.**
- Вход (`/api/v1/auth/token/`) закрыт только общим throttle `anon` 60/час на IP. Этот лимит один на весь API: `core/settings.py:214`, `:228-235`.
- Счётчика неудачных попыток по email нет. Перебор пароля с множества IP ничем не ограничен.
- После задачи 1.3 вход обрабатывает свой `CookieTokenObtainView` (`users/views.py`), а не стандартный SimpleJWT (`users/urls.py:27` до 1.3).
- Регистрация (`users/views.py:40-44`) и refresh тоже без отдельного лимита.
- Связанное (желательно): 01-S16, админка на `/admin/` (`core/urls.py:12`) без лимита попыток.

**12-S9 (важно): throttling обходится подменой `X-Forwarded-For`.**
- nginx дописывает клиентский XFF: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` в блоке API (`nginx/nginx.conf:34`) и во фронтовом блоке (`:46`).
- `NUM_PROXIES` в `REST_FRAMEWORK` не задан (`core/settings.py:219-240`). Поэтому DRF берёт как идентификатор всю строку XFF, а клиент может менять её в каждом запросе.
- Связанное (желательно): 12-S10, в nginx нет `limit_req` на `/api/v1/auth/` и `/admin/login/`, `server_tokens` не выключен (`nginx/nginx.conf:30-39`).

**Фронт.** Связанное (желательно): 08-S8, любая ошибка входа, включая 429, показывается как «Невірний email або пароль». До 1.4 это `frontend/lib/auth-context.tsx:86`, после 1.4 — функция `login()` в том же файле.

**Кэш.** С Redis (`REDIS_URL`, `core/settings.py:148-159`) кэш общий для всех воркеров gunicorn. Без Redis используется `LocMemCache`, и у каждого воркера свой счётчик. Для счётчика блокировок нужен общий кэш.

## Цель

- [ ] Отдельные scoped-лимиты по IP, значения в `.env`:
  - `login` на `token/`, `THROTTLE_LOGIN_RATE`, по умолчанию `10/min`;
  - `register` на `register/`, `THROTTLE_REGISTER_RATE`, по умолчанию `5/hour`;
  - `refresh` на `token/refresh/`, `THROTTLE_REFRESH_RATE`, по умолчанию `30/min`.
- [ ] Счётчик неудачных входов по аккаунту: ключ — хэш нормализованного email (`lower().strip()`), счётчик общий для всех IP.
  - После `LOGIN_MAX_FAILURES` неудач (по умолчанию 5) за `LOGIN_FAILURE_WINDOW_MINUTES` (15) аккаунт временно блокируется на `LOGIN_LOCKOUT_MINUTES` (15).
  - Во время блокировки вход отклоняется даже с **верным** паролем: ответ 429 и заголовок `Retry-After`.
  - Успешный вход сбрасывает счётчик.
- [ ] Ответ не раскрывает, существует ли аккаунт: для несуществующего email счётчик и блокировка работают так же, и тексты ответов одинаковые.
- [ ] Блокировка не пишет email в лог открытым текстом: в лог идут только хэш и IP.
- [ ] IP клиента определяется правильно:
  - `REST_FRAMEWORK['NUM_PROXIES']` читается из `.env` `NUM_PROXIES`. По умолчанию `0` (dev без прокси, берётся `REMOTE_ADDR`).
  - В Docker задано `1`: `docker-compose.yml`, `.env.docker.example`.
  - nginx в блоке API передаёт `proxy_set_header X-Forwarded-For $remote_addr;` вместо `$proxy_add_x_forwarded_for`. Так подменённый клиентом XFF отбрасывается.
- [ ] (01-S16, желательно) Вход в админку `/admin/login/` использует тот же счётчик по аккаунту: своя `AuthenticationForm` в `AdminSite.login_form` или обработчик сигнала `user_login_failed` плюс проверка в форме.
- [ ] (12-S10, желательно) nginx: `limit_req_zone $binary_remote_addr zone=auth:10m rate=10r/m;` плюс `limit_req zone=auth burst=5 nodelay;` для `location ~ ^/(api/v1/auth|admin/login)/`, и `server_tokens off;`.
- [ ] Фронт (08-S8, желательно): форма входа различает ошибки.
  - 400/401 → «Невірний email або пароль».
  - 429 → «Забагато спроб. Спробуйте через N хв.» (N берётся из `Retry-After`).
  - 5xx или сеть → «Сервіс тимчасово недоступний».
- [ ] Предупреждение при старте, если `not DEBUG` и кэш — `LocMemCache`: «блокировка по аккаунту работает в пределах одного воркера». Сайт не падает.

## Шаги

1. `users/lockout.py`:
   - ключи `login-fail:<sha256(email)>` (счётчик с TTL окна) и `login-lock:<sha256(email)>` (TTL блокировки);
   - инкремент через `cache.add` + `cache.incr`, чтобы не было гонки на Redis;
   - константы только из `settings`.
2. `CookieTokenObtainView.post()`:
   1. `throttle_scope = 'login'` через `ScopedRateThrottle` плюс стандартные классы;
   2. если `is_locked(email)`, вернуть 429 с `Retry-After`, пароль не проверять;
   3. `serializer.is_valid()`: при `AuthenticationFailed` вызвать `register_failure`, при успехе `reset`;
   4. ответ на неудачу — прежний 401 с нейтральным текстом.
3. `NUM_PROXIES` из `.env`. nginx: в `location ~ ^/(api|admin)/` поставить `X-Forwarded-For $remote_addr`. В комментарии написать: за внешним балансировщиком (Cloudflare и т.п.) нужно `real_ip_header` плюс `set_real_ip_from`, это пункт LAUNCH_CHECKLIST.
4. Scope `register` и `refresh` на соответствующих views.
5. (желательно) Админка: `class LockoutAdminAuthenticationForm(AdminAuthenticationForm)`, в `clean()` проверка `is_locked`, учёт неудачи и успеха; подключить через `admin.site.login_form`.
6. (желательно) nginx `limit_req` и `server_tokens off`.
7. Фронт: `login()` бросает ошибку со `status` и `retryAfter`, страница показывает соответствующий текст.

   Если задача 1.4 ещё не влита, эту часть сделать после неё или минимальной правкой того же места, чтобы не конфликтовать с 1.4.
8. Проверка при старте (`AppConfig.ready` или system check `Warning`) про `LocMemCache` в проде.
