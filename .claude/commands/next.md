Выполни одну задачу из ROADMAP.md от начала до конца. Владелец не участвует, пока не сработает одно из
условий остановки ниже.

## 1. Какая задача

- Если указан номер — `$ARGUMENTS`, бери эту задачу.
- Иначе: первая невыполненная задача ВОЛНЫ-1 в порядке критического пути из ROADMAP.md, у которой
  выполнены все зависимости. Если ВОЛНА-1 закончена — ВОЛНА-2. Замороженные задачи не брать.
- Файл задачи — `docs/tasks/<номер>-*.md`.

## 2. Проверка модели

Задачи 1.3, 1.4, 1.10, 4.1 и любые помеченные в ROADMAP как требующие Opus выполняются только на Opus.
Если ты не Opus — ничего не делай и ответь одной строкой:
«Задача X.Y требует Opus: выбери Opus 5.5 в меню модели, затем /clear и /next».

## 3. План

Прочитай файл задачи и `docs/BRIEF.md` §5–§6. Покажи план в 5–10 строк (файлы, шаги, проверки) и сразу
переходи к работе, не дожидаясь ответа.

## 4. Условия остановки (спроси владельца и жди)

- нужно изменить или удалить файлы вне раздела «Файлы» задачи;
- миграция удаляет или необратимо меняет данные;
- нужен ключ, цена, юридический текст или решение, которого нет в `docs/ANSWERS.md`;
- задача явно не укладывается в 2 сессии — предложи деление на a/b;
- тесты красные после двух попыток исправить.

## 5. Работа

- Поиск по коду — агент `code-scout`. Прогоны — агент `test-runner`.
- Во время работы — тесты только затронутого приложения: `scripts/test-backend.ps1 <app>`.
- В конце через `test-runner`: полный `scripts/test-backend.ps1`; если менялся фронт —
  `npm run build` и `npx tsc --noEmit`; Playwright-спеки этой задачи (Docker Desktop должен быть запущен;
  если стек не поднимается — запиши в отчёт, не трать попытки).
- Для e2e разрешено без вопроса (постоянное разрешение владельца): остановить dev-стек `docker compose down`
  **без `-v`**, поднять e2e-стек (команды — CLAUDE.md, «E2E»), после прогона удалить e2e-стек с томами
  и освободить диск: `bash scripts/e2e-cleanup.sh` (снимает e2e-стек с томами, удаляет висячие и устаревшие
  образы, старый кэш сборки) — после КАЖДОГО прогона, даже упавшего; затем поднять dev-стек (`docker compose up -d`).

## 6. Ревью безопасности

Для задач этапа 1, задачи 4.1 и любых изменений аутентификации, прав доступа, платежей, загрузок
и персональных данных: запусти агента `security-reviewer`, исправь все замечания «критично» и «важно»,
снова прогони тесты.

## 7. Завершение

1. Обнови `ROADMAP.md` (галочка), `PROGRESS.md`, при необходимости `docs/LAUNCH_CHECKLIST.md`.
2. Запиши в колонку «Факт» строки задачи в `ROADMAP.md` фактическое число сессий: сколько сессий
   ушло на задачу, включая эту (если задача шла не с первой попытки, посмотри `git log` и `PROGRESS.md`).
   Если факт больше оценки «Сесс.», добавь в `PROGRESS.md` одну строку — почему.
3. Проверь, что в изменениях нет `.env`, `settings.local.json`, ключей и токенов.
4. Коммит: `git add -A` и `git commit -m "задача X.Y: <коротко>"`.
   Если тесты красные — не коммить, остановись с отчётом.
5. Push после коммита (постоянное разрешение владельца, 2026-10-19): `git push origin HEAD`
   (если у ветки нет upstream — `git push -u origin HEAD`). Только текущую рабочую ветку: в `main`
   напрямую не пушить, `--force` не использовать. Если push не прошёл — не чинить, записать в отчёт.
6. Отчёт владельцу — не больше 10 строк: что сделано, результат тестов и push, что нужно от владельца,
   следующая задача и её модель. Последняя строка всегда:
   «Дальше: /clear, затем /next» (или «Дальше: выбери Opus, затем /clear и /next»).
